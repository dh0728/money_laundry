# API 서버 — 수신 관문

동기 백엔드(§5.3). 현재 구현 범위는 **수신 관문 하나**다.

```
목업 생성기 / 은행 API  →  [수신 관문]  →  큐 어댑터  →  (수집 워커 · 나중)
```

- Spring Boot 4.1.0 / Java 21 / Gradle wrapper
- 큐는 아직 로컬 로깅 스텁이다. SQS 연결은 이번 범위가 아니다.

> **이 문서의 §·Q·D·I 절 번호는 설계 원문을 가리킨다.** 원문은 구현 브랜치에 없고
> `docs` 브랜치의 `docs/04_design/jiwon/기획서_아키텍처_설계안.html` 에 있다.
> 사본을 두지 않는 이유는 원문이 개정되는 문서라 두 벌이 되면 어긋나기 때문이다.

## 실행

`JAVA_HOME`은 환경변수로 주입한다. 빌드 파일에 경로를 기록하지 않는다 — 팀원마다 다르다.

```
./gradlew test          # 테스트
./gradlew bootRun       # 8080에서 기동
```

목업 생성기로 왕복 확인:

```
python ../../tools/mock-generator/generator.py --limit 100 \
    --url http://127.0.0.1:8080/api/transactions
```

> 생성기 검증용 `stub_receiver.py`가 8080에 떠 있으면 안 된다. 포트가 충돌하거나, 더 나쁘게는
> 스텁을 상대로 통과를 보고 관문이 검증됐다고 착각하게 된다. 스텁은 JSON 파싱 실패에만 400을
> 주므로 관문의 검증 결함을 하나도 잡지 못한다.

# 수신 계약

`POST /api/transactions`

```
→ 202 Accepted   {"ingest_id": "..."}     접수 완료
→ 400 Bad Request {"error": "..."}        형식 실패, 파이프라인 미진입
→ 5xx                                      큐 발행 실패, 재전송 요망
```

**202는 "접수했다"이지 "적재했다"가 아니다.** 응답 시점에 DB에는 아무것도 없다. 은행이 받는
것은 책임 경계의 확인이며, 그래서 §4의 수신 회계가 따로 필요하다 —
`ACK ingest_id = 처리대기 + 신규적재 + 동일내용중복 + ID충돌 + DLQ`.

`400`에는 `ingest_id`를 발급하지 않는다.

## 요청 본문 — 11개 키

원본 `data/HI-Small_Trans.csv` 헤더는 11열이며 JSON 키 이름과 1:1이 아니다.
아래 행 순서는 원본 열 순서 그대로다.

| # | 원본 CSV 열 | JSON 키 |
|---|---|---|
| — | (원본에 없음 — 송신 측이 생성) | `transaction_id` |
| 1 | Timestamp | `timestamp` |
| 2 | From Bank | `from_bank` |
| 3 | Account | `from_account` |
| 4 | To Bank | `to_bank` |
| 5 | Account | `to_account` |
| 6 | Amount Received | `amount_received` |
| 7 | Receiving Currency | `receiving_currency` |
| 8 | Amount Paid | `amount_paid` |
| 9 | Payment Currency | `payment_currency` |
| 10 | Payment Format | `payment_format` |
| 11 | Is Laundering | **없음 — 정답 라벨이라 보내지 않는다** |

- 3번과 5번은 원본 헤더 이름이 `Account`로 **둘 다 같다.** `from_`/`to_` 구분은 우리 결정이다.
- 6~9번은 **수령이 먼저, 지불이 나중**이다. 동일 통화 거래에서는 두 값이 같은 경우가 많아
  순서를 잘못 읽어도 육안으로 드러나지 않는다.
- **모든 값은 문자열이다.** 은행 코드에 선행 0이 있어(`010`, `03209`) 숫자로 바인딩하면 값이
  깨진다. 금액도 원문을 보존해야 나중 `payload_hash`가 표기 흔들림에 영향받지 않는다.
- 계약에 없는 키는 400이 아니지만 큐 페이로드에도 싣지 않는다. Q-5가 다중 공급원 도입 시
  `source_id` 추가를 예고하므로, 그때 고칠 자리가 여기다.

## `transaction_id` — 거래 업무키

- **송신 측 소유.** 원본 CSV에 없으므로 생성기·은행이 만든다.
- **재전송 시 같은 값이어야 한다.** 전송마다 새 값이면 §6의 중복·ID 충돌 흡수와 Q-1을
  검증할 수 없다.
- **관문은 해석하지 않는다.** 형식을 규정하지 않고 문자열로 그대로 전달한다.

> 목업 생성기 주의: `transaction_id`는 원본 행 번호 기반이라 결정적이지만, **내용은 그렇지
> 않다.** 생성기가 `timestamp`를 재생 시각축으로 덮어쓰므로 `--epoch`를 고정하지 않으면 같은
> 거래가 실행마다 다른 내용으로 온다. 나중에 `payload_hash`를 붙이면 그 상태의 재실행은
> "동일내용 중복"이 아니라 **전건 `ID_CONFLICT`**가 된다. 내용 재현이 필요하면 `--epoch`를 고정한다.

## 400 조건 — 이 넷만이다

1. JSON 파싱 실패
2. 11개 키 중 누락
3. 값이 `null`
4. 값이 빈 문자열 또는 공백만 있는 문자열

**그 밖에는 검증하지 않는다.** 금액 부호, 통화 코드, 타임스탬프 형식은 보지 않고 문자열 그대로
통과시킨다. `timestamp`를 `LocalDateTime`/`Instant`로 바인딩하면 안 된다 — 원본 형식
`2022/09/01 00:20`은 ISO-8601이 아니라서 바인딩하는 순간 정상 거래가 400이 된다.

§6은 형식 실패만 거절하고 **의미 이상(미지 통화·음수 금액)은 수용**하라고 한다. 모니터링
도메인에서는 이상한 거래일수록 버리면 안 되는 데이터다. 격리 플래그 저장은 워커·DB 소관이라
아직 없지만, 관문이 이 데이터를 버리지 않는 것은 지금 지켜야 한다.

빈 문자열과 `" "`를 400으로 두는 것은 경계 판단이다. 음수 금액은 조사할 정보를 담지만
(`-100`을 누군가 실제로 기록했다), 공백만 있는 값은 **값이 있는 척하는 부재**라 담지 않는다.
`from_account`가 비면 거래 업무키·계좌 등록부가 성립하지 않는다.

`HI-Small_Trans.csv` 5,078,345행 전체에 빈 문자열도 공백만 있는 값도 **0건**이다(실측).
그럼에도 거절하는 이유는 실제 은행 API가 들어올 때다 — 고정폭 레코드를 공백으로 패딩하는
추출물이나 트림 누락은 흔하고, 그때 수용하면 계좌 등록부에 이름이 `" "`인 노드가 격리 표시도
없이 쌓인다. 구현은 `@NotBlank`(`@NotEmpty` 아님)를 쓴다.

# 큐 페이로드 계약 (관문 → 수집 워커)

§8 언어 경계 계약이다. **한쪽 언어에서만 바꾸지 않는다.**

```json
{
  "ingest_id": "624cb754-ef55-4c92-8403-db50562a0d8e",
  "payload_hash": null,
  "received_at": "2026-08-12T08:08:43.665Z",
  "transaction": { "transaction_id": "...", "timestamp": "...", "...": "11개 키" }
}
```

**해시 입력 범위는 `transaction` 객체다.** 봉투 필드는 해시에 넣지 않는다. `ingest_id`는 전송
시도마다 달라지므로, 해시에 섞이면 "동일내용 중복"이 영원히 성립하지 않고 모든 재전송이
`ID_CONFLICT`가 된다. 중첩 구조를 택한 이유가 이 사고의 봉쇄다.

**`received_at`은 ISO-8601 UTC, 밀리초 3자리 고정.** `Instant.toString()`은 소수부 자릿수가
값에 따라 달라지고 밀리초가 0이면 소수부를 아예 생략하므로 쓰지 않는다. 3자리를 항상 출력하는
명시적 포매터를 쓴다. 자릿수가 흔들리면 Python 워커의 파싱이 간헐 실패한다.

거래 자체의 `timestamp`는 은행이 보낸 원문 형식 그대로 둔다. `received_at`과 형식이 다르며
그게 의도다.

**`payload_hash`는 키가 존재하고 값이 `null`이다.** `""`이 아니다 — `null`은 "미계산"이고
`""`은 "빈 문자열의 해시"로 읽힐 수 있어 워커가 구분할 수 없다. 표준화 규칙은 DB 멱등 설계와
함께 정한다.

## 어댑터 경계

관문(Java) 어댑터는 **`publish` 하나만** 정의한다. `consume`/`ack`/`fail`은 Python 수집 워커
어댑터 소유다. publish 실패는 5xx로 나간다 — 400도 202도 아니다. 현 생성기가 4xx는 재시도하지
않고 5xx·연결 오류만 재시도하므로 이 계약이 송신 측 동작과 맞는다.

# 알려진 한계

**`payload_hash` 키는 Jackson 설정 하나로 사라질 수 있다.** `spring.jackson.default-property-inclusion=non_null`을
넣으면 실제 큐 메시지에서 키가 통째로 빠진다(실험으로 확인). 어댑터가 JSON을 로깅하므로 운영
로그에서는 눈에 띄지만, **테스트는 자체 매퍼를 쓰기 때문에 전부 통과한다.** SQS를 붙일 때 이
자리를 반드시 다시 봐야 한다.

**400 사유 문구는 JVM 로케일을 탄다.** 한국어 환경에서는 `"from_bank: 공백일 수 없습니다"`,
영어 환경에서는 `"must not be blank"`가 된다. 필드 이름은 와이어 키로 고정돼 있지만 메시지
텍스트는 배포 환경에 따라 다르다. 에러 응답 규격을 정할 때 함께 다룬다.
