# 단일 초기 스키마 전환

대상은 검증된 dev 업무 DB 하나다. 현재 설정의 `aml_dev_v3`라는 이름은 그대로 재사용하며 새 버전 DB를 만들지 않는다. `aml_dev` 등 다른 DB·볼륨·역할은 건드리지 않는다. prod는 별도 대상 확인과 전환 절차가 필요하다.

구 V1~V17 이력에 새 V1을 덮어 적용하지 않는다. `baseline-on-migrate`나 검증 해제로 우회하지 않는다. 기존 업무 데이터는 테스트 데이터로 초기화하지만 직원 계정·비밀번호 해시·은행·보고 기간·환율과 외부 암호키를 보존한다. 시연 업무 시각은 초기값으로 돌아가므로 top10 재전송 전에 조작패널에서 기준 시각을 다시 설정한다.

## 순서

### 흐름 기반 Alert 생애주기 전환

현재 전환에는 공개 버전 포인터·Alert 계획·병합/후속 계보·직원 변경 제안·알림 수신자·현재 범위 요약이 단일 V1에 포함된다. **이전 V1이 적용된 dev에는 업무 DB 재초기화가 필요하다.** 과거 seed_risk 조회 SQL만 수정했을 때의 ‘코드만 배포’ 절차를 이번 전환에 적용하지 않는다. 목록은 저장된 현재 요약을 조회하며 상세 JSON 전체를 목록마다 재계산하지 않는다. 수동 ANALYZE나 응답 캐시를 필수 실행 단계로 추가하지 않는다.

사용자는 단일 V1 유지와 테스트 업무 데이터 재초기화를 선택했다. 구 패널에서 업무 데이터·파일 정리를 완료하고 아래 DB 전용 백업·재생성 절차를 수행한 뒤 배포한다. 계정·은행·보고 기간·환율을 복원하고 기존 분석 계정에 새 테이블 권한을 다시 부여한 후 top10을 첫날부터 재처리한다. 기존 SSM 암호키와 분석 비밀번호는 유지한다. worker의 review 쓰기 권한은 제거하고 읽기만 허용한다. 새 생애주기 API는 백엔드 검증 범위이며 프런트엔드 변경은 이번 전환 범위에 포함하지 않는다.

### 조작패널에서 파일 초기화를 이미 완료한 경우

최신 `reset-dev.py`를 EC2에 복사하고 `python3 reset-dev.py --db-only`로 대상을 확인한다. 이 모드는 S3 API를 호출하지 않으며 기존 암호키를 생성하거나 변경하지 않는다. 기존 Docker·DB·SSM 대상 설정 확인은 유지한다.

확인 후 `python3 reset-dev.py --db-only --apply --backup-file <프로젝트 밖의 새 보호 파일 경로>`로 API 정지 → 설정 백업·읽기 검증 → 현재 DB 재생성을 수행한다. 백업 실패 시 DB를 삭제하지 않는다. S3 과거 버전 정리는 이 전환의 필수 조건이 아니다. 이후 아래 5~7단계로 스키마 생성·설정 복원·분석 권한 설정을 수행한다. 새 배포 스크립트가 요구하는 분석 계정 SSM 값은 배포 전에 준비해야 하며 실제 DB 권한은 새 스키마 생성 후 설정한다.

### S3 과거 버전까지 함께 정리하는 경우

1. 코드 테스트와 이미지 빌드를 완료하고 배포·업로드·분석 요청을 중지한다. 현재 dev top10은 전환 전 응답시간 비교 기준으로 기록한다.
2. 기존 EC2에서 `reset-dev.py`를 인수 없이 실행하여 컨테이너·SSM·DB·S3 범위가 일치하는지 읽기 전용으로 확인한다.
3. 명시적으로 초기화를 실행할 때만 `--apply --backup-file <프로젝트 밖의 새 보호 파일 경로>`를 사용한다. API를 중지하고 설정 4개 테이블을 같은 스냅샷으로 백업한다. 파일은 배타적으로 만들고 소유자 전용 권한으로 저장한 뒤 다시 읽어 검증한다. 기존 백업을 덮어쓰지 않는다. 백업 실패 시 S3·DB를 삭제하지 않는다.
4. 스크립트는 지정 S3 접두사의 객체 버전 삭제를 확인한 후 현재 업무 DB 하나만 같은 이름으로 재생성한다. API는 정지 상태로 남는다. 백업 파일에는 비밀번호 해시가 있으므로 출력·채팅·저장소에 넣지 않는다.
5. 새 애플리케이션으로 Flyway 초기 스키마를 생성한다. 업로드와 분석은 아직 재개하지 않는다. `reset-dev.py --restore-config <백업 파일>`로 설정을 단일 트랜잭션에서 복원한다. 원래 ID·비밀번호 해시·환율을 복원하고 identity 시퀀스도 맞춘다. 업무 데이터가 있거나 FK가 충돌하면 복원을 거절한다. 백업은 복원 확인 후 운영자가 보관 정책에 따라 정리한다.
6. 환경별 분석 DB 로그인과 SSM `analysis-db/username`, `analysis-db/password`를 준비한다. 새 API 이미지의 `/app/worker/configure_analysis_db.py`에 관리자 PG 환경변수와 분석 계정 환경변수를 주입하여 실행한다. 명령 인수에 비밀번호를 넣지 않는다. [워커 배포 문서](../backend/api-server/worker/README.md)의 권한 경계를 따른다.
7. API·추론 서비스 상태, 기존 계정 로그인, 은행 보고 기간, 원문 키 버전, 분석 역할의 private/evaluation 접근 거부를 확인한다. top10을 날짜순으로 전송·분석한 후 거래·소유주·Alert 건수와 응답시간을 비교한다. Episode는 합성 조사 시나리오로 연결·해체·종결을 확인한다.

이 절차는 업무 데이터의 무손실 마이그레이션이 아니다. 초기화 이후 옛 이미지로 되돌려서는 새 스키마를 사용할 수 없다. 초기화 전 코드 검증을 마치고, 문제가 생기면 업로드·분석을 중지한 채 새 구조의 결함을 수정한다. S3 삭제나 DB 재생성이 실패하면 API를 자동 재시작하지 않는다.

`reset-dev.py` 테스트는 외부 서비스를 호출하지 않는 범위·실패 순서 검증이고, Python PostgreSQL 테스트는 설정 복원 SQL과 제한 역할을 실제 PostgreSQL17에서 검증한다. 실제 EC2·SSM·S3 전환은 별도 실행 결과로 확인한다.
