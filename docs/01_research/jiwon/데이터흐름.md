# 데이터 흐름 — 거래 · 판정 · 알림 · 사건

작성일: 2026-08-17 · GNN 기반 AML 모니터링 프로젝트

## 1. 전체 흐름

```
① 거래 수신        → 거래 (상태: 판정 대기)
② 모델 추론        → 판정 결과 = 거래별 위험점수 + 정상/이상 라벨
③ 알림 생성(집계)  → "이상" 거래들을 주체·시간창·연결성 기준으로 묶음 → 알림
④ 알림 큐          → L1 검토 → 오탐 종결 or 분석팀 이관
⑤ 사건             → 이관 시 생성(또는 기존 사건에 연결) → L2 조사 → 종결
```

| 단계 | 산출물 | 처리 주체 |
|---|---|---|
| ② 거래 → 판정 | 거래 1건당 점수·라벨 (score / prediction) | **모델** (유일하게 학습된 부분) |
| ③ 판정 → 알림 | 이상 거래 묶음 + 관련 계좌 집합 + 근거 거래 목록 | **결정론 로직** (θ, W, 연결 요소, 병합 규칙) |
| ⑤ 알림 → 사건 | 알림 묶음 + 조사 기록 | **사람** (MVP 기준. 자동 상관은 후순위) |

- 모델 출력(판정)은 알림이 아니다. 이상 판정 거래 수 ≠ 알림 수 — 이상 거래 16건이 알림 1건이 될 수 있다(FAN-OUT 하나).
- 사람이 개입하는 것은 ④부터.

## 2. 판정 → 알림: 결정론 집계 로직

기준 3개: **임계값(θ) → 연결성 → 시간창(W)**

```
1. 플래그:  점수 ≥ θ 인 거래만 추림
2. 묶음:    시간창 W 안의 플래그 거래끼리 계좌를 공유하면 같은 묶음
            (= 플래그 거래들의 연결 요소 1개 = 알림 1건)
3. 속성:    관련 계좌 집합(알림-계좌 N:M) + 대표 계좌(표시용 라벨, 최다 관여 기준)
4. 병합:    기존 열린 알림과 근거 거래·계좌 집합이 겹치면 신규 생성 대신 병합
```

알림의 정체성은 **근거 거래 집합(서브그래프)**이다. "주체 계좌"는 필수 필드가 아니라 표시용 파생값이다:

- FAN-OUT/FAN-IN은 허브가 명확해 대표 계좌가 자연스럽지만, CYCLE(A→B→C→A)은 계좌들이 대등하고 BIPARTITE/SCATTER-GATHER는 그룹 구조라 단일 주체 지정이 임의적이다.
- 주체가 하던 역할은 분해해서 처리한다: 큐 표시 라벨 → 대표 계좌 또는 "계좌 N개" 요약(표시용이라 임의여도 무해), 병합 키 → 집합 겹침(주체 동일성보다 정확), 계좌별 이력 조회 → 알림-계좌 N:M 관계(의심계좌 집계 뷰도 이것으로 해결).

### 예시 (θ=0.8, W=48h)

```
tx101  A→B  0.93  플래그 ┐
tx102  A→C  0.88  플래그 ├ A를 공유 → 묶음 ①  → AL-101 (계좌 {A,B,C,D}, 대표 A, 근거 3건, 점수 0.93)
tx103  A→D  0.91  플래그 ┘
tx104  E→F  0.85  플래그    독립          → AL-102 (계좌 {E,F}, 대표 E, 근거 1건, 점수 0.85)
tx105  B→G  0.42  탈락
```

### 의사코드

```python
flagged = [tx for tx in preds if tx.score >= θ]
groups  = connected_components(flagged, key=계좌공유, window=W)
for g in groups:
    alert = find_open_alert(overlap=g.txs_or_accounts) or new_alert()
    alert.accounts = alert.accounts | g.accounts        # N:M
    alert.label    = max(alert.accounts, key=관여건수)  # 표시용 대표
    alert.add_evidence(g)
    alert.score    = max(tx.score for tx in alert.evidence)
```

### 묶음 기준을 연결 요소로 하는 이유

| 기준 | 방식 | 결과 |
|---|---|---|
| A. 계좌×시간창 | 플래그 거래를 계좌별로 모음 | 다계좌 패턴(CYCLE, SCATTER-GATHER)이 계좌 수만큼 조각남 |
| B. 연결 요소 (채택) | 계좌 공유로 이어지는 덩어리 전체 | 다계좌 패턴이 한 알림으로 온전히 묶임 |

- B는 Patterns.txt의 "세탁 시도(attempt)" 단위와 대응 → 묶음 품질을 정답과 비교 평가 가능 (알림 1개 ↔ attempt 1개 일치율).
- 다홉 패턴이 알림 하나로 나와야 그래프 화면의 서브그래프 하이라이트가 성립.

### 캘리브레이션 대상 파라미터

- **θ** (플래그 임계값): 알림 예산(일일 처리 가능 건수)에 맞춤
- **W** (시간창): {24h, 48h, 7일} 중 attempt 일치율 최대인 값
- **병합 정책**: 기존 열린 알림과의 집합 겹침 판정 방식 (거래 겹침만 볼지, 계좌 겹침까지 볼지)

## 3. 룰엔진 파이프라인과의 비교

룰엔진은 ②와 ③이 한 단계로 합쳐져 있다. 입력(거래 행)은 동일하고, **묶기와 판정의 순서**가 다르다.

```
룰:   묶기 → 판정   (계좌×시간창으로 집계부터 하고, 집계값에 임계값 적용)
GNN:  판정 → 묶기   (거래별로 점수부터 매기고, 점수 넘은 것들을 집계)
```

룰의 "묶기"는 룰 정의 안에 내장돼 있다 — 룰 실행이 곧 집계 쿼리:

```sql
-- "분할거래" 룰의 실체
SELECT 계좌, COUNT(*), SUM(금액)
FROM 거래
WHERE 금액 BETWEEN 0.9*T AND T
  AND 시각 > now() - 7일
GROUP BY 계좌            -- 이 GROUP BY가 곧 "묶기"
HAVING COUNT(*) >= 3     -- 이 HAVING이 곧 "판정"
```

| | GNN 파이프라인 | 룰 파이프라인 |
|---|---|---|
| ② 판정 단위 | 거래 1건 | 주체×시간창 (처음부터 집계) |
| ② 출력 | 거래별 점수 | 시나리오 히트 (= 알림 후보) |
| ③ 할 일 | 묶음 + 계좌 집합·대표 라벨 + 중복제거 | 중복제거만 |

두 파이프라인은 ③ 이후 같은 알림 테이블로 합류한다. 알림의 출처 필드(시나리오 ID / 모델)만 다르다.

### "집계도 임계값 로직이면 룰엔진과 뭐가 다른가"

임계값이 **무엇에 걸리느냐**가 다르다.

- 룰엔진: 임계값이 원시 통계량(금액, 건수, 차수 — 사람이 정의한 피처)에 걸림. **탐지 지식이 룰 자체에 있음.** 임계값 = 탐지 기준.
- GNN 집계: 임계값이 모델이 학습한 위험점수에 걸림. 탐지 지식은 모델 가중치에 있고, 집계는 판정을 업무 객체로 포장만 함. θ = 운영 컷오프(알림량 조절 밸브).

비유: 모델 = 채점, 집계 = 합격선 긋기. 합격선 긋기가 결정론이라고 채점까지 룰인 것은 아니다. 실질 차이는 판별력 — 룰은 사람이 만든 피처로 표현 안 되는 패턴(CYCLE 등)을 원리적으로 못 잡고, GNN 점수에는 다홉 구조가 반영된다.

## 4. 알림 생성까지 학습시키지 않는 이유

1. **라벨이 없고 문제가 어려워짐** — 라벨은 거래 단위. 묶음을 학습하려면 서브그래프 단위 예측이 필요한데 후보 생성부터 조합 폭발하는 별개 태스크.
2. **얻을 게 없음** — 판별력은 전부 점수에서 나옴. 묶기는 확정된 판정의 포장이라 새 정보를 만들지 않음.
3. **운영 레버 상실** — θ가 설정값이어야 관리자가 재학습 없이 알림량을 조절함 (유즈케이스 '탐지 임계값 변경').
4. **설명·재현 불가** — "왜 이 16건이 알림 하나인가"에 "48h 창에서 A를 공유하고 점수 θ 이상"이라고 결정적으로 답해야 함(감사 요건).
5. **디버깅 분리** — 점수 이상 = 모델 문제, 묶음 이상 = θ/W/병합 규칙 문제로 나눠 수정.

요약: **학습이 이득을 주는 곳(판별)에만 학습을 쓰고, 규칙이면 충분한 곳(포장)은 규칙으로 남긴다.**

## 5. 알림 → 사건

- 사건 = 조사의 단위. "같은 실체에 대한 하나의 의혹"을 구성하는 알림들의 묶음. 조사·처분·(향후 STR 보고)는 사건 단위.
- **MVP: 수동 묶기만** — 모니터링 직원이 이관하면서 "신규 사건 생성 or 기존 사건 연결" 선택, 분석 직원이 조사 중 연결·병합 (유즈케이스 그대로).
- 자동 상관(correlation)을 넣는다면 결정론 규칙으로: "관련 계좌가 겹치는 열린 사건이 있으면 새 알림을 자동 연결" 한 줄부터. 실제 제품(Oracle ECM correlation)은 엔터티 공유 + 시간 근접성 + 유형 호환 + 열린 상태 조건으로 상관 점수를 계산해 자동 편입/승격한다. 우리는 후순위.
