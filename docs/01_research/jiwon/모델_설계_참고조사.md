# AML 거래모니터링(TMS) 구조 — 룰 엔진과 Alert 큐, 그리고 ML 모델의 자리

실무 AML 시스템
"(1) 룰 엔진, (2) alert 큐, (3) 케이스 조사 도구, (4) STR/SAR 보고"

---

## 1. 핵심 요약

| 질문 | 답 |
|---|---|
| **룰 엔진**이 하는 일 | **탐지** — "무엇을 잡을지" 판정하고 **alert을 만들어낸다** |
| **Alert 큐**가 하는 일 | **작업 관리** — 만들어진 alert이 쌓이는 대기열, "무엇을 먼저 볼지" |
| AI 이진분류 모델은 어디? | **탐지 계층.** 룰 엔진 "안에" 들어가는 게 아니라, 룰 엔진과 **같은 자리**에 서거나 그 **뒤에서 큐를 재정렬**한다 |

거래별 세탁 여부를 예측하는 모델은 **alert을 만드는 쪽(탐지)**이지 큐 자체가 아니다.

그런데 실무에서 ML이 가장 많이 배치되는 자리는 **큐 쪽**이다. 이 어긋남이 혼동의 원인

---

## 2. 실제 TMS 파이프라인 (+ 전후처리)

```
[1] 거래 유입 · 데이터 정비
     원장 거래 + KYC/CDD + 고객위험등급 + 국가위험 + 엔티티 해석
              │
              ▼
[2] 탐지 계층                         ◄── "룰 엔진"의 자리
     시나리오를 돌려 "이건 의심스럽다"를 판정
     ★ AI 이진분류 모델이 들어간다면 여기
              │
              ▼
[3] Alert 생성
     탐지 히트 → alert 레코드로 변환
     (집계 · 중복제거 · 주체 확정 · 근거 거래 첨부)
              │
              ▼
[4] Alert 큐                          ◄── "무엇을 먼저 볼지"
     우선순위 부여 · 배정 · SLA · aging
     ★ ML이 실무에서 가장 많이 들어가는 자리 (재점수화)
              │
              ▼
[5] 1차 검토 (L1 트리아지)
     대부분 여기서 "정상"으로 종결
              │
              ▼
[6] 케이스 조사 (L2)
     link analysis · 거래이력 · KYC 재확인 · adverse media
              │
              ▼
[7] 처분 결정
     종결(오탐) / 상신
              │
              ▼
[8] STR 보고 → 금융정보분석원(KoFIU)
     보고서 서술문 작성
              │
              ▼
[9] 피드백 루프
     처분 결과가 다음 모델의 라벨이 된다
```

**[2]는 "판정 로직", [4]는 "작업 대기열"이다. 층위가 다르다.**

기존 지형도 문서의 4단 목록은 **[3] alert 생성 단계를 빠뜨렸고**, [2]와 [4]를 대등하게 나열했다.
정확한 구성은 **탐지 → alert 생성 → alert 큐 → 케이스 조사 → STR 보고** 5단이다.

---

## 3. 룰 엔진이 정확히 무엇인가

**결정론적 시나리오의 집합.** 각 시나리오는 조건 + 임계값으로 이뤄진다.

### 전형적인 시나리오

| 시나리오 | 조건 예시 |
|---|---|
| 구조화(structuring) | 5일 내 보고 기준액 직하 현금입금 3건 이상 |
| 급속 자금이동 | 입금 후 N시간 내 90% 이상 출금 |
| 고위험 국가 송금 | FATF 고위험국 대상 + 금액 임계 초과 |
| 프로파일 이탈 | 최근 3개월 평균 거래액 대비 K배 초과 |
| 휴면 후 급증 | 6개월 무거래 후 대량 거래 |
| 다수 계좌 집중 | 무관해 보이는 다수 계좌 → 단일 계좌 자금 집중 |

### 룰 엔진의 성질

- **설명이 자동으로 나온다.** "5일간 990만원 입금 3건" — 그대로 STR 서술문에 들어간다
- **감독당국 승인이 이미 되어 있다.** 검증받은 자산이라 걷어내기 어렵다
- **임계값 튜닝(threshold tuning)이 별도의 큰 업무.** 정기 조정 + 근거 문서화
- **오탐이 압도적.** 업계 통상 95~98%가 오탐
- **판정 단위가 대개 "고객 × 기간"** — §7에서 중요해진다

---

## 4. Alert 큐가 정확히 무엇인가

**탐지 결과가 사람 앞에 놓이는 작업 대기열.** 탐지가 아니라 **운영** 영역이다.

### 왜 별도 단계인가

**(1) 처리 용량이 유한하다.**
조사관 20명이 하루 500건을 본다면, 시스템이 alert을 5,000건 뽑아도 4,500건은 안 본다.
이것이 AML 시스템의 실질적 병목이다.

**(2) alert은 거래와 1:1이 아니다.** ← 특히 중요

```
룰 엔진이 한 고객의 한 달치 거래에서 시나리오 3개에 걸림
    → alert 3건이 아니라, 보통 alert 1건으로 묶임
    → 주체(subject) = 고객 또는 계좌
    → 기간 = 해당 월
    → 근거 거래 = 트리거된 거래 목록
```

**alert의 단위는 대개 "고객 × 기간"이지 "거래 1건"이 아니다.**

**(3) 큐 자체에 상태 관리가 붙는다.**
배정, 재배정, 보류, 에스컬레이션, SLA 경과일, aging.

### 큐에서 하는 일

- **우선순위 부여(triage / scoring)** ← ML이 들어가는 자리
- **자동 종결(auto-closure / alert hibernation)** — 명백히 무해한 alert을 사람 없이 닫는 것.
  규제상 매우 민감해 별도 검증이 필요하다
- 중복 병합, 관련 alert 묶기

## 5. 이진분류 모델이 들어갈 수 있는 세 자리

| | 위치 | 하는 일 | 규제 난이도 | 실무 빈도 |
|---|---|---|---|---|
| **A** | [2] 탐지 계층 | 모델이 **직접 alert을 생성** | **매우 높음** | 드묾 |
| **B** | [4] alert 큐 | 룰이 만든 alert을 **재점수화·정렬** | 낮음 | **가장 흔함** |
| **C** | [6] 케이스 조사 | 네트워크 시각화, 관련 계좌 추천, 서술문 초안 | 낮음 | 흔함 |

### A — 탐지 계층 (룰 엔진의 자리)

거래별 `Is Laundering` 예측은 **alert 트리거 그 자체**다.

- 룰 엔진을 **대체**하거나 **병행**한다. "룰 엔진 안에 들어간다"가 아니다
- Google Cloud AML AI가 이 방식이고, HSBC가 실제로 룰 기반을 대체했다
  (단 공개 성과 수치는 벤더/고객 공동 발표로 독립 검증되지 않았다)
- 규제 부담이 가장 크다 — alert의 근거를 설명해야 하고 모델 리스크 관리 대상이 된다
- **"룰이 놓치던 것을 새로 잡는다"는 증명이 필요하다.** 룰과 같은 것만 잡으면 도입 명분이 없다

### B — Alert 큐 재점수화 (실무 주류)

```
룰 엔진 → alert 5,000건/일 → ML 재점수화 → 상위 500건만 조사관에게
```

**규제상 훨씬 쉽다.** 룰 엔진이 그대로 남아 있어 "탐지 범위는 줄지 않았다"고 말할 수 있고,
모델은 순서만 바꾼다. 실패해도 룰이 뒤를 받친다.

> 평가지표 `budget_recall`(상위 0.1/0.5/1% alert 구간의 recall)이 **정확히 이 관점의 지표**다.
> 이미 큐 제약을 모델링하고 있는 셈이다.

### C — 조사 보조

Quantexa, Feedzai Genome이 강한 영역. 탐지 성능과 무관하게 조사 효율을 올린다.

## 6. 지형도 문서 서술이 헷갈렸던 이유

원문:

> "엣지(거래) 분류는 ... '이 거래가 Is Laundering=1인가?'를 직접 예측하며
> **실무의 거래 모니터링(TMS) alert 생성**과 가장 밀접하다."

**이 문장 자체는 맞다.** "alert 생성"이라고 했지 "alert 큐"라고 하지 않았다. [3] 단계를 가리킨다.

혼동은 그 위의 4단 목록에서 왔다. 그 목록이 [3]을 빠뜨리고 [2]와 [4]를 대등하게 놓았기 때문에,
"모델이 alert 생성에 밀접하다"가 "큐에 들어간다"로 읽힐 여지가 생겼다.

## 7. 프로젝트에 주는 함의

### 7.1 ⚠ 집계 계층이 빠져 있다

현재 모델의 출력:

```
거래 1건 → 확률 1개
```

실제 alert 큐가 요구하는 것:

```
고객(또는 계좌) × 기간 → alert 1건 + 근거 거래 목록 + 위험점수
```

**둘 사이에 집계 계층이 필요하다.** 현재 파이프라인에는 없다.

집계 방식은 설계 결정이다:

| 방식 | 설명 | 특징 |
|---|---|---|
| 최대값 | 계좌의 거래 중 최고 점수 | 단순. 단발 고위험 거래에 민감 |
| 상위 k 합 | 상위 k건 점수 합 | 반복 패턴을 반영 |
| 임계 초과 건수 | 점수 > t 인 거래 수 | 룰 엔진과 형태가 비슷해 설명이 쉽다 |
| 별도 노드 모델 | 계좌 단위로 다시 학습 | 정확하지만 태스크가 하나 늘어난다 |

### 7.2 지표에도 영향을 준다

현재 `budget_recall`은 **거래 단위 상위 k%**를 본다.
실제 운영은 **고객 단위 상위 k건**이다.

거래 500건이 고객 50명에 몰려 있으면 조사 부담은 50건이지 500건이 아니다.
집계 계층을 정한 뒤에는 지표도 그 단위로 다시 정의해야 한다.

### 7.3 A 경로와 B 경로 중 목표를 정해야 한다

| | A: 탐지 대체 | B: 큐 재점수화 |
|---|---|---|
| 필요한 것 | 룰이 못 잡는 것을 잡는다는 증명 | 룰 alert에 대한 **처분 라벨** |
| 데이터 | 지금 AMLworld로 가능 | **룰 alert + 조사관 처분 이력 필요** |
| 규제 | 무겁다 | 가볍다 |
| 현재 개발 방향 | 여기에 맞춰져 있음 | 데이터가 없음 |

**AMLworld에는 "룰 alert"이라는 개념이 없다.** 세탁 여부 정답만 있다.
따라서 현재 데이터로는 **A 경로만 훈련 가능**하다.

실서비스가 B를 원한다면(대부분 그렇다), 실제 룰 alert과 처분 이력이 확보된 뒤
태스크를 다시 정의해야 한다.

**확인할 것**: 현업조사 결과에서 (a) 룰 엔진이 이미 존재하는지,
(b) alert이 어떤 단위(거래/계좌/고객 × 기간)로 생성되는지,
(c) 처분 이력이 데이터로 남는지. 이 셋이 A/B 결정을 좌우한다.

## 부록: 용어

| 용어 | 뜻 |
|---|---|
| **TMS** | Transaction Monitoring System, 거래모니터링시스템 |
| **시나리오(scenario)** | 룰 엔진의 개별 탐지 규칙. 조건 + 임계값 |
| **임계값 튜닝** | 시나리오 임계값을 조정하고 근거를 문서화하는 정기 업무 |
| **Alert** | 탐지 히트가 사람이 검토할 단위로 변환된 레코드. 주체 + 기간 + 근거 거래 |
| **트리아지(triage)** | 큐에 쌓인 alert의 우선순위를 정하고 1차 선별하는 과정 |
| **Auto-closure / Hibernation** | 저위험 alert을 사람 검토 없이 종결하는 것. 규제상 민감 |
| **케이스(case)** | L1을 통과해 본격 조사 대상이 된 단위. 여러 alert이 묶이기도 한다 |
| **처분(disposition)** | 조사 결과 결정. 종결(오탐) 또는 상신 |
| **STR** | 의심거래보고. 한국은 금융정보분석원(KoFIU)에 보고 |
| **CTR** | 고액현금거래보고. 임계액 이상 현금거래를 자동 보고 |
| **엔티티 해석(Entity Resolution)** | 여러 소스에 흩어진 중복·불완전 레코드를 하나의 실체로 통합 |
| **Link analysis** | 조사관이 계좌·인물 간 관계를 시각적으로 탐색하는 도구 |
| **챔피언/챌린저** | 운영 모델과 후보 모델을 실데이터로 동시 검증해 교체를 결정하는 운영 전략 |# AML 거래모니터링(TMS) 구조 — 룰 엔진과 Alert 큐, 그리고 ML 모델의 자리

**작성 맥락**: 「GNN 기반 AML 모니터링 지형도」 문서가 실무 AML 시스템을
"(1) 룰 엔진, (2) alert 큐, (3) 케이스 조사 도구, (4) STR/SAR 보고" 4단으로 서술했는데,
이 목록이 **탐지 로직과 작업 대기열을 대등한 부품처럼 나열해** 혼동을 일으켰다.
둘은 대등한 부품이 아니라 **순차 단계**다. 이 문서가 그 구조를 정리한다.
