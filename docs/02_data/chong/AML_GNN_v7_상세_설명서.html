0. v7은 무엇이고 왜 만들었습니까

v7의 목표는 점수를 더 올리는 것이 아니라 "지금까지의 점수를 믿어도 되는가"를 보장하는 것입니다. v6까지의 성능(test PR-AUC 0.57대)은 좋아 보이지만, 코드에는 점수를 은근히 부풀릴 수 있는 관행 세 가지가 남아 있었습니다. v7은 이 셋을 제거하는 것에서 출발합니다.

v6까지 남아 있던 문제왜 문제인가v7의 해결
① 대상 거래가 자기 자신이 포함된 그래프 위에서 판정됨같은 윈도우 안의 대상 거래·미래 거래의 구조(차수, 병렬 엣지 등)가 메시지 전달에 섞입니다. 실전에서는 판정 시점에 존재하지 않는 정보입니다strict-causal window — 메시지 그래프에는 과거 컨텍스트만 (§3)
② 확률 보정·임계값 결정 전용 데이터가 없음검증셋 하나로 모델 선택과 임계값 튜닝을 겸하면, 임계값이 검증셋에 과적합됩니다train/val/calibration/test 4분할 (§1-3)
③ 경보 예산 임계값을 테스트 분위수로 계산테스트 분포를 미리 본 셈 — 미래 데이터의 통계를 운영 파라미터에 사용한 누수입니다모든 임계값·온도를 calibration에서만 결정하고 test에 고정 (§6-1)

노트북 서두에는 해석의 자세도 못박혀 있습니다 — "외부 세트 결과가 나오기 전에는 '일반화 성능 향상'을 확정하지 않습니다. IBM 데이터는 합성 데이터이므로 실데이터 이관 성능도 별도 검증 대상입니다." 연구 근거로는 IBM AML-Data, MEGA-GNN(병렬 엣지 2단계 집계), GroupDRO(최악 환경 학습), temperature scaling(확률 보정), LineMVGNN(방향별 multi-view·거래 중심 readout)을 인용하되, "그대로 복제하지 않고 대규모 방향 멀티그래프에서 실행 가능한 strict-causal MEGA형 edge classifier로 조합했다"고 명시합니다.

1. 데이터 — 무엇을, 어디까지 포함시켰는가

1-1. 입력 소스와 탐색 순서

학습 세트는 Config.source_dataset = "HI-Small"이고, 로더(locate_dataset())의 우선순위는 다음과 같습니다: ① 전처리 노트북의 산출물 processed/transactions_clean.parquet이 있으면 그것을 사용(불필요한 파생 컬럼은 읽지 않도록 columns=REQUIRED로 9개 컬럼만 로드) → ② 없으면 IBM_AML_dataset/, _to_delete/, aml/data/, 현재 폴더에서 CSV/parquet 탐색 → ③ 그것도 없으면 zip 내부 멤버 탐색. 이렇게 만든 이유는 두 가지입니다: 전처리 파이프라인과의 연결 고리를 공식화하면서도, 어떤 실행 환경에서든(파일이 어디에 있든) 노트북이 자기완결적으로 돌게 하기 위함입니다.

_canonicalize()는 어떤 소스로 들어와도 동일한 표준 형태로 만듭니다 — 필수 9컬럼(timestamp, src, dst, amount_paid, amount_received, payment_currency, receiving_currency, payment_format, is_laundering)만 남기고, 계좌 키를 은행|계좌번호로 합성하고, 필수 9컬럼 기준 중복을 제거(keep first)하고, timestamp+원본 행번호로 안정 정렬한 뒤, 계좌 문자열을 정수 ID로 factorize하고, 첫 거래 기준 경과 분(minute) 컬럼을 만듭니다. 누락 컬럼이 있으면 즉시 ValueError를 던집니다 — 이후 세트 간(zero-shot) 평가에서 LI-Small 등 다른 세트도 같은 함수 하나로 표준화하기 위한 세트 독립 설계입니다.

1-2. 포함 범위: 꼬리 절단 없이 전 구간 사용

실행 기록 기준 적재 결과는 5,078,336건, 양성 5,177건(0.1019%)입니다. 원본 5,078,345건에서 중복 9건만 빠진 수치로, ②~⑥ 노트북들이 수행하던 꼬리 절단(2022-09-11 이후 라벨 급증 구간 제거)이 v7에는 없습니다. 코드 경로로 보면: 기록된 실행에서는 parquet이 없어 원본 CSV 폴백으로 들어왔고, _canonicalize()는 세트 독립 함수라 특정 세트의 수동 절단 규칙을 포함하지 않기 때문입니다(전처리 노트북의 parquet을 입력으로 쓰면 그쪽에서 절단된 데이터가 들어옵니다). 결과적으로 라벨이 급증하는 이상 구간이 테스트에 포함되어 테스트 양성률이 0.2048%로 올라간, 더 어렵고 보수적인 평가 조건이 됩니다 — 노트북이 "v6 수치와 직접 비교 금지"를 명시한 이유 중 하나입니다(§7).

1-3. 4분할: train / val / calibration / test

chronological_splits()가 시간순으로 55/15/15/15를 자릅니다. 이때 비율 지점을 그대로 자르지 않고 searchsorted(minute, ...)로 분(minute) 경계에 스냅합니다 — 같은 분에 속한 거래가 두 분할에 걸쳐 찢어지면 "동일 분 거래는 서로 못 본다"는 인과 규칙(§2-3)과 충돌하기 때문입니다. 분할 비율 합이 1이 아니거나 빈 분할이 생기면 예외를 던지는 방어 코드도 있습니다.

2. 전처리·피처 구조 — 42차원의 내역과 이유

v7 피처의 설계 목표는 "세트 독립 + 엄격 인과" 두 가지입니다. v6의 68차원에서 42차원으로 오히려 줄었는데, 줄인 것 자체가 설계입니다 — 학습 세트의 어휘(통화 이름 목록 등)에 묶인 피처를 없애야 다른 세트에 재학습 없이 이식(zero-shot)할 수 있기 때문입니다. 실행 출력: features=(5078336, 42), time=12, shortcut=25.

2-1. 기본 피처 6차원 — 로버스트 정규화

2-2. 카테고리 24차원 — 원-핫을 버리고 해시 인코딩

def _hash_matrix(values, namespace, buckets):
    ids = blake2b(f"{namespace}|{값}") % buckets   # 문자열 → 고정 8버킷 중 하나
    ...

payment_currency·receiving_currency·payment_format 3개 컬럼을 각각 blake2b 해시로 8버킷 원-핫(3×8=24차원)에 매핑합니다. 이유: v6까지의 원-핫은 "train에 등장한 카테고리 목록"에 차원이 묶여 있어, 통화 구성이 다른 세트에 모델을 그대로 가져가면 입력 차원부터 어긋납니다. 해시는 어떤 세트가 와도 차원이 고정이고 같은 문자열은 항상 같은 버킷에 떨어집니다(결정적). 대신 서로 다른 값이 같은 버킷에 충돌할 수 있다는 정보 손실을 감수합니다 — 일반화를 위해 표현력을 일부 내준 명시적 트레이드오프입니다.

중요한 부수 장치로, 이 해시 24차원 + currency_mismatch를 shortcut_idx(지름길 피처 목록, 총 25개)로 지정해 둡니다 — §4-3의 shortcut dropout이 학습 중 이 피처들을 통째로 지워 "결제수단 몇 번이면 세탁"식의 암기를 방해합니다.

2-3. 상대 시간 12차원 — "같은 분은 서로 못 본다"

v6의 시간 피처 16종을 12종으로 정리하고, 인과 규칙을 한 단계 조입니다. _prior_stats()는 (계좌 또는 계좌쌍, 분) 복합 키를 정렬해 두고 searchsorted(side="left")로 자기 자신뿐 아니라 같은 분(minute)의 모든 거래를 제외한 과거만 집계합니다. out(송금 계좌)·in(수취 계좌)·pair(계좌쌍) 3개 관점 × (직전 이벤트까지의 Δt, 첫 등장 여부, 최근 60분 건수, 최근 1,440분 건수) 4종 = 12차원입니다. Δt는 log1p 후 1주(7×24×60분) 상수로, 건수는 log1p 후 log(101)로 정규화합니다.

왜 "같은 분"까지 제외합니까 데이터의 시간 해상도가 분 단위라, 같은 분에 찍힌 거래들은 실제 선후 관계를 알 수 없습니다. v6는 정렬 순서상 앞에 있으면 "과거"로 취급했지만, 이는 우연한 정렬 순서에 기대는 것입니다. v7은 애매한 경우를 전부 "못 본 것"으로 처리하는 보수적 선택을 했고, 같은 이유로 분할 경계와 윈도우 경계도 분 단위로 스냅합니다(§1-3, §3-1). 정수 오버플로 가드(OverflowError)와 피처 행렬의 NaN/Inf 전수 검사(ValueError)도 이 단계에 들어 있습니다.

참고: v6에서 단변량 판별력이 가장 높던 pair_dt(ROC-AUC 0.8147) 계열이 유지되되, v7은 이 피처들이 합성 생성기 패턴에 과적합됐을 가능성을 검사하는 no_relative_time ablation(시간 12차원 전체를 0으로 마스킹)을 §6-5에 준비해 두었습니다.

3. 그래프 구성 — 누수 없는 causal window

3-1. 윈도우 나누기: make_ranges()

정렬된 거래를 대상 5만 건 단위로 자르되(target_edges=50_000), 각 윈도우 앞에 과거 10만 건을 컨텍스트로 붙입니다(context_edges=100_000). 윈도우 끝은 searchsorted로 분(minute) 경계에 스냅합니다 — 같은 분의 거래가 두 윈도우로 찢어지지 않게 하기 위함입니다(실제로 실행 출력의 첫 윈도우가 50,000이 아니라 54,740에서 잘린 것이 이 스냅의 흔적입니다). 각 윈도우에는 시간 환경 번호(env 0~3)도 부여됩니다 — train 구간을 시간순 4등분한 것으로, §5-3의 GroupDRO가 사용합니다.

3-2. 핵심: 대상 거래를 메시지 그래프에서 뺀다

v7 그래프 구성의 본질은 build_causal_window(ctx_lo, lo, hi) 한 함수에 있습니다. 메시지 전달 그래프에 들어가는 엣지는 과거 컨텍스트 [ctx_lo, lo) 뿐이고, 판정 대상 [lo, hi)의 거래들은 그래프에 넣지 않습니다. 대상 거래는 ① 자기 자신의 피처 벡터(target_edge_x)와 ② 양끝 계좌의 노드 인덱스만 readout 단계로 전달됩니다. 노드 피처 9종(출/입 차수, 평균 송·수금액, 고유 상대방 수, 팬아웃-팬인 비대칭, 상대방당 거래수)도 전부 과거 컨텍스트에서만 계산합니다.

# 메시지 엣지 = 컨텍스트 구간만 (정방향 + 역방향)
ei = np.concatenate([np.stack([sl, dl]), np.stack([dl, sl])], axis=1)
...
# 누수 단위 테스트 — 대상 엣지가 그래프에 섞이면 즉시 사망
assert ei.shape[1] == 2 * (lo - ctx_lo), "target edge가 message graph에 섞였습니다"

§2 셀. "규칙을 지켰는지"를 주석이 아니라 assert로 검증합니다. 실행 출력의 probe: bounds (0, 54740, 100000) / message_edges 109480 / targets 45260 — 메시지 엣지 수가 정확히 컨텍스트 54,740건 × 2(역방향 포함)임을 확인할 수 있습니다.

왜 이렇게까지 합니까 v6까지는 대상 거래도 그래프 안에 있었습니다. 그러면 모델이 "이 거래가 존재함으로써 생기는 구조"(예: 이 거래 때문에 늘어난 병렬 엣지 수, 같은 윈도우 안 미래 거래들의 차수)를 보고 판정할 수 있습니다. 실전 운영에서 거래를 판정하는 순간에는 그 거래가 만들 미래 구조를 알 수 없으므로, 이는 평가 점수만 올려주고 실전에서는 재현되지 않는 정보입니다. v7은 "판정 시점에 실제로 알 수 있는 것"만 입력이 되도록 그래프 구성 단계에서 원천 차단했습니다.

이 밖에 병렬 엣지 그룹 정보(pair_inv, pair_dst, pair_count — §4의 2단계 집계용)와 계좌 보조 라벨(node_y = 대상 구간에서 양성 거래에 연루된 계좌, node_mask = 대상 구간에 등장한 계좌)도 이 함수에서 함께 만들어집니다.

4. 모델 — CausalMegaGNN의 구조와 이유

4-1. 전체 구조

구성 요소내용이유
입력 인코더 3개node_in(9→128), context_edge_in(42+방향2 → 128), target_edge_in(42→128) — 각각 Linear+LayerNorm+SiLU컨텍스트 엣지(방향 플래그 포함)와 대상 엣지(그래프 밖)는 역할이 달라 인코더를 분리
CausalMegaLayer × 3병렬 엣지 2단계 평균 집계 + 노드/엣지 갱신 + 잔차 + LayerNorm (아래 4-2)MEGA-GNN 계열, degree shortcut 억제형으로 변형
JK readout입력층 포함 4개 층의 노드 표현을 연결(concat) 후 압축얕은 층(국소 패턴)과 깊은 층(광역 패턴) 정보를 모두 보존 (Jumping Knowledge)
거래 head[h_src ‖ h_dst ‖ h_src·h_dst ‖ |h_src−h_dst| ‖ 대상엣지표현] 5×128 → 2-hidden MLP → 위험도 로짓곱(상호작용)·절대차(대칭 비교) 항을 명시적으로 제공 — 송금·수취 계좌의 "관계"를 읽기 쉽게. LineMVGNN의 거래 중심 readout 참고
계좌 보조 head노드 표현 → 128→64→1, 보조 손실 가중 0.2화두 1의 근본 위험("개별 거래 라벨은 노이즈가 크다") 대응 — 계좌 수준 신호로 표현 학습을 보강 (아래 4-4)

4-2. CausalMegaLayer: 합이 아니라 평균으로 집계하는 이유

def forward(self, h, ei, e, pair_inv, pair_dst, pair_count):
    msg  = self.msg(torch.cat([h[ei[0]], e], dim=1))
    pair = index_mean(msg, pair_inv, len(pair_dst))          # ① 같은 계좌쌍의 병렬 엣지끼리 "평균"
    pair = pair * (1.0 + torch.log1p(pair_count) / 5.0)      # 거래량은 명시적 항으로 따로
    agg  = index_mean(pair, pair_dst, h.size(0))             # ② 이웃(계좌쌍) 단위 "평균"
    h2 = self.node_norm(h + self.node(torch.cat([h, agg], 1)))   # 잔차 연결
    e2 = self.edge_norm(e + self.edge(torch.cat([h2[ei[0]], h2[ei[1]], e], 1)))
    return h2, e2

v6의 MegaConv는 두 단계 모두 합(sum) 집계였습니다. 합 집계는 이웃이 많을수록 값이 커지므로, 모델이 패턴이 아니라 "거래량이 많다 = 의심"이라는 지름길(degree shortcut)을 배우기 쉽습니다 — 합성 데이터에서는 통하지만 거래량 분포가 다른 세트로 가면 무너지는 전형적 과적합 경로입니다. v7은 두 단계를 모두 평균(index_mean)으로 바꾸고, 거래량 정보가 정말 필요할 때를 위해 log1p(병렬 엣지 수)/5라는 통제된 명시 항으로만 남겼습니다. 활성함수는 ReLU 대신 SiLU(부드러운 기울기), 잔차 연결은 ③ 2stage에서 시도했다가 빠졌던 것이 3층 안정화를 위해 복귀했습니다.

4-3. shortcut dropout — 지름길 피처를 일부러 지운다

def _drop_shortcuts(self, x):
    if torch.rand(()) >= self.shortcut_dropout:   # 학습 스텝의 35%에서만 발동
        return x
    x = x.clone(); x[:, self.shortcut_idx] = 0.0   # 해시 24 + currency_mismatch를 통째로 0
    return x

학습 스텝의 35%에서 카테고리 해시·통화 불일치 피처를 배치 전체에서 통째로 0으로 지웁니다(추론 시에는 항상 켜짐). 이유: "ACH면 의심" 같은 표 피처 암기는 GBT도 할 수 있는 일이고, 세트가 바뀌면 무너집니다. 그 피처가 사라진 상황을 강제로 만들어 모델이 그래프 구조(관계 패턴)에서도 판단 근거를 찾도록 압박하는 정칙화입니다.

4-4. 계좌 보조 head

거래 위험도와 별도로, 대상 구간에 등장한 계좌 각각에 대해 "이 계좌가 양성 거래에 연루되는가"를 예측하는 보조 손실(가중 0.2)을 둡니다. 개별 거래 라벨은 노이즈가 크지만(세탁 시나리오의 일부 거래만 라벨됨) 계좌 수준 신호는 더 안정적이라, 노드 표현 학습을 보강합니다. 단, 이 보조 출력을 거래 확률과 강제로 합치지 않고, 운영에서는 §6-3의 별도 계좌 위험 집계로만 사용합니다 — "계좌 라벨은 거래 라벨의 집계일 뿐 진짜 KYC/SAR 정답이 아니다"라는 한계를 노트북이 명시하기 때문입니다.

5. 학습 절차 — 스윕 → 본학습 → 앙상블

5-1. 학습 기본 설정과 그 이유

설정이유
AdamW lr 1.5e-3, weight_decay 1e-4, 최대 50에폭, 조기종료 patience 7, dropout 0.20v6(60에폭·wd 1e-5·dropout 0.15)보다 정칙화를 강화 — 일반화 우선 방침. LR은 ReduceLROnPlateau(선택 점수 정체 시 절반, min 1e-5)
손실 = 거래 BCE(pos_weight) + 0.2 × 계좌 BCE극단 불균형 보정 + 보조 신호. pos_weight 상한은 스윕으로 선택(5-2)
혼합정밀 bf16 우선 (지원 GPU에서), fp16이면 GradScalerbf16은 fp16보다 수치 범위가 넓어 overflow에 강함. 그래도 non-finite logit이 나오면 같은 창을 fp32로 재시도 → 그래도 실패하면 손상 파라미터 목록과 함께 예외를 던지는 3단 방어 코드가 학습·평가 루프 양쪽에 있습니다. 기울기도 non-finite면 즉시 중단
모델 선택 점수 = 0.70 × val PR-AUC + 0.30 × 최악 시간환경 PR-AUC평균만 보면 특정 시기에 무너지는 모델이 선택될 수 있음 — 검증 구간을 시간순 4조각 내 최악 조각 성능을 30% 반영해 "어느 시기에도 무너지지 않는 모델"을 선택

5-2. POS_WEIGHT_CAP 스윕 — ④부터 미뤄온 숙제의 해결

양성 가중 상한 {5, 15, 30} 세 후보를 동일 시드(0)·12에폭 파일럿으로 각각 학습해, 위의 선택 점수가 가장 높은 값을 고릅니다. 핵심 규율은 "cap 선택에는 validation만 사용하고 calibration/test는 관여하지 않는다"입니다 — 하이퍼파라미터 선택까지도 누수 관리 대상으로 본 것입니다. ④ 노트북이 "5/15/30 스윕 권장(이번엔 고정)"이라고 미뤄둔 과제가 여기서 절차로 구현됐습니다. 업로드본에는 첫 후보의 파일럿 결과(cap=5: val AP 0.2851, 최악 시간환경 AP 0.1708, 선택 점수 0.2508, 7.2분)까지 기록되어 있습니다.

5-3. GroupDRO — 최악의 시기를 잘하도록 학습

q[env] *= torch.exp(0.05 * raw_loss)   # 손실이 큰 시간환경의 가중치를 지수적으로 키움
q /= q.sum()
loss = raw_loss * q[env] * 4           # 그 환경의 손실을 더 무겁게 반영

train 구간을 시간순 4개 "환경"으로 나누고, 학습 중 손실이 큰(못하는) 환경의 가중치를 키워 그 시기를 집중 학습합니다(Sagawa et al., ICLR 2020). 거래 데이터는 시기마다 분포가 달라지는 비정상(non-stationary) 데이터라, 평균 손실만 낮추면 특정 시기에 취약한 모델이 나올 수 있다는 문제의식입니다. 모델 선택 점수의 "최악 시간환경 30%"와 짝을 이루는 학습 측 장치입니다.

5-4. 본학습과 앙상블

선택된 cap으로 시드 3개(0, 1, 2)를 각각 본학습(최대 50에폭)하고, 평가 시에는 3개 모델의 로짓을 평균해 앙상블합니다(v6의 4시드 확률 평균과 달리 로짓 평균 — 이후 temperature scaling이 로짓 단위에서 동작하기 때문입니다). 매 학습은 seed_everything()으로 random/numpy/torch 시드를 함께 고정해 재현 가능합니다.

6. 보정·평가·운영 장치

6-1. temperature scaling과 임계값 — 전부 calibration에서, 한 번만

3시드 앙상블 로짓을 calibration 분할에서 temperature scaling합니다 — 로짓을 단일 상수 T로 나눠(sigmoid(z/T)) 출력 확률이 실제 적중률과 맞도록 보정하는 후처리로, T는 LBFGS로 calibration BCE를 최소화해 학습합니다(Guo et al., ICML 2017). 순위를 바꾸지 않으므로 PR-AUC는 그대로이고, "위험도 0.9"라는 숫자가 실제로 90% 확률을 의미하게 만들어 조사역·경보 예산 계산이 신뢰할 수 있는 확률 위에서 돌게 합니다. F1 최적 임계값과 경보 예산 임계값(calibration 확률의 상위 0.1% 분위수)도 모두 calibration에서 정한 뒤 test에 고정합니다 — "test 분위수로 경보 임계값을 정했던 v6 방식은 test 분포를 미리 사용하므로 제거했다"고 노트북이 명시합니다.

6-2. 최종 지표: 점수에 불확실성과 신뢰도를 붙인다

test에서는 PR-AUC 한 점만 보고하지 않습니다. 시간 블록 부트스트랩 95% 신뢰구간(하루 단위 블록을 300회 복원추출 — 거래는 시간적으로 상관되어 있어 개별 행 단위 부트스트랩은 CI를 과소평가하기 때문에 블록 단위로 뽑습니다), ECE(보정 오차 — 출력 확률과 실제 적중률의 괴리), 고정 임계값 2종에서의 Precision/Recall/F1/경보 건수를 함께 산출합니다.

6-3. 계좌 단위 보조 판정

거래 점수를 계좌로 투영해 계좌 위험도 = 0.7 × 최대 점수 + 0.3 × 평균 점수로 집계합니다 — 최대값(가장 위험한 거래 한 건)을 주로 보되 평균으로 일회성 스파이크를 완충하는 가중입니다. 계좌 정답은 "해당 평가 구간에서 양성 거래에 한 번이라도 연루됐는가"로 정의하는데, 이것이 진짜 KYC/SAR 계좌 라벨이 아니라 거래 라벨의 집계일 뿐이므로 보조 triage(조사 우선순위 참고)로만 보고한다고 한계를 명시합니다. 상위 1,000개 계좌는 top_accounts.csv로 저장됩니다.

6-4. 드리프트 모니터 — 라벨이 늦게 오는 운영 현실 대비

실제 운영에서는 정답(세탁 여부 확정)이 수개월 늦게 도착합니다. 그래서 라벨 없이도 모델 열화를 감지하는 신호를 준비했습니다: score PSI(점수 분포 이동), 42개 피처 각각의 PSI, 경보율 비율(임계값이 calibration에 고정되어 있으므로 test 경보율 변화 자체가 드리프트 신호), 그리고 라벨 도착 후의 PR-AUC 하락·ECE. 각 신호에 WARN/CRITICAL 임계(예: PSI 0.10/0.25, 경보율 비율 1.5/2.0)를 부여해 표로 출력합니다 — 백엔드 대시보드의 모니터링 지표로 그대로 옮길 수 있는 형태입니다.

6-5. 필수 ablation 5종과 zero-shot 세트 간 평가

ablation은 "한 번에 하나만 제거" 원칙으로 5종을 정의합니다: full_v7(기준) / no_relative_time(시간 12차원을 0으로 마스킹 — 합성 시간 패턴 과적합 검사) / no_group_dro / no_account_aux / no_shortcut_dropout. 계산비용 때문에 기본 OFF이며 "논문 표를 만들 때 반드시 켜라"고 적혀 있습니다. 세트 간 평가는 zero-shot 프로토콜입니다 — source(HI-Small)에서 학습한 모델·금액 통계·온도·임계값을 전부 고정한 채 대상 세트(LI-Small 등)의 마지막 20%를 채점하고, 앞 80%는 라벨 없이 과거 그래프 컨텍스트로만 사용합니다. "대상 세트에서 재학습한 성능"과 혼동하지 말라는 주석과 함께, 파일이 없으면 스킵하고 확보 후 해당 셀만 재실행하도록 만들어져 있습니다.

6-6. 대조군과 재현성

그래프의 기여를 분리하기 위해 동일 42차원 피처·동일 분할·동일 calibration 임계값 절차로 HistGradientBoosting(테이블 모델, 그래프 없음)을 학습하는 strict-causal 베이스라인이 포함되어 있고(gnn_minus_tabular_test_ap로 차이를 직접 기록), 실험 전체의 설정·피처 통계·분할 경계·임계값·인과 계약("메시지 엣지와 노드 통계는 엄격히 target_start 이전, 동일 분 제외")을 manifest.json으로 저장합니다. "test를 여러 번 보며 설계를 바꾸지 마라, 변경이 생기면 새 experiment id를 만들라"는 운영 규율도 §10에 명문화되어 있습니다.

7. 실행 상태와 해석 원칙 (반드시 읽으십쇼)

업로드본 실행 상태 코드는 전 구간 완성되어 있으나, 업로드된 사본에 기록된 실행 출력은 데이터 적재·분할표·피처 구성·causal probe·스윕의 첫 후보(cap=5 파일럿: val AP 0.2851, 12에폭, 7.2분)까지입니다. 시드 3개 본학습, calibration/test 최종 지표, GBT 대조, 드리프트 표, zero-shot 결과는 기록되어 있지 않습니다. 따라서 v7의 최종 성능 수치는 아직 없으며, 본 문서도 결과가 아닌 설계와 절차를 설명합니다.

노트북 §11이 명시한 해석 원칙 다섯 가지는 그대로 옮길 가치가 있습니다. 첫째, v6의 test PR-AUC 0.5742와 v7 수치를 그대로 우열 비교하면 안 됩니다 — v7은 더 엄격한 인과 그래프, 별도 calibration 분할, 꼬리 포함 테스트(양성률 0.205%)를 쓰므로, 공정 비교에는 v6 구조를 v7 프로토콜로 재실행해야 합니다. 둘째, zero-shot 세트 간 성능이 개선되지 않으면 "일반화 모델" 주장을 철회하고 어떤 shortcut ablation이 실패했는지 보고합니다. 셋째, 상대 시간 제거(A/B)가 외부 세트에서 더 좋으면 실데이터 기본 모델은 time-off로 정합니다. 넷째, 계좌 보조 라벨은 거래 라벨의 집계일 뿐 KYC/SAR ground truth가 아닙니다. 다섯째, 실배포 전에는 entity resolution, 지연 라벨, 조사자 피드백 편향, 공정성, 비용 기반 임계값을 별도 검증합니다.
