Patterns.txt 자체가 그래프 그림은 아닙니다. 텍스트 블록을 파싱한 뒤 계좌를 node, 거래를 directed edge로 변환해야 합니다. Patterns 밖 자금세탁 거래에는 attempt ID가 없으므로 사건별 색칠이나 사건 recall 계산이 불가능합니다.

날짜를 그대로 모델에 넣으면 왜 문제가 되나?

예를 들어 Small 데이터에서는 9월 11일부터 정상 거래가 거의 사라집니다. 모델에 날짜를 그대로 주면 자금 흐름을 분석하지 않고도 “9월 11일 이후 거래는 자금세탁일 가능성이 높다”는 규칙을 외울 수 있습니다. 이것은 자금세탁 패턴을 배운 것이 아니라 합성 데이터가 끝나는 날짜를 외운 것입니다.

처리 방법: 달력 날짜, 데이터 시작 후 며칠째인지, 데이터 종료일까지 며칠 남았는지는 입력 변수로 사용하지 않습니다. 대신 예측 시점 이전 1시간·24시간·7일의 거래 횟수, 직전 거래 후 지난 시간처럼 실제 운영에서도 알 수 있는 과거 정보만 사용합니다. 시간대와 요일은 사용할 수 있지만, 이 두 변수를 뺀 모델도 다시 학습해 성능이 크게 떨어지는지 비교합니다.

평가 지표를 쉽게 읽기

재현율(Recall)

실제 자금세탁 거래 중 모델이 경보로 찾아낸 비율입니다. 실제 세탁 거래가 100건이고 60건을 찾았다면 재현율은 60%입니다. 높을수록 놓친 세탁 거래가 적습니다.

정밀도(Precision)

모델이 의심스럽다고 경보를 낸 거래 중 실제 자금세탁인 비율입니다. 경보 1,000건 중 실제 세탁이 60건이면 정밀도는 6%입니다. 높을수록 조사해야 할 불필요한 경보가 적습니다.

정해진 경보 수에서의 재현율

조사팀이 하루에 확인할 수 있는 경보 수를 먼저 정하고, 그 범위 안에서 실제 세탁을 얼마나 찾는지 봅니다. 예를 들어 상위 1,000건만 조사할 때 실제 세탁 100건 중 60건이 들어 있다면 Recall@1,000 = 60%입니다.

상위 K건의 정밀도

위험 점수가 높은 상위 K건 중 실제 세탁이 얼마나 되는지 봅니다. 위 예시에서 상위 1,000건 중 실제 세탁이 60건이면 Precision@1,000 = 6%입니다. K는 조사 가능한 경보 수입니다.

PR-AUC

경보 기준점을 느슨하게 또는 엄격하게 바꿨을 때 재현율과 정밀도가 함께 어떻게 변하는지를 하나의 값으로 요약합니다. 0에 가까울수록 나쁘고 1에 가까울수록 좋습니다. 정상 거래가 압도적으로 많은 AML 데이터에서 모델 전체 성능을 비교할 때 유용합니다.

사건 적발률(Incident Recall@1)

자금세탁 사건을 구성하는 여러 거래 중 한 건이라도 경보를 냈으면 해당 사건을 적발했다고 봅니다. 사건 50개 중 35개에서 한 번 이상 경보가 발생했다면 사건 적발률은 70%입니다.

첫 경보까지 걸린 시간

자금세탁 사건의 첫 거래가 시작된 뒤 모델이 처음 경보를 낼 때까지 걸린 시간입니다. 같은 사건을 찾더라도 2시간 뒤 경보한 모델이 3일 뒤 경보한 모델보다 대응에 유리합니다. 짧을수록 좋습니다.

계좌 상위 K개 재현율

위험 점수가 높은 계좌 K개를 조사할 때 실제 위험 계좌가 얼마나 포함되는지 봅니다. 거래가 아니라 계좌를 조사 대상으로 삼는 경우에 사용합니다.

Patterns 커버리지는 HI 약 61~65%, LI 19~29%입니다. Patterns에 없는 Is Laundering=1 거래를 정상으로 취급하면 안 되며, 거래 평가는 전체 양성으로, 사건 평가는 attempt가 있는 부분집합으로 각각 보고해야 합니다.

6. 거래가 매우 많은 계좌를 GNN에서 처리하는 방법

송신 거래 수 중앙값은 2건, 99백분위는 92건이지만 최대는 168,672~222,037건입니다. GNN이 이런 계좌의 모든 거래 상대를 한꺼번에 불러오면 필요한 메모리와 계산량이 급격히 늘고, 소수의 대량 거래 계좌가 모델 판단에 지나치게 큰 영향을 줄 수 있습니다.

“거래 상대를 불러온다”는 뜻

현재 A → B 거래가 자금세탁인지 판단한다고 가정합니다. 최종 결과는 이 거래의 자금세탁 확률 하나이지만, GNN은 그 확률을 계산하기 전에 A와 B가 과거에 누구와 어떤 거래를 했는지 참고합니다. 주변 계좌와 과거 거래 정보를 모아 A와 B의 특징을 숫자 벡터로 만든 뒤, 현재 거래의 금액·통화·결제수단과 결합해 위험 점수를 계산합니다.

A·B의 과거 거래 조회주변 계좌와 과거 거래 정보
→

→

왜 일부만 선택하나? 예를 들어 A의 과거 송신 거래가 168,672건이고 고유 상대 계좌가 14,230개라면, A와 연결된 정보를 모두 읽는 것만으로도 계산량이 매우 커집니다. 여기에 상대 계좌들의 거래까지 한 단계 더 따라가면 참고해야 할 거래 수가 수십만~수백만 건으로 늘어날 수 있습니다. 거래 하나를 판단할 때마다 이 작업을 반복하는 것은 학습과 실시간 탐지 모두에서 비효율적입니다.

7. 어떤 평가 숫자를 볼 것인가

정확도만 사용하지 않음

정상 거래가 99.9% 이상이므로 모든 거래를 정상이라고 예측해도 정확도가 매우 높습니다. 정해진 경보 수 안에서 실제 세탁을 얼마나 찾는지, 경보 중 실제 세탁이 얼마나 되는지, 하루에 경보가 몇 건 발생하는지를 봅니다.

조건별 결과를 따로 확인

Patterns 안/밖, 8개 패턴 유형, 정상 대량 처리 계좌, 은행별, 결제수단별, 시간 구간별 성능을 분리해 어떤 조건에서 놓치거나 오탐하는지 확인합니다.

데이터 규모별 역할

Small은 코드와 데이터 처리 검증, Medium은 여러 모델과 입력 변수 비교, Large는 최종 성능·메모리·처리시간 확인에 사용합니다.

HI/LI 강건성

HI에서 선택한 모델과 임계값을 더 희소한 LI에서 검증합니다. 두 세트는 독립 세계이므로 동일 계좌 추적에는 사용하지 않습니다.

8. 서비스에서 무엇을 입력하고 무엇을 판정할 것인가

먼저 구분할 것: 여러 거래를 한 번에 모델에 넣는 처리 단위와 모델이 무엇에 대해 결과를 내는 판정 단위는 서로 다릅니다. 거래 1,000건을 묶어서 한 번에 처리해도, 결과는 거래마다 하나씩 총 1,000개를 받을 수 있습니다.

8.1 판정 단위는 무엇인가?

IBM 데이터의 원래 라벨은 거래 한 건마다 붙어 있으므로 첫 모델은 거래별 자금세탁 확률을 출력하는 거래 판정 모델로 두는 것이 가장 자연스럽습니다. 계좌 위험도와 조사 사건은 거래별 결과를 모아 그 다음 단계에서 만들 수 있습니다.

구분단위서비스에서 하는 일이 프로젝트의 권장안
모델 처리 단위여러 거래의 묶음GPU·서버 병목을 줄이기 위해 거래를 배치로 계산거래 수 또는 최대 대기시간 기준의 작은 배치
모델 판정 단위거래 1건각 거래에 0~1 위험 점수와 정상·의심 판정 부여기본 출력으로 사용
계좌 위험 단위계좌 1개최근 거래 점수와 행동을 모아 계좌 위험도 계산거래 결과를 집계한 보조 출력
조사 케이스 단위연관 거래·계좌 묶음같은 자금 흐름으로 보이는 경보를 묶어 조사자에게 제공최종 운영 경보 형태

예시

거래 1,000건을 한 번에 입력하면 모델은 [0.03, 0.87, 0.42, …]처럼 거래별 위험 점수 1,000개를 출력합니다. 이후 A 계좌에서 높은 점수의 거래가 반복되면 A의 계좌 위험도를 높이고, A → B → C처럼 연결된 의심 거래들은 하나의 조사 케이스로 묶을 수 있습니다.

계좌 임베딩·상태

각 계좌의 과거 행동을 고정 길이 숫자 벡터로 요약한 값입니다. 계좌마다 별도로 저장할 수 있고, 새로운 거래가 처리되면 달라질 수 있습니다.

8.3 임베딩이 저장돼 있다면 과거 거래도 다시 넣어야 하나?

일반 GNN도 과거 거래 전체를 항상 다시 넣는 것은 아닙니다. 보통 예측 대상 계좌 주변에서 최근 일정 기간 또는 일부 이웃만 조회해 작은 그래프를 만들고 임베딩을 계산합니다. 방식의 차이는 과거 전체 사용 여부가 아니라, 예측할 때 주변 그래프를 다시 조회해 임베딩을 계산하는가, 아니면 미리 저장하고 갱신해 둔 계좌 상태를 바로 읽는가입니다.

방식예측할 때 필요한 정보상태를 만들거나 갱신할 때장점주의점
주변 그래프 조회형 GNN현재 거래 + A·B 주변의 최근 거래 또는 선택된 이웃예측할 때마다 작은 주변 그래프에서 임베딩을 계산예측 시점의 최신 주변 구조를 직접 반영과거 전체를 쓰지는 않지만 매번 그래프 조회와 계산이 필요
저장 임베딩 사용현재 거래 + 미리 저장한 A·B 임베딩별도 작업으로 주기적으로 다시 계산하거나 새 거래를 반영해 갱신예측할 때 과거 거래를 다시 읽지 않아 빠름저장 값이 오래되면 최근 행동을 반영하지 못함
시간 변화형 GNN(TGN)현재 거래 + 저장된 A·B 상태, 필요하면 최근 이웃 일부각 거래를 예측한 뒤 해당 거래로 A·B 상태를 갱신과거를 상태에 요약해 실시간 처리에 적합거래 순서와 상태 저장·복구를 정확히 관리해야 함

세 방식을 한 문장으로 구분하면

  • 주변 그래프 조회형 GNN: 예측할 때 관련 과거 거래와 주변 계좌 일부가 필요합니다.
  • 저장 임베딩 방식: 예측할 때 과거 거래를 다시 조회하지 않지만, 임베딩을 만드는 작업과 최신 상태로 갱신하는 작업이 별도로 필요합니다.
  • TGN: 저장된 계좌 상태와 현재 거래가 기본 입력입니다. 과거 거래 전체는 다시 넣지 않으며, 최근 이웃 일부는 모델 설계에 따라 추가할 수 있습니다.

따라서 저장 임베딩 방식과 TGN이 과거 정보가 전혀 필요 없다는 뜻은 아닙니다. 과거 정보가 이미 저장 상태에 요약되어 있기 때문에 예측할 때 전체 이력을 다시 읽지 않는 것입니다.

왜 상태를 갱신해야 하나?

임베딩은 고정된 계좌번호가 아니라 해당 시점까지의 행동 요약입니다. A가 새로운 계좌들에 연속 송금하면 A의 행동과 주변 연결이 달라지므로 저장된 상태도 바뀌어야 합니다. 오래된 임베딩을 계속 사용하면 최근의 급격한 행동 변화를 놓칠 수 있습니다.

8.4 여러 거래를 한 번에 처리하는 순서

거래 1,000건 도착배치에 등장한 고유 계좌 추출
→
계좌 상태 일괄 조회중복 계좌는 한 번만 조회
→
위험 점수 1,000개 출력입력 거래마다 개별 판정
  1. 배치에 포함된 송신·수신 계좌의 저장 상태를 한 번에 가져옵니다.
  2. 각 거래의 송신 상태, 수신 상태, 금액·통화·결제수단을 결합합니다.
  3. 입력 거래 수와 같은 개수의 자금세탁 위험 점수를 계산합니다.
  4. 거래별 경보를 반환한 뒤 배치 거래로 관련 계좌 상태를 갱신합니다.
  5. 높은 거래 점수를 계좌별로 모으고 연관된 거래를 조사 케이스로 묶습니다.

중요: 현재 거래를 계좌 상태에 먼저 반영한 뒤 같은 거래를 예측하면 판단 대상 거래를 이미 본 것이 됩니다. 반드시 거래별 점수 계산 → 결과 반환 → 상태 갱신 순서를 지켜야 합니다.

8.5 저장 상태와 최근 이웃을 함께 쓰는 이유

저장 상태만 사용하면 빠르지만 최근의 중요한 연결을 충분히 기억하지 못할 수 있습니다. 반대로 과거 그래프 전체를 매번 조회하면 너무 느립니다. 따라서 저장된 계좌 상태에 최근 이웃 20개나 100개만 추가하는 절충 방식을 비교할 수 있습니다.

권장 비교: 저장 상태만 사용 / 저장 상태+최근 20개 이웃 / 저장 상태+최근 100개 이웃을 비교합니다. 처리시간·메모리와 함께 거래 탐지율, 정상 대량 거래 계좌의 오탐률, 8개 패턴별 탐지율을 확인합니다.

현재 서비스 구상의 기본안: 여러 거래를 작은 배치로 입력하고, 저장된 송·수신 계좌 상태와 현재 거래 특징으로 거래별 위험 점수를 출력합니다. 필요한 경우 최근 이웃 일부를 보완 정보로 사용하며, 거래별 결과를 계좌 위험도와 조사 케이스로 다시 묶습니다.

8.6 모델 종류와 임베딩 사용 방식을 구분하기

핵심: LightGBM 같은 테이블 모델, GraphSAGE 같은 GNN, TGN 같은 시간 그래프 모델은 서로 다른 모델입니다. 반면 주변 그래프 조회형과 저장 임베딩 사용은 특정 모델 이름이 아니라, GNN이 계좌 임베딩을 언제 계산하고 서비스에서 어떻게 사용할지에 관한 방식입니다.

전체 관계

├─ Logistic Regression / Random Forest
├─ LightGBM / XGBoost / CatBoost
└─ MLP
그래프 신경망
├─ 일반 GNN: GCN / GraphSAGE / GAT / GIN

일반 테이블 모델

거래 한 건을 표의 한 행으로 보고 학습합니다. 현재 거래 특징과 과거 집계 특징을 입력해 거래별 위험 점수를 냅니다. 그래프 연결 자체를 입력하지는 않습니다.

예: LightGBM, XGBoost, CatBoost, MLP

일반 GNN

계좌 연결 구조와 거래 간선을 직접 사용해 계좌 임베딩을 만드는 별도 신경망 모델입니다. 자금세탁 분류가 목적이면 송·수신 계좌 임베딩과 거래 특징을 위험 점수로 바꾸는 출력층을 뒤에 붙이며, 보통 GNN과 작은 MLP를 하나의 모델로 함께 학습합니다.

예: GraphSAGE, GAT, GIN + 거래 분류 출력층

주변 그래프 조회형

특정 모델명이 아니라 GNN을 사용하는 방식입니다. 예측 시 A·B 주변의 최근 거래와 선택된 계좌를 조회하고, GraphSAGE 등의 GNN으로 임베딩을 계산합니다.

저장된 고정 임베딩

특정 모델명이 아니라 GNN 등으로 미리 계산한 계좌 임베딩을 저장하고 재사용하는 방식입니다. 새로운 거래를 예측할 때 GNN으로 주변 그래프를 다시 계산하지 않고 저장소에서 송·수신 계좌 임베딩을 조회합니다.

시간 그래프 모델과 TGN

TGN은 시간에 따라 계좌 상태를 갱신하는 별도의 그래프 신경망 모델입니다. LightGBM으로 TGN을 구현하는 것은 아니며, 계좌별 상태·시간 정보·현재 거래를 이용해 점수와 다음 상태를 계산합니다.

저장 임베딩으로 거래를 판정하는 방법

저장소에서 가져온 송신 계좌 임베딩과 수신 계좌 임베딩을 현재 거래의 금액·통화·결제수단과 합칩니다. 이렇게 만든 한 행을 MLP나 LightGBM에 입력해 현재 거래의 위험 점수를 계산할 수 있습니다.

현재 권장안: 거래를 작은 배치로 입력하고, 저장된 계좌 상태를 사용하는 TGN 계열 모델로 거래마다 위험 점수를 출력합니다. 저장 상태만으로 부족한 최신 그래프 관계는 최근 이웃 일부로 보완하고, 거래별 결과는 계좌 위험도와 조사 케이스로 다시 묶습니다.
거래 마이크로배치거래 수 또는 최대 대기시간 기준
→
TGN 계좌 상태+최근 이웃송·수신 계좌의 과거 행동 요약
→
거래별 점수와 케이스개별 판정 후 계좌·사건 단위 집계

왜 이 방식이 적합해 보이나?

시간에 따라 변하는 거래 그래프

거래가 발생할 때마다 계좌의 행동과 연결 관계가 달라집니다. TGN은 거래 순서에 따라 계좌 상태를 갱신하므로 이 특성을 직접 반영할 수 있습니다.

대량 거래 계좌 처리

최대 송신 거래가 16만~22만 건인 계좌가 있어 주변 그래프를 매번 크게 만드는 방식은 부담이 큽니다. 저장 상태를 사용하면 과거 전체를 다시 계산하지 않아도 됩니다.

배치 처리와 거래별 출력

여러 거래를 한 번에 계산해 서버·GPU 사용 효율을 높이면서도 입력 거래마다 개별 위험 점수를 반환할 수 있습니다.

최신 그래프 정보 보완

저장 상태가 기억하지 못한 최근 연결은 최근 이웃 20~50개를 추가해 보완할 수 있습니다. 최근 이웃이 실제 성능을 높이는지는 실험으로 결정합니다.

후보 방식 비교

방식예상 탐지 성능서비스 속도구현 난이도권장 역할
일반 테이블 모델기준 성능매우 빠름낮음반드시 구축할 비교 기준
저장된 고정 임베딩중간매우 빠름낮음~중간빠른 서비스 후보, 상태 노후화 확인
주변 그래프 조회형 GNN높을 가능성상대적으로 느림중간그래프 구조의 추가 가치 확인
TGN 상태만 사용높을 가능성빠름높음실서비스 주 모델 후보
TGN+최근 이웃 일부가장 높을 가능성중간~빠름가장 높음성능 향상이 충분할 때 최종 후보

주의: 복잡한 GNN이 반드시 더 좋은 것은 아닙니다. TGN+최근 이웃의 성능 향상이 작고 처리시간이나 운영 복잡도가 크게 늘어난다면 TGN 상태만 사용하거나 일반 테이블 모델을 선택하는 편이 더 나을 수 있습니다.

단계적으로 구현하는 이유

  1. 테이블 기준 모델: 현재 거래와 과거 1시간·24시간·7일 집계 특징으로 빠른 기준 성능을 만듭니다.
  2. 주변 그래프 조회형 GNN: 최근 이웃을 이용했을 때 계좌 관계가 실제로 추가 성능을 주는지 확인합니다.
  3. TGN 상태 기반 모델: 그래프 조회 비용을 줄이면서 성능을 유지할 수 있는지 확인합니다.
  4. TGN+최근 이웃: 상태만으로 부족할 때 최근 이웃 20~50개를 추가하고 성능 향상과 비용을 비교합니다.

현재 결론: 최종 목표는 거래별 판정 + 마이크로배치 + TGN 계좌 상태 + 선택적인 최근 이웃 + 계좌·케이스 집계입니다. 다만 TGN의 추가 성능이 구현·운영 비용을 정당화하는지는 반드시 단순 모델과 같은 조건에서 비교한 뒤 결정합니다.

권장 실험 순서

  1. Small로 적재·키 정규화·시간 재생·그래프 생성 코드를 검증합니다.
  2. Medium에서 정상 거래가 충분한 기간만 사용해 시간순으로 데이터를 나누고, 입력 변수를 하나씩 뺀 모델도 비교합니다.
  3. 일반 머신러닝 모델, 한 은행이 볼 수 있는 그래프만 사용한 GNN, 전체 그래프를 사용한 참고용 GNN을 같은 기준으로 비교합니다.
  4. Large의 정상 거래가 충분한 기간에서 최종 성능·메모리·처리시간을 평가합니다.
  5. 정상 거래가 끝난 이후 구간은 특수 상황에 대한 보조 시험으로 따로 보고합니다.
  6. 거래를 얼마나 찾았는지와 자금세탁 사건을 얼마나 찾았는지, 조건별 결과를 함께 제시합니다.
