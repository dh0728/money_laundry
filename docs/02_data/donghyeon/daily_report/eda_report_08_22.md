### 데이터셋에서 나온 패턴들

| 패턴 | 데이터에서 확인할 구조 |
|---|---|
| FAN-OUT | 한 계좌가 여러 계좌로 분산 송금 |
| FAN-IN | 여러 계좌가 한 계좌로 집중 송금 |
| GATHER-SCATTER | 여러 계좌 → 중심 계좌 → 다시 여러 계좌 |
| SCATTER-GATHER | 한 계좌 → 여러 중간 계좌 → 한 계좌 |
| CYCLE | 자금이 여러 계좌를 거쳐 시작 계좌로 복귀 |
| RANDOM | 통제 계좌 사이를 무작위 경로처럼 이동하고 시작점으로 돌아오지 않음 |
| BIPARTITE | 여러 입력 계좌에서 여러 출력 계좌로 이동 |
| STACK | Bipartite 구조가 여러 층으로 이어짐 |

현재 로드한 HI-Small과 LI-Small의 거래·계좌 데이터에서는 결측값이 확인되지 않았다.

### 계좌 및 엔티티 고유값 확인

| 데이터셋 | 계좌 행 수 | Account Number 고유값 수 | 행 수와의 차이 | Entity ID 고유값 수 | Entity Name 고유값 수 |
|---|---:|---:|---:|---:|---:|
| HI-Small | 518,581 | 518,573 | 8 | 166,207 | 166,207 |
| LI-Small | 712,688 | 712,684 | 4 | 224,931 | 224,931 |

- HI-Small은 계좌 행 수보다 `Account Number` 고유값 수가 8개 적고, LI-Small은 4개 적다. 이는 단순히 중복 행이 8개·4개라는 뜻은 아니므로, 중복 계좌번호별 행 수와 은행 ID 조합을 추가 확인해야 한다.
- `Entity ID`와 `Entity Name`의 고유값 수는 각 데이터셋에서 동일하다. 다만 두 컬럼이 실제로 일대일 대응하는지는 별도 교차 검증이 필요하다.

### 수치형 거래 금액 요약

은행 ID와 자금세탁 라벨은 수치형으로 자동 인식되었지만 연속형 측정값이 아니므로, 아래 표는 실제 금액 컬럼만 정리했다.

| 데이터셋 | 컬럼 | 평균 | 중앙값(50%) | 95% 분위수 | 99% 분위수 | 최댓값 |
|---|---|---:|---:|---:|---:|---:|
| HI-Small | Amount Received | 5,988,726 | 1,411.01 | 649,906.51 | 14,751,230 | 1,046,302,000,000 |
| HI-Small | Amount Paid | 4,509,273 | 1,414.54 | 623,757.22 | 13,524,530 | 1,046,302,000,000 |
| LI-Small | Amount Received | 6,324,067 | 1,397.62 | 623,594.67 | 13,368,490 | 3,644,854,000,000 |
| LI-Small | Amount Paid | 4,676,036 | 1,399.44 | 600,085.32 | 12,364,830 | 3,644,854,000,000 |

평균이 중앙값보다 매우 크고 최댓값이 1조 이상이므로 거래 금액 분포의 오른쪽 꼬리가 매우 긴 것으로 보인다. 이후 로그 변환, 통화별 분리, 이상치 구간 확인이 필요하다.

### ID 컬럼의 원본 형식 보존 필요

| 데이터셋 | 컬럼 | Pandas 자동 타입 | 원본 예시 | 자동 추론 결과 예시 | 확인된 문제 |
|---|---|---|---|---|---|
| HI-Small | From Bank | `int64` | `010`, `03208` | `10`, `3208` | 선행 0 소실 |
| HI-Small | To Bank | `int64` | `001`, `002439` | `1`, `2439` | 선행 0 소실 |
| LI-Small | From Bank | `int64` | `011`, `03402` | `11`, `3402` | 선행 0 소실 |
| LI-Small | To Bank | `int64` | `001120`, `0243166` | `1120`, `243166` | 선행 0 소실 |
| HI/LI-Small | Account, Account.1 | `str` | `8000EBD30`, `8006AA910` | 동일 | 예시 범위에서는 원본 유지 |

`From Bank`와 `To Bank`는 계산 대상 숫자가 아니라 식별자이며, 기본 CSV 로드 시 선행 0이 사라진다. 원본 식별자와 패턴 파일의 값을 정확히 연결하려면 문자열 타입으로 읽는 것이 적절하다. 계좌 데이터의 `Bank ID`도 같은 기준으로 원본 형식을 확인해야 한다.

### 현재까지의 핵심 정리

- transaction 데이터 타입 변환
  - "From Bank": "string"
  - "Account": "string"
  - "To Bank": "string"
  - "Account.1": "string"
- account 데이터 타입 변환
  - "Bank ID": "string"
  - "Account Number": "string"
  - "Entity ID": "string"
- 계좌번호 고유값 : HI는 행 수보다 8개, LI는 4개 적음 
  - 은행 ID와 계좌번호의 복합키 기준으로 중복 해보니 계좌 번호만 동일하고 은행 ID는 달랐음
- 엔티티 고유값 : Entity ID와 Entity Name의 고유값 수가 동일 
- 결측값 : 거래·계좌 데이터 모두 0개
- 클래스 불균형 : 자금세탁 비율 HI 0.1019%, LI 0.0515% 
- 금액 분포 : 평균이 중앙값보다 매우 크고 최댓값이 1조 이상 
  - 통화별 분석 및 로그 스케일 검토
