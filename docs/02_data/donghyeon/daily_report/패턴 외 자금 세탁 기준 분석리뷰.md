### 패턴 외 자금 세탁 기준 분석
- Patterns.txt에 포함되지 않는 자금세탁 거래가 정상거래와 구분되는 특징을 가지고 있는지 확인
- 패턴 외 거래는 단건 또는 다건으로 미리 단정하지 않는다.

#### 실험 정의
- 양성 1: Is Laundering이 1이면서 Patterns.txt에 없는 거래
- 음성 0: Is Laundering이 0인 정상거래
- 학습 제외: Patterns.txt에 포함된 자금세탁 거래
- Reinvestment: 시뮬레이션 초기 잔액 성격이므로 기본적으로 제외 (481,056건) - 모델링 전체 행 수: 4,593,618
- Is Laundering이 0인 패턴 보조·환전 거래도 1차 기준에서는 데이터 라벨에 따라 음성으로 유지
- 분석 기간: 2022-09-01부터 2022-09-10까지
- 시간 분할: 학습 1-6일, 검증 7-8일, 테스트 9-10일
- 학습에서만 무작위로 1:10 언더샘플링해서 비율을 맞춤(정상거래만 지움)

#### 숫자형 피처

| 피처 | 설명 |
|---|---|
| `log_amount_paid` | 송금자가 지급한 `Amount Paid`를 `log1p`로 변환한 값입니다. 값이 클수록 지급 금액이 큽니다. |
| `log_amount_received` | 수취인이 받은 `Amount Received`를 `log1p`로 변환한 값입니다. |
| `log_amount_ratio` | `ln(Amount Received / Amount Paid)`입니다. 0에 가까우면 두 숫자가 비슷하고, 양수면 수취액 숫자가 더 크며, 음수면 지급액 숫자가 더 큽니다. |
| `is_cross_bank` | 송금 은행과 수취 은행이 다른지 나타냅니다. 다르면 1, 같으면 0입니다. |
| `is_self_transfer` | 은행 ID와 계좌번호가 송금·수취 양쪽에서 모두 같은 자기거래인지 나타냅니다. 자기거래면 1입니다. |
| `is_cross_currency` | `Payment Currency`와 `Receiving Currency`가 다른 환전 거래인지 나타냅니다. 다르면 1입니다. |
| `hour_sin` | 거래 시간의 24시간 순환성을 사인 값으로 표현한 피처입니다. `sin(2π × 시간 / 24)`로 계산합니다. |
| `hour_cos` | 거래 시간의 24시간 순환성을 코사인 값으로 표현한 피처입니다. `cos(2π × 시간 / 24)`로 계산합니다. |
| `is_weekend` | 토요일 또는 일요일이면 1, 평일이면 0입니다. |
| `sender_prev_count_log` | 현재 거래 이전에 해당 송금 계좌가 송금자로 등장한 횟수를 `log1p`로 변환한 값입니다. |
| `receiver_prev_count_log` | 현재 거래 이전에 해당 수취 계좌가 수취인으로 등장한 횟수를 `log1p`로 변환한 값입니다. |
| `pair_prev_count_log` | 현재 송금 계좌→수취 계좌 조합이 이전에 같은 방향으로 거래한 횟수를 `log1p`로 변환한 값입니다. |
| `hours_since_sender_prev_log` | 현재 송금 계좌의 직전 송금 이후 경과 시간을 시간 단위로 계산하고 `log1p`로 변환한 값입니다. |
| `amount_vs_sender_history` | 현재 지급 금액이 송금 계좌의 과거 평균 지급액보다 얼마나 큰지 로그 차이로 표현한 값입니다. |

시간 피처를 `hour_sin`, `hour_cos`으로 보는 이유?
- 시간은 순환하기 때문에 23시와 0시가 숫자로는 멀어 보이지만 실제로는 가깝습니다. 그래서 hour_sin과 hour_cos를 함께 사용
- 두 피처를 각각 따로 해석하기 보다는 한쌍으로 봐야함

#### 범주형 피처

| 피처 | 설명 |
|---|---|
| `Payment Format` | 거래 방식입니다. ACH, Cash, Cheque, Credit Card, Bitcoin, Wire 등이 있습니다. `Reinvestment`는 기본적으로 제외했습니다. |
| `Payment Currency` | 송금자가 지급한 통화입니다. 예: US Dollar, Euro, Yen |
| `Receiving Currency` | 수취인이 받은 통화입니다. 지급 통화와 다르면 환전이 포함된 거래입니다. |
| `day_of_week` | 거래 요일입니다. 월요일 0부터 일요일 6까지이며, 숫자의 크기 관계를 학습하지 않도록 범주형으로 처리합니다. |

- 요일, 주말, ACH 및 다른 Payment Format도 중요도에 포함돼 생성기 규칙을 활용하고 있음을 보여준다.
- 이 중요도는 트리가 해당 피처를 분할에 사용한 횟수이며 영향의 방향을 알려주지 않는다. 중요도가 높다고 실제 자금세탁의 원인이라는 뜻도 아니다.
- `log_amount_paid`와 `log_amount_received`처럼 강하게 중복된 피처는 중요도가 나뉘거나 불안정해질 수 있다.

#### 생성기 특성 의존 여부 확인

시간 피처와 Payment Format을 제거한 Logistic Regression을 전체 피처 모델과 비교했다.

##### 제거 모델 Confusion matrix

| 실제값 | 정상 예측 (`pred_0`) | 자금세탁 예측 (`pred_1`) | 합계 |
|---|---:|---:|---:|
| 정상거래 (`actual_0`) | 799,714 | 62,118 | 861,832 |
| 패턴 외 자금세탁 (`actual_1`) | 168 | 203 | 371 |

해석:

- 자금세탁 203건을 찾아 Recall은 54.72%로 높아졌다.
- 그러나 정상거래 62,118건을 잘못 경고했고, 경고 62,321건 중 실제 양성은 203건뿐이다.
- 자금세탁 1건을 찾기 위해 평균 약 307건의 경고를 확인해야 하므로 운영 효율은 매우 낮다.
- 높은 Recall은 양성을 정교하게 순위화해서가 아니라 넓은 범위의 거래를 양성으로 분류한 결과다.

#### 첫 번째 실험 결론

- 패턴 외 자금세탁과 정상거래 사이에 완전히 신호가 없는 것은 아니지만, 첫 번째 모델 성능은 ACH와 시간·요일 규칙에 크게 의존했다.
- 의미 있는 구조적 단서는 `sender_prev_count_log`와 `receiver_prev_count_log`는 양성 방향이고 `pair_prev_count_log`는 강한 정상 방향이라는 조합이다. 이는 활동 이력이 있는 계좌들이 기존에 거래하지 않던 상대와 거래하는 경우를 추가로 분석할 필요가 있음을 뜻한다.

- 금액 지급·수취 피처와 통화 지급·수취 피처의 중복도 줄여 다중공선성을 완화할 필요가 있다.
