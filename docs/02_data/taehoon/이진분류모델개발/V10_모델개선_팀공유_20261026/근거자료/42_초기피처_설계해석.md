## 피처와 패턴 연결을 읽는 방법

아래 표의 **관련 패턴·포착 단서와 한계**는 계산식에 근거한 설계 해석입니다. 현재 모델은 거래별 정상/세탁 의심을 이진 분류하며, 특정 피처가 해당 패턴을 실제로 탐지했다고 검증한 결과는 아닙니다. 정상 거래에도 같은 특성이 나타날 수 있습니다.

- **구조 단서:** 계좌·엔티티별 거래 상대 수처럼 집금·분산·직접 왕복 관계를 요약합니다.
- **보조 단서:** 횟수·시간·금액·통화·소유 관계를 구조와 함께 해석합니다.
- **직접 대응 없음:** 엔티티 유형, 국가 정보 가용성, 미관측 통화 등은 특정 패턴이 아니라 판정의 문맥을 제공합니다.

| 패턴 | 쉬운 설명 | 이 후보 모델에서 기대하는 단서 | 해석의 한계 |
|---|---|---|---|
| FAN-IN | 여러 계좌 → 한 계좌로 집금 | `log_in_neighbors`, `log_in_count`, `receiver_count_1h` | 다수 상대인지 확인해야 하며 정상 집금도 가능 |
| FAN-OUT | 한 계좌 → 여러 계좌로 분산 | `log_out_neighbors`, `log_out_count`, `sender_count_1h` | 반복 송금 횟수만으로 다수 상대 분산을 확정할 수 없음 |
| GATHER-SCATTER | 집금한 뒤 여러 곳으로 분산 | 같은 노드의 입출금 상대 수·활동량과 GNN 연결 | 일별 집계만으로 집금 후 분산의 순서나 동일 자금 여부를 입증하지 못함 |
| SCATTER-GATHER | 분산한 자금이 다시 모이는 형태 | 출발 계좌의 송금 상대 수, 도착 계좌의 수취 상대 수, 중간 연결 | 경로와 금액 보존을 직접 추적하는 피처는 없음 |
| CYCLE | 여러 계좌를 거쳐 돌아오는 순환 | GNN 연결, `reverse_history_count`, 상호 거래 피처 | 직접 왕복은 긴 순환과 다름. A→B→C→A는 역방향 거래가 없을 수 있음 |
| BIPARTITE | 두 계좌 집단 사이의 다대다 연결 | 양측 상대 수와 엔티티 입출금 다양성, GNN 연결 | 높은 연결 수만으로 집단 간 공통 연결 구조를 확정하지 못함 |
| STACK | 여러 단계의 계좌 이동·연결 | GNN 국소 연결과 활동량·시간·소유 관계 | 단순 사슬로 단정하지 않으며 실제 에피소드 구조 확인 필요 |
| RANDOM | 고정된 집금·분산 형태로 설명하기 어려운 경로 | 구조·시간·금액 단서의 조합 | 직접 대응하는 전용 피처 없음 |

2-hop과 최근 유입 거래 10개, 최대 30일 문맥은 긴 경로나 넓은 분산 구조 전체를 보존하지 않을 수 있습니다. 후보에서 제외한 `net_count_ratio`는 아래 40개 입력 표에 포함하지 않았습니다.

## 노드 피처 22개 — 계좌의 최근 활동

노드 통계는 판정일 D−29일부터 D일까지 전체 거래로 계산합니다. 최근 유입 거래 10개로 그래프를 줄이기 **전**의 집계입니다. 횟수·다양성은 ln(1+n), 평균은 통화 내 상대 금액, 비율은 해당 분모 기준입니다. 자금세탁 패턴 연결은 설계 가설이며 전용 패턴 검출 성능의 입증이 아닙니다.

| 6 | `receiver_gap_minutes` | 수신 계좌의 직전 수취 이후 간격 | 수취 활동의 속도 | FAN-IN·SCATTER-GATHER의 집금 단계가 빠르게 진행될 때 보조 단서 |
| 7 | `receiver_count_1h` | 수신 계좌의 이전 60분~1분 수취 횟수 | 수취 집중도 | FAN-IN·SCATTER-GATHER의 단시간 다수 수취 단서. 상대 계좌 수와 결합 필요 |
| 8 | `paid_currency_z` | 송금 통화 내 상대 금액 점수 | 해당 통화의 일반적인 거래 대비 금액 규모 | 모든 유형의 상대 금액 단서. 반복 횟수와 결합해 소액 반복 후보를 볼 수 있으나 금액 보존·신고 기준 회피를 직접 검출하지 않음 |
| 9 | `pair_history_count` | 당일 0시 이전까지 해당 방향 계좌 쌍의 누적 거래 횟수 | 하루 시작 시점의 기존 관계 | 기존 관계의 반복 이체 단서. 신규 경로를 사용하는 STACK·CYCLE을 이 값만으로 구분할 수 없음 |
| 10 | `reverse_history_count` | 당일 0시 이전까지 반대 방향 계좌 쌍의 누적 거래 횟수 | 역방향·왕복 거래 이력 | 두 계좌 사이의 왕복 거래 단서. CYCLE 관련 보조 후보이나 A→B→C→A처럼 긴 순환에는 직접 역방향 거래가 없어도 됨 |
| 11 | `pair_age_at_day_start` | 당일 0시에서 해당 방향 마지막 거래까지 경과 시간 | 기존 거래 관계의 최근성 | 한동안 거래가 없던 계좌 쌍의 재거래 단서. 특정 패턴 전용 피처는 아님 |
| 12 | `same_entity` | 송신·수신 계좌의 엔티티 ID가 같은지 | 동일 소유 엔티티 내부 이동 | 동일 소유자의 여러 계좌를 통한 이동 단서. STACK·CYCLE 등과 결합 가능하지만 정상 내부 이체에도 나타남 |
| 13 | `same_known_country` | 양쪽 국가를 알고 있으며 같은지 | 알려진 국가 간 관계 | 국가 간 이동의 보조 정보. 양쪽 국가가 알려졌을 때만 0을 국가 불일치로 해석하며, 특정 패턴을 직접 식별하지 않음 |
| 14 | `both_countries_known` | 양쪽 국가가 모두 알려져 있는지 | 국가 불일치와 국가 미상을 구분 | 직접 대응 없음. 국가 미상과 국가 불일치를 구분하는 정보 가용성 피처 |
| 15 | `same_currency` | 송금 통화와 수취 통화가 같은지 | 통화 변경 거래 구분 | 통화가 바뀌는 거래의 보조 단서. STACK·CYCLE 등의 경로 해석에 활용 가능하나 환전 자체가 패턴 정답은 아님 |
| 16 | `is_self_transfer` | 송신·수신 노드가 같은지 | 동일 계좌 자기 이체 구분 | 자기 이체 식별. 여러 계좌를 거쳐 돌아오는 CYCLE과는 다른 구조 |
| 17 | `paid_currency_unseen` | 송금 통화가 기준 산출 기간에 없었는지 | 송금 금액 정규화 기준 부재 표시 | 직접 대응 없음. 송금 금액 정규화 기준이 없는 거래임을 알리는 보조 피처 |
| 18 | `received_currency_unseen` | 수취 통화가 기준 산출 기간에 없었는지 | 수취 금액 정규화 기준 부재 표시 | 직접 대응 없음. 수취 금액 정규화 기준이 없는 거래임을 알리는 보조 피처 |

## 중복처럼 보이지만 구분해서 보존할 정보

- 거래 수와 거래 상대 수: 같은 상대에게 반복 송금한 정도와 여러 상대에게 분산한 정도를 구분합니다.
- `pair_prior_count`와 `pair_history_count`: 현재 분 이전 누적과 당일 00시 이전 누적으로 당일 활동 포함 여부가 다릅니다.
- `log_self_count`와 `is_self_transfer`: 전자는 계좌의 기간 내 자기 거래 횟수, 후자는 이번 거래가 자기 거래인지 여부입니다.
- `same_entity`와 `is_self_transfer`: 같은 엔티티의 서로 다른 계좌도 존재합니다.
- `log_reciprocal_neighbors`와 `reciprocity_ratio`: 왕복 관계의 수와 규모 대비 비율입니다. 비율의 분모는 출금 이웃 수+입금 이웃 수이고 최댓값은 0.5입니다.
- `same_known_country`와 `both_countries_known`: 국가 불일치와 국가 정보 미상을 구분합니다.
- 엣지 금액 z와 노드 평균·이상치 비율: 개별 거래와 계좌 기간 내 행동 수준을 구분합니다. `received_currency_z`는 별도 엣지 입력은 아니지만 노드 수취 집계 계산에는 필요합니다.

## 시간 범위·입력 계약

- 일 마감 모델: D+1일 00시 미만 데이터까지 사용. 같은 날 이후 거래가 문맥에 들어가므로 거래 순간 실시간 판정과 구분합니다. 원본 시간대는 확정하지 않았습니다.
- 쌍·송신·수신의 직전 횟수/간격은 같은 분 제외, 1시간 횟수는 이전 60분~1분입니다. 쌍별 일 시작 이력은 D 이전 전체 관측 이력으로 30일 창에 제한되지 않습니다.
- 통화 정규화는 8/1~7 기준으로 고정, BTC 포함, 금액 z는 −8~8 제한. 신규 통화 z=0과 별도 플래그를 사용합니다.
- 원본의 두 Account는 송신·수신으로 보존. 정제 데이터 179,702,079건과 이진 정답 Is Laundering은 변경하지 않습니다.
- X 입력에 정답·패턴 라벨·원본 계좌 ID의 수치값을 넣지 않습니다. 계좌 ID는 그래프 연결에 사용합니다.
- JSON에 저장한 순서를 모델 체크포인트와 정확히 맞춥니다. 기존 23열 캐시에서 노드 컬럼을 이름으로 투영하여 22열을 만듭니다. 원본·캐시 열 삭제는 필요하지 않습니다.
- 후보 모델은 22개 노드 입력을 기대하므로 기존 23열 모델 로더에 그대로 연결하면 안 됩니다. 후보의 ablation_schema와 decision_rule을 함께 사용해야 합니다.
