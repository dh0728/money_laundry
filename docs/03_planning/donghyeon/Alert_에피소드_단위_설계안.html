AML 서비스 재검토: Alert 에피소드 단위 설계안

거래별 모델 판정과 AML 담당자의 검토 업무를 분리하고, IBM AML 데이터에서 시간·계좌 연결을 이용해 위험 에피소드 Alert를 생성하는 방법을 정리한다.

0. 문서의 목적과 결론

현재 서비스는 거래별 이상 여부를 판정하는 기술 흐름을 중심으로 설계되어 자연스럽게 이상 거래 1건 → Alert 1건 구조가 만들어졌다. 그러나 실제 AML 서비스에서 모델 판정 단위와 담당자의 업무 단위는 같지 않아야 한다.

한 문장 결론: 거래별 모델 판정 결과는 그대로 보존하되, 담당자에게 전달하는 Alert는 시간과 계좌 관계로 연결된 위험 행동 단위로 만든다.

1. SAS·Lucinity 조사에서 확인한 공통점

  1. 업무는 단순 대시보드보다 Queue 또는 Workboard에서 시작한다.
  2. Alert와 Case는 서로 다른 객체다.
  3. 담당자의 Claim, Assign, Release가 명시된다.
  4. 고객·계좌·거래·과거 사건을 하나의 맥락에서 확인한다.
  5. 체크리스트와 Narrative로 조사 누락을 방지한다.
  6. 관리자는 SLA, 업무량과 QA를 관리한다.
  7. 모든 결정과 상태 변경이 감사 이력으로 남는다.
Alert는 시스템이 발견해 L1 담당자에게 전달한 검토 대상이고, Case는 담당자가 심층 조사가 필요하다고 판단해 여러 Alert·거래·계좌·증거를 묶은 조사 사건이다.

2. 현재 기획에서 발견한 핵심 문제

현재 기획의 1단계 양성 거래 1건 → Alert 1건 구조는 모델의 판정 단위와 담당자의 업무 단위를 동일하게 취급한다. 그러나 자금세탁 위험은 여러 거래의 시간적 순서, 반복, 계좌 관계와 자금 흐름에서 드러나는 경우가 많다.

모델·처리 파이프라인 관점: 거래 한 건씩 판정
서비스·조사 업무 관점: 여러 거래의 연결 행동을 판단
핵심: 거래별 모델 결과는 원천 증거로 보존하되, 담당자가 처리하는 Alert는 관련 위험 신호를 묶은 위험 에피소드여야 한다.

거래 1건당 Alert가 서비스적으로 부적절한 이유

  1. 자금세탁의 의심 근거는 거래 한 건만으로 완성되지 않는다.
    자금세탁은 거래 한 건의 금액만 보고 판단하기 어렵다. 여러 거래의 순서, 횟수, 계좌 관계와 발생 기간을 함께 봐야 위험 행동을 이해할 수 있다. 각각은 평범해 보여도 짧은 시간 안에 분산된 뒤 특정 계좌로 다시 모이면 하나의 의심스러운 자금 흐름이 될 수 있다.
  2. 하나의 의심행위가 여러 업무로 중복 생성된다.
    한 고객이 24시간 동안 의심 거래 20건을 발생시키면 최대 20개의 Alert가 생성된다. 그러나 담당자가 판단해야 할 질문은 “이 고객의 최근 반복·분산 거래 행동이 의심스러운가?”라는 하나의 질문일 수 있다.
  3. 같은 판단을 반복하면서 일관성이 깨질 수 있다.
    각 Alert마다 Claim, 상태 변경, 종결 사유와 감사 이력을 남겨야 한다. 같은 사건의 거래가 다른 담당자에게 배정되면 한 명은 정상 종결하고 다른 담당자는 분석팀으로 이관하는 등 대표 결론이 불명확해질 수 있다.
  4. Alert Queue의 업무량이 실제 위험량과 달라진다.
    거래량이 많은 고객은 같은 의심행위로 Alert를 많이 발생시키고, 거래 수가 적은 고위험 고객은 중요한 위험이 있어도 적은 Alert만 발생시킬 수 있다. 따라서 Alert 100건 = 고객 3명의 반복 거래일 수도 있다.
  5. 운영 및 성과 지표가 왜곡된다.
    Alert 적체량, 평균 처리시간, Alert-to-Case 전환율, 담당자 처리 실적, 오탐 종결률과 SLA 위반 건수 등이 실제 위험 사건이 아니라 거래 건수의 영향을 크게 받게 된다.
  6. 그래프 분석의 핵심 결과를 담을 자리가 애매해진다.
    우리 서비스의 핵심은 수상한 거래 한 건이 아니라 연결된 여러 거래에서 발견된 수상한 행동이다. Alert를 거래 단위로 먼저 확정하면 연결 계좌 집단, 허브 계좌, 연속 자금 흐름, 순환·분산 패턴과 동일 에피소드의 거래 목록은 이미 생성된 Alert에 붙는 부가정보로 밀려난다.
결과: 서비스의 차별점인 그래프 분석이 Alert의 생성 근거가 아니라 보조 화면이 될 수 있다. 화면에서 거래를 묶어 보여주는 것만으로는 각각의 Alert 상태와 종결 업무가 남기 때문에 근본적인 중복을 해결할 수 없다.
거래 1 → Alert #1 ─┐
거래 2 → Alert #2 ─┼→ 동일 그래프 결과를 사후 첨부
거래 3 → Alert #3 ─┤
거래 4 → Alert #4 ─┘

쉬운 예시

A → B : 300만 원
A → C : 300만 원
B → D : 290만 원
C → D : 290만 원

거래별 방식은 Alert 네 개를 만들지만, 그래프 관점에서는 A에서 분산된 자금이 D로 재집중한 하나의 행동이다. 따라서 하나의 Alert에 관련 거래 4건, 계좌 A·B·C·D, 출발 계좌 A, 재집중 계좌 D와 위험 근거를 담는 편이 담당자의 판단 단위에 맞다.

모든 Alert가 여러 거래를 포함해야 하는 것은 아니다. 연결 관계가 없더라도 단건 위험도가 매우 높으면 단건 Alert가 될 수 있다. 문제는 모든 양성 거래를 무조건 독립 Alert로 만드는 규칙이다.

4. IBM AML 데이터에서 사용할 정보

그럼 에피소드 단위 Alert를 어떻게 생성하는가?

IBM AML 데이터의 Patterns.txt에서 attempt 하나는 여러 거래로 구성된 하나의 자금세탁 시도 또는 사건을 나타낸다. 즉, 데이터셋 자체도 자금세탁 사건 하나 = 거래 한 건이 아니라 하나의 attempt에 여러 거래와 계좌가 포함되는 구조를 가지고 있다.

이 구조를 참고하면 거래별 모델 결과를 다음 기준으로 묶어 위험 에피소드 후보를 만들 수 있다.

  계좌 연결
+ 발생 시간
+ 거래 방향
+ 모델 위험점수
+ 그래프 패턴
= 위험 에피소드

다만 현재 데이터셋에는 실제 고객 프로필, KYC·CDD 위험등급, 직업·사업 유형, 정상적인 평소 거래 패턴, 자금 출처와 거래 목적이 충분하지 않다. 따라서 고객 중심 에피소드보다 계좌·Entity·시간·거래 연결 관계 중심의 에피소드를 만드는 것이 현실적이다.

데이터 누수 주의: Patterns.txt의 attempt ID나 Is Laundering 값으로 거래를 직접 묶으면 정답을 미리 사용하는 것이 된다. attempt는 개념을 이해하고 생성 결과를 평가할 때만 사용한다. 실제 생성 로직은 거래 시각, 계좌 관계, 거래 방향과 모델 위험점수만 사용해야 한다.
  • 거래 시각, 송금·수취 계좌, 금액, 통화와 결제 방식
  • 계좌의 Entity ID와 거래별 모델 위험점수
  • 계좌 사이의 방향성 연결 관계
계좌번호 단독에는 충돌이 있으므로 account_id = (Bank ID, Account Number) 복합키를 사용해야 한다.

5. 시간 창과 거래 그래프

시간 창(Time Window)은 하나의 위험 행동으로 묶을 거래를 찾기 위해 조회하는 시간 범위다. 8월 14일 10시에 고위험 거래가 발견되고 시간 창이 24시간이면 8월 13일 10시부터 8월 14일 10시까지의 관련 거래를 확인한다.

10:00 A → B
10:15 B → C
10:40 C → D

위 거래는 짧은 시간 안에 연속됐으므로 하나의 자금 흐름일 가능성이 있다. 현재 서비스에는 고위험 거래 시점을 기준으로 과거 일정 시간을 조회하는 슬라이딩 시간 창이 적합하다. 24시간은 확정값이 아니라 1·6·12·24·48시간 후보를 비교해야 한다.

거래 그래프에서는 계좌가 점(Node), 거래가 방향이 있는 선(Edge)이 된다. Connected Component(연결요소)는 거래선을 따라 서로 연결되는 계좌와 거래의 묶음이다.

연결요소 1: A → B → C
연결요소 2: D → E → F
연결요소 3: G → H
주의: 연결요소는 최종 Alert가 아니라 후보 묶음이다. 대형 허브 때문에 무관한 거래가 합쳐지지 않도록 1~2 hop, 시간 간격, 최대 거래·계좌 수와 허브 확장 제한을 적용해야 한다.

6. 에피소드 Alert 생성 절차

① Seed 거래 선정

model_score ≥ 0.80 → 에피소드 탐색 시작

② 관련 거래 확장

Seed의 송금·수취 계좌 주변을 시간 창 안에서 1-hop, 필요 시 2-hop까지 조회한다. 주변 거래는 모두 Seed 임곗값을 넘지 않아도 된다. 자금 경로를 완성하는 중간 거래를 제외하면 Cycle이나 재집중 흐름이 끊길 수 있기 때문이다.

Seed 거래: score ≥ 0.80
주변 거래: score ≥ 0.50 또는 경로 연결에 필요한 거래
시간 창: 24시간 후보
확장: 기본 1-hop, 최대 2-hop

③ 에피소드 후보 생성

  • 계좌 또는 Entity 공유
  • 시간 창 안에 존재
  • Seed에서 1~2 hop 이내
  • 거래 방향과 순서가 연속 행동으로 설명 가능

④ Alert 생성 또는 기존 Alert 갱신

동일 중심 계좌 또는 Entity
AND 동일·유사 위험 유형
AND 마지막 거래 이후 허용 시간 이내
AND Alert 상태가 NEW 또는 IN_REVIEW
→ 새 Alert 대신 기존 Alert 갱신

7. 패턴의 역할과 Patterns 밖 거래

HI-Small에는 자금세탁 거래 5,177건이 있으나 Patterns에 포함된 거래는 3,209건이고, 1,968건은 Patterns 밖에 있다. 따라서 알려진 패턴 발견을 Alert 생성의 필수조건으로 삼으면 안 된다.

원칙: 시간과 계좌 관계가 에피소드를 만들고, 알려진 패턴은 에피소드를 설명하고 위험점수를 보강한다.
Alert 유형생성 조건
PATTERN_EPISODEFAN-IN, FAN-OUT, CYCLE 등 알려진 패턴 발견
GENERAL_EPISODE패턴명은 없지만 시간·계좌·Entity로 연결된 위험 거래 집합
SINGLE_HIGH_RISK연결 거래가 없지만 단건 위험도가 매우 높은 거래

8. 패턴별 초기 후보 기준

패턴초기 후보 조건
FAN-OUT동일 송금 계좌, 24시간 이내, 고유 수취 계좌 3개 이상, 거래 3건 이상
FAN-IN동일 수취 계좌, 24시간 이내, 고유 송금 계좌 3개 이상, 거래 3건 이상
CYCLE서로 다른 계좌 3개 이상, 방향성 순환 경로 길이 3~6, 24시간 이내
SCATTER-GATHER하나의 출발 계좌에서 3개 이상으로 분산 후 하나의 계좌로 재집중
GATHER-SCATTER3개 이상 송금 계좌에서 집중 후 3개 이상 수취 계좌로 분산

BIPARTITE와 STACK은 다대다·다계층 판별이 필요하므로 MVP 이후 확장하는 것이 현실적이다. 패턴이 없더라도 동일 계좌나 Entity를 공유하고 시간 창 안에 있는 위험 거래들이 집계 임곗값을 넘으면 GENERAL_EPISODE가 될 수 있다.

9. 에피소드 위험점수 예시

episode_score =
  0.40 × 최고 거래 위험점수
+ 0.20 × 상위 3개 거래 평균점수
+ 0.25 × 패턴 명확도 또는 연결 강도
+ 0.15 × 금액·거래 속도 점수
episode_score ≥ 0.70
AND 관련 거래 ≥ 3
AND 관련 계좌 ≥ 3
→ 에피소드 Alert

transaction_score ≥ 0.95 AND 연결 거래 없음
→ 고위험 단건 Alert

가중치와 임곗값은 확정 정책이 아니라 데이터 검증을 위한 초기 가설이다.

10. 평가 방법과 한계

Patterns.txt의 attempt ID는 모델 입력에 사용하지 않고 에피소드 평가 정답으로만 사용한다.

지표의미
Episode Recall실제 attempt 중 Alert로 탐지된 비율
Transaction Coverage실제 에피소드의 거래를 얼마나 포함했는가
Fragmentation Rate한 사건을 여러 Alert로 잘못 나눈 비율
Merge Rate서로 다른 사건을 한 Alert로 잘못 합친 비율
Alerts per Attempt실제 사건 하나당 생성 Alert 수
Alert Volume시간 또는 일 단위 Alert 생성량

Patterns 밖 양성 거래에는 attempt ID가 없어 실제 사건 경계를 알 수 없다. 이 영역은 거래 탐지 성능과 시스템이 제시한 시간·계좌 연결 근거를 평가하되, 실제 사건과 정확히 일치한다고 주장할 수 없다.

11. MVP 초기안

시간 창: 슬라이딩 24시간
종료: 마지막 관련 거래 후 24시간
Seed: model_score ≥ 0.80
확장: 기본 1-hop, 최대 2-hop
주변 거래: score ≥ 0.50 또는 경로 연결에 필요
최소 거래: 3건
최소 계좌: 3개
우선 패턴: FAN-IN, FAN-OUT, CYCLE, SCATTER-GATHER
Alert 생성: episode_score ≥ 0.70
긴급 단건: transaction_score ≥ 0.95

시간 창 1h / 6h / 12h / 24h / 48h, Seed 임곗값 0.70 / 0.80 / 0.90, 최소 계좌 수 3 / 4 / 5 조합을 실험하고 Episode Recall, Fragmentation, Merge와 Alert Volume을 비교해 최종값을 정해야 한다.

12. 조원에게 설명하는 순서

  1. 현재 문제: 거래별 모델 결과를 곧바로 Alert로 만들고 있다.
  2. 문제의 영향: 하나의 행동이 여러 업무로 쪼개지고 판단과 운영 지표가 왜곡된다.
  3. 수정 원칙: 거래별 결과는 Risk Signal로 보존하고 연결된 신호를 에피소드 Alert로 만든다.
  4. 묶는 방법: 시간 창 안에서 같은 계좌·Entity와 1~2 hop으로 연결된 거래를 찾는다.
  5. 패턴이 없는 경우: 패턴은 필수조건이 아니며 GENERAL_EPISODE로 처리한다.
  6. 단건 예외: 위험점수가 매우 높은 단건은 즉시 Alert를 만들 수 있다.
  7. 수치 검증: 24시간과 0.80 등의 값은 attempt 정답으로 실험한 뒤 결정한다.
가장 짧은 설명: 모델은 거래를 한 건씩 판정해도 된다. 그 결과를 위험 신호로 저장하고, 일정 시간 안에 같은 계좌나 연결 계좌에서 발생한 신호를 묶어 담당자가 한 번에 판단할 에피소드 Alert로 만든다. 패턴은 필수조건이 아니라 설명과 우선순위를 강화하는 근거다.

13. 결론

최종 방향: 현재의 거래 수집과 거래별 추론 구조는 유지한다. 그 위에 Risk Signal → Episode Aggregation → Alert 계층을 추가하여 시간·계좌·Entity 연결로 위험 행동을 묶고, 패턴은 설명과 점수 보강에 사용한다.
