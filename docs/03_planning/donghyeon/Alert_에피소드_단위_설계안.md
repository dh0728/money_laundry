# AML 서비스 재검토: Alert 에피소드 단위 설계안

## 0. 이 문서에서 설명하려는 것

현재 우리 서비스는 거래를 수집하고 모델이 거래별 이상 여부를 판정하는 기술 흐름을 중심으로 설계되어 있다. 이 과정에서 자연스럽게 `이상 거래 1건 → Alert 1건`이라는 구조가 만들어졌다.

하지만 SAS와 Lucinity 같은 실제 AML 솔루션의 화면과 업무 흐름을 조사한 결과, **모델이 판정하는 단위와 담당자가 처리하는 업무 단위는 같지 않아야 한다**는 점을 확인했다.

이 문서는 다음 질문에 답하기 위해 작성했다.

1. 실제 AML 솔루션은 어떤 업무 구조를 사용하는가?
2. 거래 1건당 Alert 1건 방식은 왜 문제가 되는가?
3. 에피소드 단위 Alert란 무엇인가?
4. 현재 IBM AML 데이터로 에피소드를 어떻게 만들 수 있는가?
5. 패턴 정보가 없는 거래는 어떻게 처리하는가?
6. 시간 창과 거래 그래프는 무엇이며 실제 구현에 어떻게 사용하는가?
7. 현재 프로젝트에서 우선 적용할 수 있는 MVP 기준은 무엇인가?

> 한 문장 결론: 거래별 모델 판정 결과는 그대로 보존하되, 담당자에게 전달되는 Alert는 시간과 계좌 관계로 연결된 위험 행동 단위로 만들어야 한다.

---

## 1. 실제 AML 솔루션 조사에서 확인한 공통점

인터페이스와 업무 흐름을 확인할 수 있는 SAS와 Lucinity를 조사했을 때 다음 공통점을 확인했다.

1. 업무는 단순 현황 대시보드보다 `Queue` 또는 `Workboard`에서 시작한다.
2. `Alert`와 `Case`는 서로 다른 객체다.
3. 담당자의 `Claim`, `Assign`, `Release`가 명시된다.
4. 고객·계좌·거래·과거 사건을 하나의 맥락에서 확인한다.
5. 조사 누락을 방지하기 위한 체크리스트와 Narrative가 있다.
6. 관리자는 SLA, 업무량과 QA를 관리한다.
7. 모든 결정과 상태 변경이 감사 이력으로 남는다.

이 공통점은 AML 서비스가 단순한 이상거래 탐지 화면이 아니라, **발생한 위험 신호를 사람이 배정받아 검토하고 조사하는 업무 시스템**이라는 사실을 보여준다.

### Alert와 Case의 차이

```text
Alert
= 시스템이 발견하여 L1 담당자에게 전달한 검토 대상

Case
= 담당자가 심층 조사가 필요하다고 판단하여
  여러 Alert·거래·계좌·증거를 묶은 조사 사건
```

따라서 `거래 → 모델 판정 → Alert → 담당자 검토 → Case 이관` 사이의 객체와 책임을 명확히 구분해야 한다.

## 2. 현재 기획에서 발견한 핵심 문제

현재 기획에는 1단계 모델이 거래 한 건을 양성으로 판정하면 Alert 한 건을 생성하는 구조가 포함되어 있다.

```text
거래 1건
→ 모델 추론 결과 1건
→ 양성 판정
→ Alert 1건
```

그러나 이 구조는 **모델의 판정 단위**와 **담당자의 업무 단위**를 동일하게 취급한다. 자금세탁 위험은 거래 한 건보다 여러 거래의 시간적 순서, 반복, 계좌 관계와 자금 흐름에서 드러나는 경우가 많다.

따라서 거래별 모델 결과는 원천 증거로 보존하되, 담당자가 처리하는 Alert는 관련된 위험 신호를 묶은 **위험 에피소드**로 정의하는 것이 적절하다.

---

현재 아키텍처에는 `1단계 양성 = Alert 1건`, 거래 단위 Alert 원천 보존, 조회 화면에서 묶어 보기라는 방향이 포함되어 있다. 반면 데이터 분석과 유스케이스는 반복 위험 계좌, 연결 계좌 그룹과 여러 Alert를 묶은 사건 조사를 강조한다.

즉, 현재 기획 안에는 다음 충돌이 있다.

```text
모델·처리 파이프라인 관점: 거래 한 건씩 판정
서비스·조사 업무 관점: 여러 거래의 연결 행동을 판단
```

거래별 추론 자체는 유지해도 된다. 수정해야 하는 부분은 거래별 양성 결과를 담당자의 최종 업무인 Alert와 바로 동일시하는 것이다.

## 3. 거래 1건당 Alert가 부적절한 이유

### 3.1 자금세탁의 의심 근거는 거래 한 건만으로 완성되지 않는다

자금세탁은 거래 한 건의 금액만 보고 판단하기 어렵다. 여러 거래의 **순서, 횟수, 계좌 관계와 발생 기간**을 함께 봐야 위험 행동을 이해할 수 있다.

예를 들어 각각의 송금은 평범해 보여도 짧은 시간 안에 여러 계좌로 분산된 뒤 특정 계좌로 다시 모이면 하나의 의심스러운 자금 흐름이 된다. 거래를 한 건씩 Alert로 분리하면 이러한 전체 맥락을 한 번에 판단하기 어렵다.

### 3.2 하나의 의심행위가 여러 업무로 중복 생성된다

한 고객 또는 계좌가 짧은 시간 동안 20건의 의심 거래를 발생시키면 현재 방식에서는 최대 20개의 Alert가 생성된다. 하지만 담당자가 판단해야 할 핵심 질문은 다음 하나일 수 있다.

> 이 계좌가 최근 일정 시간 동안 보인 반복·분산 거래 행동이 의심스러운가?

거래별 Alert를 사용하면 담당자는 같은 위험 행동에 대해 Claim, 상태 변경, 종결 사유 입력과 감사 기록을 반복해야 한다.

### 3.3 동일 위험 에피소드에 대한 판단을 반복하면서 일관성이 깨질 수 있다

거래별 Alert마다 Claim, 상태 변경, 종결 사유와 감사 이력을 남겨야 하므로 담당자는 사실상 같은 위험 에피소드에 대해 동일한 판단을 반복한다.

같은 사건에 포함된 거래들이 서로 다른 담당자에게 배정되면 다음과 같이 결론이 달라질 수도 있다.

```text
담당자 A: 정상 거래로 종결
담당자 B: 분석팀으로 이관
담당자 C: 중복 Alert로 종결
```

이 경우 하나의 위험 행동에 대한 대표 결론이 무엇인지 불명확해지고, 담당자별 판단 일관성과 책임 추적도 어려워진다.

### 3.4 Alert Queue의 업무량이 실제 위험량과 달라진다

거래량이 많은 고객이나 계좌는 동일한 의심행위라도 Alert를 많이 발생시키고, 거래 수가 적은 고위험 고객은 더 중요한 위험을 가지고 있어도 적은 Alert만 발생시킬 수 있다.

따라서 Queue에 Alert 100건이 표시되더라도 실제로는 다음과 같은 상황일 수 있다.

```text
Alert 100건 = 고객 3명의 반복 거래
```

즉, Alert 건수만으로 실제 위험 사건 수나 업무 난이도를 판단할 수 없게 된다. 동일 계좌의 비슷한 거래가 Queue 상단을 반복해서 차지하면 다른 계좌의 중요한 위험 신호가 뒤로 밀릴 수도 있다.

### 3.5 운영 및 성과 지표가 왜곡된다

Alert 건수가 실제 위험 사건 수와 일치하지 않으면 이를 기반으로 계산하는 여러 운영 지표도 함께 왜곡된다.

- Alert 적체량
- 평균·최장 처리시간
- Alert에서 Case로 전환된 비율
- 담당자별 처리 건수와 실적
- 오탐 종결률
- SLA 위반 건수

예를 들어 담당자가 같은 고객의 반복 거래 Alert 20건을 종결했다고 해서 서로 다른 위험 사건 20개를 처리했다고 평가할 수는 없다.

### 3.6 그래프 분석의 핵심 결과를 담을 자리가 애매해진다

현재 데이터 분석 구조는 다음과 같다.

```text
1단계: 거래 단위 이상 여부 판정
2단계: 연결 계좌와 거래 그룹 분석
```

1단계 양성 거래마다 Alert를 먼저 확정하면, 2단계에서 여러 거래가 하나의 분산·재집중 또는 순환 행동임을 발견해도 이미 생성된 여러 Alert에 같은 그래프를 반복 첨부해야 한다.

```text
거래 1 → Alert #1 ─┐
거래 2 → Alert #2 ─┼→ 동일 그래프 결과를 사후 첨부
거래 3 → Alert #3 ─┤
거래 4 → Alert #4 ─┘
```

이 경우 그래프 분석은 Alert 생성 근거가 아니라 참고 화면으로 밀려난다.

우리 서비스의 핵심 분석 결과는 단순한 `수상한 거래 한 건`이 아니라 **서로 연결된 여러 거래에서 발견된 수상한 행동**이다. Alert를 1단계에서 거래 단위로 너무 일찍 확정하면 2단계 그래프 분석에서 찾은 다음 정보를 어느 Alert의 핵심 내용으로 넣어야 하는지가 애매해진다.

- 연결 계좌 집단
- 허브 계좌
- 연속 자금 흐름
- 순환·분산·재집중 패턴
- 동일 위험 에피소드에 속한 거래 목록

결국 서비스의 차별점인 그래프 분석이 Alert의 중심 근거가 아니라 이미 만들어진 거래별 Alert에 붙는 부가정보나 보조 화면으로 밀려날 수 있다.

### 예시로 이해하기

```text
A → B : 300만 원
A → C : 300만 원
B → D : 290만 원
C → D : 290만 원
```

거래별 Alert 방식은 4개의 업무를 만든다. 하지만 그래프 관점에서는 A에서 자금을 분산한 뒤 D로 재집중한 하나의 행동이다.

```text
권장 Alert #1
- 위험 유형: 분산 후 재집중
- 관련 거래: 4건
- 관련 계좌: A, B, C, D
- 출발 계좌: A
- 재집중 계좌: D
- 자금 흐름과 모델 점수 포함
```

## 4. 권장 객체 구분

| 객체 | 의미 |
|---|---|
| `Transaction` | 실제로 발생한 개별 금융 거래 |
| `Model Inference Result` | 거래별 모델 위험점수와 판단 근거 |
| `Risk Signal` | Alert로 확정하기 전의 개별 위험 신호 또는 후보 |
| `Alert` | 관련 위험 신호와 거래를 묶어 L1 담당자에게 전달하는 검토 단위 |
| `Case` | 심층 조사가 필요한 Alert, 계좌, 거래와 추가 증거를 묶은 조사 단위 |

권장 흐름은 다음과 같다.

```text
거래 수집
→ 거래별 모델 추론
→ Risk Signal 저장
→ 시간·계좌 관계를 이용한 에피소드 집계
→ Alert 생성 또는 기존 열린 Alert 갱신
→ 담당자 검토
→ 필요 시 Case 이관
```

모든 Alert가 반드시 여러 거래를 포함해야 하는 것은 아니다. 연결 관계가 없더라도 단건 위험도가 매우 높은 거래는 예외적으로 단건 Alert가 될 수 있다. 문제는 **모든 양성 거래를 무조건 독립 Alert로 만드는 고정 규칙**이다.

## 5. IBM AML 데이터에서 사용할 수 있는 정보

### 그럼 에피소드 단위 Alert를 어떻게 생성하는가?

IBM AML 데이터의 `Patterns.txt`에서 attempt 하나는 실제로 여러 거래로 구성된 하나의 자금세탁 시도 또는 사건을 나타낸다. 즉, 데이터셋 자체도 `자금세탁 사건 하나 = 거래 한 건`이 아니라 **하나의 attempt에 여러 거래와 계좌가 포함되는 구조**를 가지고 있다.

이 구조를 참고하면 거래별 모델 결과를 다음 기준으로 묶어 위험 에피소드 후보를 만들 수 있다.

```diff
  계좌 연결
+ 발생 시간
+ 거래 방향
+ 모델 위험점수
+ 그래프 패턴
= 위험 에피소드
```

다만 현재 데이터셋에는 실제 금융기관이 보유하는 다음 정보가 충분하지 않다.

- 실제 고객 프로필
- KYC·CDD 위험등급
- 직업과 사업 유형
- 정상적인 평소 거래 패턴
- 자금 출처 및 거래 목적

따라서 현재 프로젝트에서는 고객 중심 에피소드보다 **계좌·Entity·시간·거래 연결 관계를 중심으로 에피소드를 생성**하는 것이 현실적이다.

> 중요: `Patterns.txt`의 attempt ID나 `Is Laundering` 값으로 거래를 직접 묶으면 정답을 미리 사용하는 데이터 누수가 발생한다. attempt는 에피소드의 개념을 이해하고 생성 결과를 평가할 때만 사용한다. 실제 생성 로직은 거래 시각, 계좌 관계, 거래 방향과 모델이 출력한 위험점수만 사용해야 한다.

현재 데이터셋에는 다음 정보가 있으므로 고객 KYC 정보가 부족하더라도 계좌 기반 에피소드 생성이 가능하다.

- 거래 시각 `Timestamp`
- 송금 계좌 `(From Bank, From Account)`
- 수취 계좌 `(To Bank, To Account)`
- 송금·수취 금액과 통화
- 결제 방식
- 계좌의 `Entity ID`
- 거래별 모델 위험점수
- 계좌 사이의 방향성 연결 관계

계좌번호 단독으로는 충돌이 존재하므로 계좌 식별자는 반드시 다음 복합키를 사용해야 한다.

```text
account_id = (Bank ID, Account Number)
```

## 6. 시간 창이란 무엇인가

**시간 창(Time Window)**은 하나의 위험 행동으로 묶을 거래를 찾기 위해 조회하는 시간 범위다.

예를 들어 시간 창이 24시간이고 8월 14일 10시에 고위험 거래가 발견되었다면 다음 범위의 관련 거래를 확인한다.

```text
조회 범위: 8월 13일 10시 ~ 8월 14일 10시
```

시간 제한이 없으면 같은 계좌를 거쳤다는 이유만으로 며칠 또는 몇 달 떨어진 거래가 하나의 사건으로 합쳐질 수 있다.

```text
10:00 A → B
10:15 B → C
10:40 C → D
```

위 거래는 짧은 시간 안에 연속됐으므로 하나의 자금 이동일 가능성이 있다. 반면 13일 이상 떨어진 거래는 계좌가 연결됐더라도 같은 행동이라고 단정하기 어렵다.

### 6.1 고정 시간 창과 슬라이딩 시간 창

고정 시간 창은 날짜나 시간을 일정 구간으로 나누는 방식이다.

```text
8월 14일 00:00 ~ 23:59
8월 15일 00:00 ~ 23:59
```

구현은 단순하지만 자정 전후의 연속 거래가 분리될 수 있다.

슬라이딩 시간 창은 고위험 거래가 발생한 시점을 기준으로 최근 일정 시간을 조회한다.

```text
8월 15일 00:10 고위험 거래 발생
→ 8월 14일 00:10 ~ 8월 15일 00:10 조회
```

현재 서비스에는 슬라이딩 시간 창이 더 적합하다. 단, 24시간은 확정값이 아니며 `1h`, `6h`, `12h`, `24h`, `48h`를 실험해 선택해야 한다.

## 7. 거래 그래프와 연결요소

거래 그래프에서는 계좌를 점(Node), 거래를 방향이 있는 선(Edge)으로 표현한다.

```text
A 계좌 ──송금──▶ B 계좌 ──송금──▶ C 계좌
```

- Node: `(Bank ID, Account Number)`
- Edge: 거래 한 건
- Edge 속성: 거래 시각, 금액, 통화, 결제 방식, 모델 위험점수

**Connected Component(연결요소)**는 거래선을 따라 서로 연결되는 계좌와 거래의 묶음이다.

```text
그룹 1: A → B → C
그룹 2: D → E → F
그룹 3: G → H
```

위 거래는 서로 이어지지 않으므로 세 개의 연결요소가 된다. 각 연결요소를 에피소드 후보로 사용할 수 있다.

단, 연결요소 자체가 최종 Alert는 아니다. 거래소, 정산계좌 같은 대형 허브를 통해 무관한 거래까지 하나의 거대한 연결요소가 될 수 있기 때문이다. 따라서 다음 제한이 함께 필요하다.

- 고위험 시작 거래와 최대 1~2 hop 이내
- 거래 간 시간 간격 제한
- 최대 계좌 수와 거래 수 제한
- 과도한 허브 계좌에서 확장 중단
- 일정 시간 새 관련 거래가 없으면 에피소드 종료

## 8. 에피소드 Alert 생성 절차

### 8.1 1단계: 고위험 시작 거래 선정

모델이 각 거래에 `0~1` 위험점수를 출력한다고 가정한다.

```text
model_score >= 0.80
→ 에피소드 탐색을 시작하는 Seed 거래
```

`0.80`은 검증 전 초기값이며 확정 기준이 아니다.

### 8.2 2단계: 관련 거래 확장

Seed 거래가 `A → B`라면 해당 시점을 기준으로 시간 창 안에서 A 또는 B와 연결된 거래를 조회한다.

```text
Seed: A → B, score 0.91

관련 거래 후보:
C → A, score 0.62
B → D, score 0.58
D → E, score 0.73
```

모든 주변 거래가 Seed 임곗값을 넘을 필요는 없다. 중간 거래를 제외하면 자금 흐름이나 Cycle이 끊길 수 있기 때문이다.

초기 기준 예시는 다음과 같다.

```text
Seed 거래: score >= 0.80
주변 확장 거래: score >= 0.50 또는 패턴 연결에 필요한 거래
시간 창: 24시간 후보
기본 확장: 1-hop, 필요 시 최대 2-hop
```

### 8.3 3단계: 에피소드 후보 생성

다음 조건을 조합해 관련 거래를 하나의 후보로 묶는다.

- 계좌 또는 Entity를 공유한다.
- 시간 창 안에 있다.
- Seed에서 1~2 hop 이내다.
- 거래 방향과 순서가 하나의 연속 행동으로 설명된다.
- 동일 중심 계좌 또는 그래프 구조를 공유한다.

### 8.4 4단계: Alert 생성 또는 기존 Alert 갱신

에피소드 후보의 집계 위험도가 임곗값을 넘으면 Alert를 생성한다. 동일 행동에 대한 열린 Alert가 있으면 새 Alert 대신 기존 Alert에 거래를 추가한다.

```text
동일 중심 계좌 또는 Entity
AND 동일·유사 위험 유형
AND 마지막 거래 이후 시간 간격 이내
AND Alert 상태가 NEW 또는 IN_REVIEW
→ 기존 Alert 갱신
```

Alert가 갱신되면 관련 거래 수, 계좌 수와 점수 변화를 감사 이력으로 남겨야 한다.

## 9. 패턴의 역할

IBM AML의 `Patterns.txt`에는 FAN-IN, FAN-OUT, CYCLE 등 8개 유형과 attempt가 존재한다. 하지만 HI-Small 기준으로 모든 자금세탁 거래가 Patterns에 포함되는 것은 아니다.

```text
전체 자금세탁 거래: 5,177건
Patterns에 포함: 3,209건
Patterns 밖: 1,968건
```

따라서 다음 방식은 부적절하다.

```text
패턴을 발견한 경우에만 Alert 생성
```

에피소드는 시간과 계좌 관계로 만들고, 알려진 패턴은 해당 에피소드를 설명하거나 점수를 높이는 근거로 사용해야 한다.

```text
시간 + 계좌 연결 → 에피소드 후보
알려진 패턴 발견 → 유형 설명 및 위험점수 가중
```

### 9.1 Alert 유형

| Alert 유형 | 생성 조건 |
|---|---|
| `PATTERN_EPISODE` | 알려진 그래프 패턴이 발견된 다중 거래 에피소드 |
| `GENERAL_EPISODE` | 패턴명은 없지만 시간·계좌·Entity로 연결된 위험 거래 집합 |
| `SINGLE_HIGH_RISK` | 연결 거래가 없지만 단건 위험도가 매우 높은 거래 |

`GENERAL_EPISODE` 또는 `UNKNOWN`은 오류가 아니라 알려진 패턴으로 분류되지 않은 위험 에피소드를 뜻한다.

## 10. 패턴별 후보 기준

아래 수치는 구현과 평가를 시작하기 위한 초기 가설이며 데이터 검증 후 변경해야 한다.

### 10.1 FAN-OUT

```text
동일 송금 계좌
+ 24시간 이내
+ 서로 다른 수취 계좌 3개 이상
+ 후보 거래 3건 이상
```

주요 지표는 거래 수, 고유 수취 계좌 수, 총 출금액, 지속시간과 거래 위험점수다.

### 10.2 FAN-IN

```text
동일 수취 계좌
+ 24시간 이내
+ 서로 다른 송금 계좌 3개 이상
+ 후보 거래 3건 이상
```

### 10.3 CYCLE

```text
A → B → C → A
+ 서로 다른 계좌 3개 이상
+ 경로 길이 3~6 후보
+ 전체 과정 24시간 이내
```

경로상 금액 유지율도 함께 확인한다.

```text
cycle_amount_retention = 경로상 최소 금액 / 최초 거래 금액
```

### 10.4 SCATTER-GATHER

```text
하나의 출발 계좌
→ 중간 계좌 3개 이상으로 분산
→ 하나의 도착 계좌로 재집중
+ 전체 과정 24시간 이내
```

```text
amount_retention = 재집중 금액 / 최초 분산 금액
```

초기 가설로 금액 유지율 `70% 이상`을 실험할 수 있다.

### 10.5 GATHER-SCATTER

```text
서로 다른 송금 계좌 3개 이상
→ 중심 계좌에 집중
→ 서로 다른 수취 계좌 3개 이상으로 분산
+ 입금 후 출금까지 24시간 이내
```

BIPARTITE와 STACK은 다대다·다계층 판별이 필요하므로 MVP 이후 확장 대상으로 두는 것이 현실적이다.

## 11. 패턴이 없는 일반 에피소드

알려진 패턴이 없어도 다음 조건을 충족하면 일반 위험 에피소드로 만들 수 있다.

```text
동일 계좌 또는 Entity 공유
+ 시간 창 이내
+ 위험 거래 2건 이상
+ 집계 위험점수 임곗값 이상
→ GENERAL_EPISODE 후보
```

예:

```text
10:00 A → B, score 0.87
10:20 B → C, score 0.76
11:10 C → D, score 0.83
```

특정 패턴으로 확정하지 못해도 거래가 시간적으로 가깝고 연속적으로 연결되므로 하나의 일반 에피소드 후보가 될 수 있다.

## 12. 위험점수 예시

에피소드 점수는 모델 거래점수와 구조적 신호를 결합할 수 있다.

```text
episode_score =
  0.40 × max_transaction_risk
+ 0.20 × average_top3_risk
+ 0.25 × pattern_or_connection_score
+ 0.15 × amount_or_velocity_score
```

- `max_transaction_risk`: 포함 거래 중 최고 모델점수
- `average_top3_risk`: 상위 3개 거래점수 평균
- `pattern_or_connection_score`: 패턴 명확도 또는 연결 강도
- `amount_or_velocity_score`: 금액 규모 및 짧은 시간 내 거래 집중도

초기 Alert 생성 가설:

```text
episode_score >= 0.70
AND 관련 거래 >= 3
AND 관련 계좌 >= 3
→ 에피소드 Alert 생성
```

단건 예외:

```text
transaction_score >= 0.95
AND 연결 거래 없음
→ SINGLE_HIGH_RISK Alert 생성
```

이 가중치와 임곗값은 확정 정책이 아니라 검증을 위한 출발점이다.

## 13. 데이터셋을 이용한 검증 방법

`Patterns.txt`의 attempt 하나는 여러 자금세탁 거래로 구성된 알려진 사건 단위다. attempt ID는 모델이나 에피소드 생성 입력으로 사용하지 않고 평가 정답으로만 사용한다.

평가 시 거래 분류 지표 외에 다음 에피소드 지표가 필요하다.

| 지표 | 의미 |
|---|---|
| Episode Recall | 실제 attempt 중 하나 이상의 Alert로 탐지된 비율 |
| Episode Precision | 생성 Alert 중 실제 attempt와 대응되는 비율 |
| Transaction Coverage | 실제 에피소드 거래를 Alert가 얼마나 포함했는가 |
| Fragmentation Rate | 실제 사건 하나를 여러 Alert로 잘못 나눈 비율 |
| Merge Rate | 서로 다른 사건을 하나의 Alert로 잘못 합친 비율 |
| Alerts per Attempt | 실제 사건 하나당 생성된 Alert 수 |
| Alert Volume | 시간 또는 일 단위 생성 Alert 수 |

시간 창과 임곗값은 다음 후보를 비교해 선택한다.

```text
시간 창: 1h / 6h / 12h / 24h / 48h
Seed 임곗값: 0.70 / 0.80 / 0.90
최소 계좌 수: 3 / 4 / 5
```

목표는 Episode Recall을 높이는 동시에 Fragmentation, Merge와 담당자가 처리할 Alert 수를 낮추는 것이다.

### 13.1 평가 한계

Patterns 밖의 `Is Laundering=1` 거래에는 attempt ID가 없다. 따라서 다음 사실을 데이터셋만으로는 알 수 없다.

- 두 거래가 동일 사건인지 서로 다른 사건인지
- 실제로 어떤 패턴에 속하는지
- 생성한 일반 에피소드가 실제 사건 경계와 일치하는지

따라서 Patterns 안 거래는 에피소드 단위로 평가하고, Patterns 밖 거래는 거래 탐지 성능과 시스템이 만든 연결 근거를 평가해야 한다.

## 14. MVP 초기안

현재 프로젝트에서 실험을 시작할 수 있는 초기안은 다음과 같다.

```text
시간 창: 슬라이딩 24시간
에피소드 종료: 마지막 관련 거래 후 24시간
Seed 거래: model_score >= 0.80
주변 확장: 기본 1-hop, 필요 시 최대 2-hop
주변 거래: score >= 0.50 또는 경로 연결에 필요한 거래
최소 거래 수: 3건
최소 계좌 수: 3개
우선 패턴: FAN-IN, FAN-OUT, CYCLE, SCATTER-GATHER
Alert 생성: episode_score >= 0.70
긴급 단건 예외: transaction_score >= 0.95
```

이 값들은 제품 정책으로 확정하면 안 된다. `Patterns.txt`의 attempt를 평가 정답으로 사용하여 여러 조합을 실험한 후 정해야 한다.

## 15. 조원에게 설명할 때의 핵심 순서

발표나 회의에서는 다음 순서로 설명하면 된다.

1. **현재 문제:** 거래별 모델 결과를 곧바로 Alert로 만들고 있다.
2. **왜 문제인가:** 하나의 연결 행동이 여러 업무로 쪼개지고 운영 지표와 담당자 판단이 왜곡된다.
3. **수정 원칙:** 거래별 결과는 Risk Signal로 보존하고 연결된 신호를 에피소드 Alert로 만든다.
4. **어떻게 묶는가:** 시간 창 안에서 같은 계좌·Entity와 1~2 hop으로 연결된 거래를 찾는다.
5. **패턴이 없으면:** 알려진 패턴은 필수조건이 아니며 일반 연결 에피소드로 처리한다.
6. **단건은 버리는가:** 위험점수가 매우 높은 단건은 예외적으로 즉시 Alert를 만든다.
7. **수치는 확정인가:** 24시간, 0.80 등의 값은 초기 가설이며 attempt 정답으로 실험 후 결정한다.

### 가장 짧은 설명

> 모델은 거래를 한 건씩 판정해도 된다. 다만 그 결과를 바로 Alert로 만들지 않고 위험 신호로 저장한다. 이후 일정 시간 안에 같은 계좌나 연결 계좌에서 발생한 신호를 묶어 담당자가 한 번에 판단할 수 있는 에피소드 Alert로 만든다. 알려진 패턴은 Alert 생성의 필수조건이 아니라 설명과 우선순위를 강화하는 근거다.

## 16. 최종 정리

핵심 원칙은 다음과 같다.

> 패턴이 에피소드를 만드는 것이 아니라 시간과 계좌 관계가 에피소드를 만들고, 패턴은 에피소드를 설명하고 위험도를 보강한다.

```text
거래별 모델 판정
≠ 담당자의 최종 업무 단위

시간·계좌·Entity 연결 관계
→ 에피소드 후보
→ 패턴 및 집계 위험도 계산
→ Alert 생성 또는 열린 Alert 갱신
```

따라서 현재의 거래 수집과 거래별 추론 구조는 유지할 수 있다. 그 위에 `Risk Signal → Episode Aggregation → Alert` 업무 계층을 추가하는 것이 핵심 수정사항이다.
