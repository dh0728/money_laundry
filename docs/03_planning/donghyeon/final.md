
# 자료조사후 현재 기획된 기획안에서 다시 고려해봐야 할 사항

실제로 AML 모니터링 솔수션 서비스를 하고 있는 기업중에서 인터페이스를 확인 할 수 있는 기업은 두곳 SAS랑 Lucinity 두곳인데
이 두 곳을 통해 확인해봤을때 공톡점이 여러개가 있는데

1. 업무가 대시보드보다 Queue·Workboard를 중심으로 시작된다.
2. Alert와 Case가 서로 다른 객체다.
3. 담당자의 Claim·Assign·Release가 명시된다.
4. 고객·계좌·거래·과거 사건을 한 맥락에서 확인한다.
5. 조사 누락을 막는 체크리스트와 Narrative가 있다.
6. 관리자는 SLA, 업무량과 QA를 관리한다. - 
7. 모든 결정과 변경이 감사 이력으로 남는다. 

## 여기서 봤을 떄 가장 중요하기 다뤄야할 안건은 Alert 단위에 대한 부분이다.

현재 기획은 거래 처리 파이프라인이 중심이므로 거래 한 건 → Alert 한 건으로 해석될 여지가 있다. 실제 AML 모니터링에서는 거래 단건보다 고객 또는 계좌의 일정 기간 행동을 하나의 Alert로 묶어 검토하는 것이 적절하다.

이때 계좌 묶는다는것은 모델 부터 묶어서 값을 출력해야 한다는 뜻이 아니다

모델은 거래 또는 계좌별 점수를 출력할 수 있다. 그러나 담당자가 받는 Alert는 다음과 같은 위험 에피소드여야 한다는 뜻이다.

예시)
```
홍길동 고객의 최근 24시간 행동
- 다수 계좌에서 반복 입금
- 짧은 시간 내 여러 계좌로 분산 송금
- 평소 거래 패턴보다 거래량 급증
- 고위험 관계 계좌와 연결
```

#### 거래 1건당 Alert가 서비스적으로 부적절한 이유?
1. 자금 세탁의 의심 근거가 거래 한 건에 완성되지 않고 순서, 횟수, 관계, 기간을 함꼐봐야함
2. 하나의 의심행위가 여러 업무로 중복 생성된다.
  - 예를 들어 한 고객이 24시간 동안 20건의 의심 거래를 발생시키면 현재 구조에서는 최대 20개의 Alert가 생성
3. Claim, 상태 변경, 종결 사유, 감사 이력을 남겨야 하므로 동일한 위험 에피소드에 대해 같은 판단을 반복하고 일관성이 깨질 수 있음
  - 같은 사건임에도 다른 담당자에게 배정되었을 떄 판단이 달라 결론이 불명확해짐
4. Alert Queue의 업무량이 실제 위험량과 달라진다.
  - 거래량이 많은 고객은 동일한 의심행위라도 Alert를 많이 발생시키고, 거래 수가 적은 고위험 고객은 적은 Alert만 발생시킵니다.
  - Alert 100건 = 고객 3명의 반복 거래 이런 일이 생길 수 있음
5. 위에 이유로 Alert 적체량, 평균 처리시간, Alert→Case 전환율, 담당자 처리 실적 같은 여러 지표가 왜곡
6. 우리 서비스의 핵심 분석 결과는 “수상한 거래 한 건”이 아니라 “서로 연결된 여러 거래에서 발견된 수상한 행동”인데, Alert를 너무 일찍 거래 단위로 만들어 버리면 그 핵심 결과를 담을 자리가 애매하다


따라서 1단계 결과는 위험 신호로 저장하고, 2단계에서 발견한 계좌 관계와 자금 흐름을 반영하여 에피소드 단위 Alert를 생성하거나 기존 Alert를 갱신하는 구조가 적절하다.

## 그럼 에피소드 단위 Alert를 생성해야 하는데 어떻게 하노?

Patterns.txt의 attempt 하나가 실제로 여러 거래로 구성된 자금세탁 사건을 나타내기 때문에, 이걸 활용해야 한다.

일단 현재 데이터셋에서는 실제 고객정보나 KYC가 없다

따라서 다음 기준으로 거래를 묶을 수 있다.
```
계좌 연결
+ 발생 시간
+ 거래 방향
+ 모델 위험점수
+ 그래프 패턴
= 위험 에피소드
```

현재 상황에서 가장 현실적인 생성방식은 MVP로 봤을떄 아래 4단계로 구현 하는게 가장 쉽지 않을까 싶다
1. 거래별 위험점수 계산
2. 고위험 거래를 시작점(seed)으로 선정
3. 시간 창 안에서 연결 거래를 확장
4. 연결된 거래 집합의 패턴과 점수를 계산해 Alert 생성

### 1. 거래별 위험점수 계산

모델이 각 거래에 0~1 위험점수를 출력

```
risk_score >= 0.91
→ 에피소드 후보 거래
```

### 2. 후보 거래 주변 확장

고위험 거래 하나를 발견하면 해당 거래만 Alert로 만들지 않고, 같은 계좌와 연결된 거래를 조회
예를 들어 다음 거래가 후보로 탐지됐다

```
A → B, 위험점수 0.91
```

거래의 송금·수취 계좌 A, B를 기준으로 다음 조건의 거래를 추가
기준 거래 전후 24시간
+ A 또는 B와 직접 연결
+ 필요하면 2-hop까지 확장

여기서 주의할 것은 **중요한 점은 확장 과정에서 위험점수가 낮은 거래도 포함할 수 있다는 것**
모두 고위험 점수여야 하면 중간에 끊어짐

```
A → B : 0.91
B → C : 0.72
C → D : 0.68
D → A : 0.76
```


```
Seed 기준
risk_score >= 0.80

확장 거래 기준
seed와 1~2 hop 연결
AND 24시간 이내
AND risk_score >= 0.50 또는 구조적으로 필요한 거래
```

### 연결 거래를 하나의 에피소드로 묶기
1. 계좌가 직접 또는 2-hop으로 연결되어 있다.
2. 거래 시각 차이가 24시간 이내다.
3. 같은 그래프 패턴을 구성하거나 동일 중심 계좌를 공유한다.


고위험 거래가 발생하면 해당 거래 시점을 기준으로 최근 일정 시간의 관련 계좌 거래를 조회한다. 계좌를 점, 거래를 방향이 있는 선으로 표현한 부분 그래프를 구성하고, 서로 연결된 거래 집합을 에피소드 후보로 추출한다. 이후 시간 간격, 위험점수, 연결 단계, 허브 계좌 및 최대 크기 제한을 적용해 실제 Alert 생성 여부를 판단한다.
