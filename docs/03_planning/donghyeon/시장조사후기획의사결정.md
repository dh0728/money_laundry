# 회사별 플로우
#### 옥타솔루션 AML-PRISM
KYC(CDD/EDD·WLF·RA) → AML Data Mart → TMS 시나리오 탐지 → Alert → 조사·분석 → STR/CTR → KoFIU 보고
#### NAVER AMLXpress
고객사 KYC/CDD → WLF·RA → 필요 시 EDD → 거래 데이터 적재 → TMS 배치 탐지 → Alert → 검토·결재 → STR/CTR 파일 생성 → 고객사 보고전용 PC → KoFIU
#### SAS AML
고객·계좌·거래 데이터 → Rule·모델 탐지 → Alert → L1 검토 → 추가정보 요청(Inquiry) → Case 조사 → EDD·승인 → SAR/STR → 전자제출
#### Lucinity
외부 탐지시스템의 Alert → Workboard·Triage → Case 생성 → 고객 360·거래·그래프 조사 → 정상/의심 판정 → QA·승인 → SAR/STR 작성·제출

옥타·AMLXpress = KYC부터 보고까지 전체 AML
SAS = 탐지부터 조사·보고까지
Lucinity = 외부 Alert를 받은 이후 조사·Case·보고 중심

KYC: 고객이 누구인지 파악하고 지속적으로 관리하는 전체 과정
WLF: 고객 이름 등을 제재·PEP·요주의인물 목록과 비교하는 기능
RA: 국가·직업·상품·채널·WLF 결과 등을 이용해 고객 위험등급을 계산하는 기능
CDD/EDD: 실제 고객 정보를 확인하는 절차
```
KYC(고객알기·고객확인)
├─ 고객 신원 확인·검증
├─ 실제소유자·거래목적 확인
├─ WLF: 제재·PEP·요주의인물 대조
├─ 고객 RA: 고객 위험점수·등급 산출
└─ 고위험 고객이면 EDD 수행
```

### 1. 솔루션들을 보면 KYC(고객알기·고객확인) 역시 지원하고 고객사로 부터 받은 정보를 통해 WLF·RA를 수행하는데 우리는 어떻게 하면 좋을까?

- 현재 우리 시스템은 KYC, WLF, RA를 고객사 시스템이 수행하고 우리 TMS 시스템이 결과를 받아 사용하는 외부 여영역으로 설계해야 함
- 따라서 KYC/WLF/RA 결과 수신 API를 구현해야함
- 근데 이런 개인정보는 받지 않는 구조라 STR작성과 제출은 힘들어서 권한있는 사용자만 고객사 시스템에서 개인정보를 실시간 조회하는 기능이 있어야함 

받아야 할 데이터
| 구분 | 받아야 할 데이터 |
|---|---|
| 고객 식별 | 가명화된 `customer_id`, 고객·계좌 연결정보 |
| KYC | 완료 여부, CDD/EDD 상태, 마지막 확인일 |
| RA | 위험등급, 점수, 위험요인 코드, 평가일, 모델 버전 |
| WLF | 정상·잠재일치·확정일치 상태, PEP·제재대상 여부, 확인일 |
| 최소 속성 | 고객 유형, 국가위험 구간, 업종위험 구간, 가입일 |

```
고객사 KYC/WLF/RA 시스템
        ↓ 결과만 전달
TMS 룰 실행 및 Alert 우선순위 계산
        ↓
Alert Queue 
```

### 3. 케이스 생성이 필요한가?
CASE라는것은 사실 필수적인 객체는 아니다 하지만 자금 세탁으로 의심되는 건을 조사하기 위해서는 사실 하나의 Alert만으로 조사를 끝낼 수 없는 경우도 많다. 여러 알림이 동일한 자금 세탁 행위일 수 도 있기 때문에 이것을 하나의 조사건으로 묶어야 한다.

예시)
```
Case 1001
├─ Alert A
├─ Alert B
├─ Alert C
├─ 고객 1
├─ 관련 계좌 2
└─ 관련 거래 37건
```

CASE가 없으면 하나의 거래가 여러 시나리오에 걸려 여러 Alert에 포함될 때 각 Alert에서 같은 거래를 반보 조사해야 한다

### 6. 룰엔진을 어떻게 넣을 것인가? 

사실 rule엔진을 어떻게 만들 것인지는 상당히 힘듬 위험사례를 구체적으로 공개하고 있지도 않고 flagright가 그 문제를 해결해 줄 수 있는 좋은 사례라고 생각함. 

룰 엔진으로 만들 수 있는 Rule Studi를 제공

그럼 우리가 제공해야 할 기능은?
```
고객사가 탐지 시나리오 정의
→ IF/THEN 룰 설정
→ 과거 거래 백테스트
→ 예상 거래 적중·Alert 발생량 확인
→ 고객사 내부 승인
→ 섀도우 실행
→ 운영 룰 배포
→ 적중률·오탐률 모니터링
→ 임계값 수정
```

이렇게 정할 수 있을수 있도록 주고 연구 시연용 참고 템플릿만 던져 주면 괜찮지 않을까가 나의 생각. 개발 범위가 늘어난다고 생각할 수 있지만 그만큼 룰엔진에 대한 고민이 줄어듬

근데 고객이 룰을 만들더라도 시스템은 버전관리·승인·테스트·변경근거·성과측정을 지원같은 부가 기능들이 좀 생겨서 일이 너무 많아진다는 단점도 있음

그래서 내가 생각하는 시스템 구조는 아래와 같다

TMS 탐지
```
TMS 탐지
→ Alert 생성
→ L1 검토
├─ 정상·오탐 → Alert에서 종결
└─ 의심 지속 → 조사건(Case) 생성
                 → 관련 Alert·고객·계좌·거래 병합
                 → 그래프·과거 거래·증적 조사
                 → 정상 종결 또는 의심거래 확정
                 → 결재
                 → STR
```
- Alert: 탐지 결과
- Case: 사람이 실제로 조사하는 사건
- STR: 조사 결과 보고가 필요하다고 결정된 건

룰 엔진
```
고객사 정의 룰
        ↓
룰 엔진 ──────┐
               ├→ 탐지 결과 병합 → Alert
GNN 탐지모델 ─┘
```

최종 플로우
```
고객사 KYC·WLF·RA 및 전일 거래 전달
→ S3 저장
→ 데이터 검증
├─ 실패 → 오류 격리 → 고객사 재전송
└─ 성공 → PostgreSQL AML Data Mart
             → TMS 룰·GNN 일 배치
             ├─ 미탐지 → 실행 이력 저장 → 종료
             └─ 탐지 → Alert 생성·병합
                         → Alert Queue
                         → L1 검토
                         ├─ 정상·오탐 → 사유 기록 → Alert 종결
                         └─ 의심 지속 → Case 생성
                                         → 심층 조사
                                         ├─ 추가정보 필요 → 고객사 요청 → 재조사
                                         ├─ 정상·오탐 → Case 종결
                                         └─ 의심거래 → 내부 결재
                                                         ├─ 반려 → 보완·재조사
                                                         └─ 승인 → STR 파일 생성
                                                                     → 고객사 보고 환경
                                                                     → KoFIU 제출
                                                                     ├─ 오류 → 수정·재제출
                                                                     └─ 성공 → 이력 보존·종료
```

### 8. 그럼 현재 데이터셋으로 구현할 수 있는 룰은?

#### FAN-IN
```
24시간 동안 서로 다른 10개 이상의 계좌로부터 입금
그리고 총입금액이 같은 은행 계좌의 상위 1%
```
필요 정보:
- 거래 시간
- 입금 계좌
- 송금 상대방 수
- 입금 총액
- 동일 은행 내 상대적 금액 순위
모두 IBM 데이터에서 계산할 수 있습니다.

#### FAN-OUT
```
24시간 동안 하나의 계좌가 서로 다른 10개 이상의 계좌로 송금
그리고 평상시 출금 상대방 수보다 크게 증가
```

#### 빠른 자금 통과
```
계좌가 금액 X를 받은 뒤 1시간 안에
X의 80~120%에 해당하는 금액을 다른 계좌로 송금
```
논문의 예시를 IBM에 맞추면 다음처럼 됩니다.
```
원래 논문:
신설 회사가 고위험국가에서 120만 유로를 두 번 받고
비슷한 금액을 개인 계좌로 송금

IBM에서 가능한 형태:
한 Entity가 보유한 계좌가 짧은 시간에 큰 금액을 반복 수취하고
수취 금액과 비슷한 금액을 다른 Entity의 계좌로 빠르게 송금
```
신설 회사, 고위험국가, 개인 계좌라는 조건은 빠지지만, 거래 행위 자체는 탐지할 수 있습니다.

조건 예:
- 24시간 이내
- 3~5개 계좌
- 시작 금액 대비 종료 금액 차이 20% 이하

#### 다계좌 엔터티 분산거래
```
동일 Entity가 보유한 여러 계좌에서 자금을 분산 수취하고
이후 특정 계좌로 집중
```

#### 은행·통화 변화
```
평소에는 동일 은행·동일 통화로 거래하던 계좌가
짧은 기간에 여러 은행 및 여러 통화를 사용
```
단, 이것을 해외거래라고 부르면 안 됩니다. IBM에는 국가 정보가 없으므로 정확한 표현은 은행 간 거래 또는 통화 변환 거래입니다.

만약 외부정보 연결을 고려한 데이터 모델을 만들려면 지금 IBM에 값이 없더라도 확장할 수 있도록 필드는 만들어두는 것이 좋다.

국내 은행용으로 넘어갈 떄 실제 필요한 데이터

### 9. 최종 결과물에는 IBM AML 데이터만으로는 표현할 수 없는 것들이 많은데 우짬?

현재 IBM 데이터에는 Case 심층 조사에 필요한 KYC·WLF·RA·고객속성 정보가 없으므로, 제품 시연을 위해 IBM Entity ID와 연결되는 합성 AML 고객 컨텍스트 데이터를 별도로 구성
합성 데이터는 Case 조사, 추가정보 요청, 고객 360, STR 초안 작성 등 업무 흐름을 시연하는 용도로만 사용하며 GNN 및 룰 탐지 성능평가에서는 제외한다.


고객
```
demo_customers
- customer_id          # IBM Entity ID
- customer_type        # INDIVIDUAL / CORPORATE
- residence_country
- nationality
- occupation_code      # 개인
- industry_code        # 법인
- incorporation_date   # 법인
- data_source          # SYNTHETIC_DEMO
```

KYC·CDD·EDD
```
demo_kyc
- customer_id
- kyc_status           # COMPLETED / INCOMPLETE / EXPIRED
- cdd_level            # STANDARD / ENHANCED
- edd_status
- last_reviewed_at
- next_review_at
- missing_items
- data_source
```

고객위험평가
```
demo_customer_risk
- customer_id
- risk_grade           # LOW / MEDIUM / HIGH
- risk_score
- risk_factor_codes
- assessed_at
- model_version
- data_source
```

위험요인 예:
```
HIGH_TRANSACTION_VOLUME
MULTIPLE_ACCOUNTS
HIGH_VELOCITY
CROSS_BANK_ACTIVITY
MULTI_CURRENCY
HIGH_RISK_COUNTRY
PEP_RELATED
```
HIGH_RISK_COUNTRY, PEP_RELATED는 합성값이라는 표시가 반드시 있어야 합니다.

WLF·PEP·제재
```
demo_wlf_results
- customer_id
- screening_status     # CLEAR / POTENTIAL_MATCH / CONFIRMED_MATCH
- pep_flag
- sanctions_flag
- adverse_media_flag
- screened_at
- adjudication_status
- data_source
```
계좌
```
demo_accounts
- account_id           # Bank ID + Account Number
- opened_at
- closed_at
- account_type
- owner_customer_id
- data_source
```
실소유자
법인 고객에만 생성합니다.
```
demo_beneficial_owners
- corporate_customer_id
- owner_customer_id
- ownership_percentage
- control_type
- verified_at
- data_source
```

합성데이터를 넣을때 서로 모순되지 않도록 만들어야함
무작위 값만 넣으면 Case 화면에서 내용이 서로 충돌할 수 있습니다. 최소한 다음 규칙을 지켜야 합니다.
- 개인 고객에게 업종과 법인 설립일을 넣지 않는다.
- 법인 고객에게는 업종과 설립일을 넣는다.
- 법인 고객만 실소유자를 가질 수 있다.
- 계좌 개설일은 첫 거래일보다 이전이어야 한다.
- KYC 최근 검토일은 Case 조사 시점보다 이전이어야 한다.
- WLF CONFIRMED_MATCH이면 RA 위험요인에도 관련 코드가 나타나야 한다.
- EDD REQUIRED이면 고객위험등급이 중·고위험이어야 한다.
- 폐쇄된 계좌에서 폐쇄일 이후 거래가 발생하지 않게 한다.
- 같은 Entity ID는 항상 같은 고객정보를 가져야 한다.
