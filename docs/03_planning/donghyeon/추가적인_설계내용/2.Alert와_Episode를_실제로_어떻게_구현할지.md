# Alert와 Episode: 실제로 어떻게 구현할지

> **한 줄 요약**: 세 단계로 나눠 만든다. 1단계는 화면만, 2단계는 서버 계산 추가, 3단계는 DB 테이블 추가. 뒤로 갈수록 일이 크다.

- **무엇을 할지**는 `8.Alert와_Episode에서_무엇을_보여주고_어떻게_묶을지.md`에 있다. 이 문서는 **어떻게 만들지**만 적는다.
- 기준 코드: `origin/dev` (2026-10-04), `API.md` v0.10, DB 마이그레이션 V1~V17.

## 0. 지금 구조 (바뀌지 않는 부분)

```text
거래 → 모델 점수 → 씨앗 선별 → Alert 생성 → 조사 화면
                                 (워커)       (API → 프론트)
```

| 곳 | 하는 일 | 주요 파일 |
|---|---|---|
| 워커 (Python) | 씨앗에서 앞뒤 거래를 따라가 Alert를 만든다 | `worker/alert_builder.py`, `worker/alert_pipeline.py` |
| API (Spring) | 조사 화면에 줄 데이터를 만든다 | `review/ReviewService.java`, `review/CaseSummary.java` |
| 프론트 (React) | 상세 화면을 그린다 | `pages/LiveCasesPage.tsx`, `api/liveReview.ts` |

## 1. 세 단계 요약

| 단계 | 하는 일 | 바꾸는 곳 | 이걸 하면 화면에 생기는 것 |
|---|---|---|---|
| 1단계 | 서버가 이미 보내는데 화면이 안 쓰는 값을 쓴다 | 프론트만 | 거래별 포함 이유, 은행, 다른 사건의 판정, Episode 타임라인 |
| 2단계 | 서버가 새 값을 계산해서 보낸다 | API | 요약 문장, 모양(구조), 계좌 역할, 못 본 범위, 평소 대비 |
| 3단계 | "계좌 → Alert" 찾기용 테이블을 만든다 | DB + 워커 + API | 과거 조사 이력, 연관 Alert 후보, 묶은 근거 저장 |

## 2. 1단계: 프론트만 고친다

`GET /api/v1/review/cases/{caseId}` 응답에 이미 들어 있는 값이다. 타입 선언만 추가하면 쓸 수 있다.

| 이미 있는 값 | 뜻 | 쓸 곳 |
|---|---|---|
| `includedReasons` | 이 거래가 Alert에 포함된 이유 (상류·하류·같은 송금처·같은 수취처) | "왜 떴나" 블록, 거래 탭 |
| `fromBankId`, `toBankId` | 보내는 은행, 받는 은행 | 타행 거래 수, 거래 탭 |
| `amountReceived`, `receivingCurrency` | 받은 금액과 통화 | 통화가 바뀐 거래 표시 |
| `relatedDecisions` | 같은 거래를 다른 사건에서 어떻게 판정했나 | 과거 이력, 거래 탭 |
| `groups[].decision` | Episode 안에서 Alert별 판정 | Episode 판정 진행 |
| `sources[]` | 거래가 어느 Alert에서 왔나 | 여러 Alert에 걸친 거래 표시 |
| `accounts[].ownerName`, `bankId` | 계좌의 소유주와 은행 | 계좌 탭 |

고칠 파일은 다섯 개다.

- `api/liveReview.ts`: 위 값의 타입 추가
- `pages/LiveCasesPage.tsx`: 개요 블록 재배치, 계좌 탭 추가
- `features/alerts/AlertTxTable.tsx`: 포함 이유·은행·다른 사건 열 추가
- `features/episodes/LinkedAlerts.tsx`: 시간순 정렬, 판정·기간 열 추가
- `features/graph/liveAdapter.ts`: 거래 역할, Alert별 색

## 3. 2단계: 서버가 새 값을 계산한다

### 3.1 `CaseFacts` 클래스를 만든다

- 위치: `CaseSummary.java` 옆.
- 입력: 지금 조사 범위에 있는 거래 목록.
- 출력: 아래 표의 값.
- **DB에 저장하지 않는다.** 화면을 열 때마다 계산한다. Alert 하나가 최대 100건이라 가볍다.

| 값 | 계산 방법 |
|---|---|
| 구성 | 거래마다 붙어 있는 포함 이유를 종류별로 센다 |
| 수취 집중 | 계좌마다 "돈을 보낸 서로 다른 계좌 수"를 세고, 가장 큰 계좌를 고른다 |
| 송금 분산 | 반대로 "돈을 받은 서로 다른 계좌 수"가 가장 큰 계좌를 고른다 |
| 계좌 역할 | 보내기만 함 → 출발 / 받기만 함 → 도착 / 받은 뒤 보냄 → 경유 / 참고 거래에만 나옴 → 주변 |
| 최장 경로 | 거래를 시간순으로 놓고, "앞 거래의 받는 계좌 = 뒤 거래의 보내는 계좌"로 이어지는 가장 긴 줄을 찾는다 |
| 순환 | 그 줄이 출발 계좌로 돌아오는지 본다 |
| 경유 비율 | 나간 돈 ÷ 들어온 돈 |
| 체류 시간 | 입금과 출금을 짝지어 시간 차이의 중앙값을 낸다 (지금 있는 `MoneyMetrics`의 FIFO 계산을 확장) |

### 3.2 응답에 필드를 추가한다

| 추가 필드 | 내용 |
|---|---|
| `facts` | 위 표의 계산 결과 |
| `seeds` | 씨앗 거래별 점수, 백분위, 임계값 대비 배수, 유형 후보 |
| `evidence` | 시스템이 못 본 범위(`limits`), 은행별 수신 현황(`coverage`), 기준 시각 |

`evidence`는 Alert API가 이미 만들고 있는 값이다. 조사 화면 응답으로 넘겨주기만 하면 된다.

### 3.3 계좌 탭용 API를 만든다

- `GET /api/v1/review/cases/{caseId}/accounts`
- 계좌별 역할, 유입·유출, 평소 대비, 새 상대방 수를 한 번에 돌려준다.
- "평소 대비"는 사건 밖 원장 거래를 조회해야 해서 `facts`와 분리했다. 지금 있는 `/money`와 같은 방식이다.

### 3.4 주의

목록 API가 행마다 상세 조회를 부른다. `facts`를 목록에서도 계산하면 느려지니 **상세 화면에서만** 계산한다.

## 4. 3단계: DB 테이블을 추가한다

### 4.1 왜 필요한가

"이 계좌가 나온 다른 Alert"를 찾으려면 지금은 모든 Alert의 거래를 뒤져야 한다. 책 뒤의 '찾아보기'처럼 **계좌 → Alert** 색인을 만들어 두면 바로 찾는다.

### 4.2 테이블

```sql
-- V18__alert_accounts.sql
CREATE TABLE alert_accounts (
 alert_id BIGINT NOT NULL, version INTEGER NOT NULL,
 account_id UUID NOT NULL,   -- 가명 계좌
 owner_id UUID NOT NULL,     -- 가명 소유주
 bank_id INTEGER NOT NULL,
 role TEXT NOT NULL,         -- SOURCE / INTERMEDIARY / DESTINATION / PERIPHERAL
 touches_seed BOOLEAN NOT NULL,
 in_count INTEGER NOT NULL, out_count INTEGER NOT NULL,
 in_amount_usd NUMERIC(24,6) NOT NULL, out_amount_usd NUMERIC(24,6) NOT NULL,
 PRIMARY KEY(alert_id,version,account_id),
 FOREIGN KEY(alert_id,version) REFERENCES alert_versions
);
CREATE INDEX ix_alert_accounts_account ON alert_accounts(account_id);
CREATE INDEX ix_alert_accounts_owner ON alert_accounts(owner_id);
```

### 4.3 누가 채우나

- **새 Alert**: 워커가 Alert를 만들 때 같이 넣는다(`alert_pipeline.py`). 계좌별 건수와 금액은 워커가 이미 계산하고 있어서 역할과 소유주만 더하면 된다.
- **기존 Alert**: 저장돼 있는 근거(`alert_versions.evidence`)에서 한 번 채운다.

## 5. 연관 Alert 후보를 계산하는 방법

### 5.1 후보를 뽑는다

모든 Alert 쌍을 비교하지 않는다. 색인으로 겹치는 것만 찾는다.

```sql
-- 이 Alert의 계좌가 나온 다른 Alert 찾기 (각 Alert의 최신 완료 버전만)
SELECT b.alert_id, b.account_id, a.role AS my_role, b.role AS other_role
FROM alert_accounts a
JOIN alert_accounts b ON b.account_id = a.account_id AND b.alert_id <> a.alert_id
WHERE a.alert_id = :alertId;
```

같은 방식으로 `owner_id`(같은 소유주)와 `alert_transactions.tx_id`(같은 거래)도 조회한다.

### 5.2 쌍마다 근거를 만든다

| 종류 | 근거 | 판정 방법 |
|---|---|---|
| 돈 | 공유 거래 | 같은 `tx_id`가 양쪽 `alert_transactions`에 있다 |
| 돈 | 공유 계좌 | 같은 `account_id`가 양쪽 `alert_accounts`에 있다 |
| 돈 | 자금 흐름 연속 | 공유 계좌가 앞선 Alert에서는 도착·경유, 뒤 Alert에서는 출발·경유다 |
| 돈 | 직접 거래 | 원장에 "A의 계좌 → B의 계좌" 거래가 있다. 어느 Alert에도 없는 거래도 포함한다 |
| 사람 | 같은 소유주 | `owner_id`는 같고 `account_id`는 다르다 |

### 5.3 종류와 강도를 매기고 정렬한다

종류(`kind`)와 강도(`grade`)는 따로 계산해서 둘 다 응답에 넣는다.

| 종류 | 조건 |
|---|---|
| 돈으로 이어짐 | 공유 거래, 공유 계좌, 직접 거래 중 하나라도 있다 |
| 사람으로 이어짐 | 위는 없고 같은 소유주만 있다 |
| 비슷함 | 둘 다 없고 기간·유형만 같다 |

| 강도 | 조건 |
|---|---|
| 강 | 공유 거래, 공유 계좌(양쪽에서 출발·경유·도착), 직접 거래, 같은 소유주 중 하나라도 있다 |
| 중간 | 공유 계좌가 있지만 한쪽에서 역할이 `PERIPHERAL`(주변)이다 |
| 약 | 허브 계좌만 겹치거나, 계좌가 아주 많은 소유주만 겹치거나, 기간·유형만 같다 |

정렬은 점수를 더하지 않고 아래 순서로 하나씩 비교한다. 돈으로 이어진 근거가 사람으로 이어진 근거보다 앞에 온다.

```text
강도 → 공유 거래 수 → 자금 흐름 연속 수 → 공유 계좌 수 → 직접 거래 수 → 같은 소유주 수 → 시간 간격
```

### 5.4 너무 흔한 계좌와 소유주를 뺀다

| 대상 | 왜 빼나 | 기준 |
|---|---|---|
| 허브 계좌 | 거래 상대가 아주 많은 계좌(거래소, 정산 계좌 등)는 거의 모든 Alert와 겹친다 | 워커가 이미 쓰는 기준 그대로 (`ACCOUNT_ACTIVITY`, 기간 내 100건 초과) |
| 계좌가 아주 많은 소유주 | 계좌 수백 개를 가진 소유주는 허브 계좌처럼 거의 모든 Alert와 "같은 소유주"로 걸린다 | 소유주별 계좌 수가 기준을 넘으면 제외. 기준 개수는 실제 분포를 보고 정한다 |

둘 다 후보에서 지우지는 않는다. 강도를 "약"으로 내리고 이유를 표시한다.

"공통 상대방"(두 Alert가 같은 제3의 계좌와 각각 거래함)은 아직 넣지 않는다. 원장 조회가 필요하고 허브 계좌에 특히 약해서 나중으로 미룬다.

### 5.5 소유주 보기

새 API는 필요 없다. 프론트가 합친 그래프의 계좌를 `ownerId`로 묶어 한 점으로 그린다. 지금 그래프에 있는 소유주 보기(`OwnerGraph`)와 같은 방식이다. 계좌가 아주 많은 소유주는 합치지 않는다.

### 5.6 API

| API | 용도 |
|---|---|
| `GET /api/v1/review/cases/{caseId}/related?basket=…` | 후보 목록. 후보마다 `kind`(돈·사람·비슷함), `grade`(강·중간·약), 근거 목록을 준다. `basket`에 담은 사건 ID를 주면 묶음 전체 기준으로 계산한다 |
| `GET /api/v1/review/links?caseIds=…` | 고른 사건들 사이의 쌍별 근거와 잇는 거래. 합친 그래프와 관계도에 쓴다 |

이미 Episode에 속한 Alert는 후보 목록에서 그 Episode 한 줄로 접어서 돌려준다. 등급은 소속 Alert 중 가장 강한 연결을 따른다.

## 6. 묶을 때 근거를 저장한다

- 묶는 명령은 지금 있는 `TRANSFER`를 그대로 쓴다. 기존 Episode 편입도 이미 지원한다(`targetCaseId`).
- 여기에 `linkEvidence[]`(고른 근거 목록)를 추가해서 `review_events.snapshot`에 넣는다.
- **왜 복사해서 저장하나**: 근거는 화면을 열 때마다 계산하는 값이다. 나중에 데이터가 바뀌면 값도 바뀐다. "묶을 당시 무엇을 보고 묶었는지"를 남기려면 그 순간의 값을 복사해 둬야 한다.
- Episode 화면의 "왜 묶었나"는 이 저장된 값을 읽어서 보여준다.

"편입 요청"(다른 담당자 Alert)은 아직 없는 기능이다. 만든다면 지금 있는 알림(V15)에 요청 종류를 추가하고, 수락하면 `TRANSFER`를 실행하는 방식이 가장 작다. 팀 결정이 먼저다.

## 7. 만드는 순서

| 순서 | 할 일 | 끝나면 되는 것 |
|---|---|---|
| 1 | 1단계 전부 | "왜 떴나", Episode 선후 관계가 보인다 |
| 2 | `CaseFacts` + 응답 필드 추가 | 요약 문장, 모양, 못 본 범위 |
| 3 | `/accounts` API + 계좌 탭 | 계좌 역할, 평소 대비 |
| 4 | `alert_accounts` 테이블 + `/related` | 과거 이력, 연관 후보 목록 |
| 5 | `/links` + 연관 Alert 탭 | 합친 그래프, 관계도, 담기 |
| 6 | `linkEvidence` 저장 | Episode에 "왜 묶었나"가 남는다 |

1~3은 DB를 안 건드려서 바로 시작할 수 있다. 4부터는 마이그레이션이 필요하다.

## 8. 미리 알아둘 문제

| 문제 | 영향 |
|---|---|
| 시연 원장의 기간이 짧다 | "평소 대비"를 계산할 과거 기간이 없어 대부분 "기준선 부족"으로 나온다 |
| 지금 워커의 모델은 시연용 계산기다 (`demo-random-v1`) | "모델 유형 vs 실제 모양" 비교는 실모델을 붙인 뒤에야 의미가 있다 |
| 기준값이 가설이다 | "3개 이상이면 집중", "30일 기준선", 허브 기준은 검증된 수치가 아니다 |
| 본인 담당 Alert만 묶을 수 있다 (API.md §9.4) | 연관 후보가 대부분 다른 담당자 것이라, 규칙을 정하지 않으면 묶기 버튼을 쓸 일이 적다 |
| Episode는 거래 수가 많다 | 최장 경로 계산이 Alert 수에 비례해 커진다. 건수 상한이 필요한지 실제 데이터로 확인해야 한다 |
