 룰엔진 어떻게 설계할건지? 좀 구체적으로

- 회사가 제공한 정책 프로필과 검증된 룰 템플릿을 바탕으로 자연어를 구조화된 룰 초안으로 변환하고, 백테스트·승인·Shadow 운영을 거친 버전만 실제 탐지에 사용
- 자연어가 직접 SQL이나 실행 코드를 만드는 구조는 피해야 함

방식에 따른 과정
- IF/THEN → 백테스트 → 승인 → Shadow → 운영 
- LLM 구조화 초안 생성 → 검증 가능한 Rule DSL → 구문·의미·성능 검증 → 백테스트  → 승인 → Shadow → 운영

#### 룰 템플릿 카탈로그
- 사용자가 빈 화면에서 전부 작성하게 하지 말고 시나리오 템플릿을 제공

| 템플릿 | 판정 단위 | 주요 파라미터 |
|---|---|---|
| 단건 고액거래 | 거래 | 금액, 통화, 고객군 |
| 분할 입·출금 | 계좌×기간 | 기준금액 비율, 기간, 건수, 합계 |
| FAN-IN | 수취계좌×기간 | 송금인 수, 건수, 총액 |
| FAN-OUT | 송금계좌×기간 | 수취인 수, 건수, 총액 |
| 급속 자금 통과 | 계좌×기간 | 유입·유출 비율, 체류시간 |
| 휴면계좌 활성화 | 계좌×기간 | 휴면기간, 활성화 이후 거래량 |
| 평소 대비 급증 | 고객×기간 | 기준기간, 비교기간, 증가배수 |
| 고위험 국가 거래 | 고객·계좌×기간 | 국가 목록, 금액, 건수 |
| 순환거래 | 서브그래프 | 최대 경로 길이, 시간, 금액 차이 |
| 반복 상대방 거래 | 계좌쌍×기간 | 반복횟수, 금액, 시간창 |

각 템플릿은 다음을 갖는다.
- 필요한 데이터 필드
- 허용 가능한 조건
- 회사가 수정할 파라미터
- 기본 실행 단위
- 실행 쿼리 골격
- 설명 문장 템플릿
- 양성·음성 테스트 예시
- 예상 계산 비용

#### 자연어 룰 생성 과정

예를 들어 사용자가 다음처럼 입력을 하면
```
개인 고객이 7일 동안 회사 기준금액의
90% 이상 100% 미만인 현금 입금을
3회 이상 하면 분할입금으로 탐지해줘.
```

LLM은 SQL을 만드는 것이 아니라 다음과 같은 구조화된 초안을 생성
```
{
  "templateId": "STRUCTURING_DEPOSIT_V1",
  "scope": {
    "type": "ACCOUNT",
    "groupBy": ["account_id"]
  },
  "window": {
    "value": 7,
    "unit": "DAY"
  },
  "filters": {
    "all": [
      {
        "field": "customer_type",
        "operator": "EQ",
        "value": "INDIVIDUAL"
      },
      {
        "field": "direction",
        "operator": "EQ",
        "value": "IN"
      },
      {
        "field": "payment_format",
        "operator": "EQ",
        "value": "CASH"
      },
      {
        "field": "amount_base",
        "operator": "BETWEEN",
        "lower": {
          "multiply": [
            "${company.reporting_threshold}",
            0.9
          ]
        },
        "upper": "${company.reporting_threshold}"
      }
    ]
  },
  "metrics": [
    {
      "name": "transaction_count",
      "aggregate": "COUNT"
    },
    {
      "name": "total_amount",
      "aggregate": "SUM",
      "field": "amount_base"
    }
  ],
  "conditions": {
    "all": [
      {
        "metric": "transaction_count",
        "operator": "GTE",
        "value": 3
      }
    ]
  },
  "action": {
    "type": "EMIT_SIGNAL",
    "code": "STRUCTURING_DEPOSIT",
    "severity": "HIGH"
  }
}
```

시스템은 이를 다시 사용자에게 읽기 쉬운 문장으로 보여준다.

```
개인 고객의 계좌를 기준으로 최근 7일 동안
회사 기준금액의 90% 이상 100% 미만인
현금 입금이 3건 이상이면
고위험 분할입금 신호를 생성합니다.
```

이때 애매한 자연어는 자동 추정하지 않고 시스템에서 빠진 파라미터를 표시해줘야 한다.

```
고위험 고객이 짧은 기간에 큰 금액을 여러 번 송금하면 알려줘.

      ↓

확정되지 않은 항목

- 짧은 기간: 미설정
- 큰 금액: 미설정
- 여러 번: 미설정
- 송금 대상 범위: 국내/해외/고위험 국가 미설정

      ↓  

후보값 추천

기간 후보: 24시간 / 7일 / 30일
금액 후보: 회사 기준금액 / 정상분포 상위 1% / 직접 입력
횟수 후보: 3회 / 5회 / 직접 입력
```

허용할 Rule DSL 범위

비교연산
- EQ, NE, GT, GTE, LT, LTE, BETWEEN, IN

논리연산
- ALL(AND), ANY(OR), NOT

집계
- COUNT, SUM, AVG, MAX, MIN, DISTINCT_COUNT

시간 관계
- WITHIN, BEFORE, AFTER, SEQUENCE, TIME_GAP

행동·통계
- BASELINE_RATIO, PERCENTILE, ZSCORE, DORMANT_DAYS

그래프 관계
- FAN_IN_DEGREE, FAN_OUT_DEGREE, PATH_LENGTH, CYCLE_EXISTS, SHARED_COUNTERPARTY_COUNT

자연어에서 이 목록 밖의 연산이 나오면 실행 룰로 만들지 않고 지원하지 않는 조건으로 반환

#### 자연어 모델의 역할 제한

자연어 모델은 **룰을 직접 실행하는 엔진이 아니라, 사용자의 의도를 Rule DSL 초안으로 바꾸는 작성 보조 도구**로만 사용한다.

자연어 모델이 담당하는 역할
- 사용자의 문장에서 대상, 기간, 금액, 횟수, 거래 방향 등의 조건 추출
- 가장 가까운 룰 템플릿 추천
- 허용된 Rule DSL 형식으로 초안 생성
- 설정되지 않았거나 서로 충돌하는 조건 표시
- 완성된 Rule DSL을 사용자가 이해할 수 있는 문장으로 재설명
- 기존 룰과 유사하거나 중복될 가능성이 있는 경우 비교 대상 추천

자연어 모델이 하면 안 되는 역할
- SQL, Python 코드 또는 실행 쿼리를 직접 생성하여 실행
- 시스템에 존재하지 않는 데이터 필드나 연산자를 임의로 생성
- `큰 금액`, `짧은 기간`, `여러 번`과 같은 표현의 값을 임의로 확정
- 법적 기준이나 회사 내부 기준을 임의로 결정 또는 변경
- 룰의 위험도와 운영 우선순위를 근거 없이 결정
- 백테스트, 승인, Shadow 운영을 생략하고 룰을 바로 활성화
- 승인자의 결정을 대신하거나 운영 중인 룰을 자동 수정
- 입력 문장에 포함된 지시를 이유로 권한, 검증, 승인 절차를 우회

즉, 자연어 모델의 결과는 항상 다음 상태로 저장한다.

```
LLM 출력 = 실행 불가능한 DRAFT

DRAFT
→ DSL 스키마 검증
→ 데이터·의미 검증
→ 사용자의 조건 확인
→ 백테스트
→ 승인
→ Shadow 운영
→ ACTIVE 전환
```

자연어 모델이 잘못된 결과를 만들더라도 검증기를 통과하지 못하면 실행 단계로 넘어가지 못하도록 해야 한다. 또한 자연어 입력, 모델이 만든 초안, 사용자가 수정한 내용, 최종 승인본을 모두 따로 저장하여 어떤 값이 누구에 의해 바뀌었는지 확인할 수 있어야 한다.

#### 회사 정책 프로필과 룰 파라미터 분리

금액 기준, 고위험 국가 목록, 휴면 기준 등은 룰마다 직접 입력하지 않고 회사 정책 프로필에서 가져올 수 있도록 한다.

회사 정책 프로필 예시

```
company_policy_profile
├─ 기준 통화
├─ 영업일·시간대·일자 마감 기준
├─ 고객 위험등급
├─ 개인·법인·업종별 고객군
├─ 고위험 국가 목록
├─ 고위험 상품·채널 목록
├─ 회사 기준금액
├─ 휴면계좌 기준일수
├─ 화이트리스트와 적용 사유
└─ 일별 Alert 처리 가능량
```

Rule DSL에는 실제 값 대신 정책 변수의 참조를 저장할 수 있다.

```
"lower": {
  "multiply": [
    "${company.reporting_threshold}",
    0.9
  ]
}
```

룰을 실행할 때는 정책 변수를 실제 값으로 치환한 **해결된 실행본**을 별도로 만든다. 이후 회사 정책값이 변경되더라도 과거에 어떤 기준으로 탐지했는지 재현할 수 있도록 아래 정보를 실행 이력에 함께 저장해야 한다.

- 룰 버전
- 회사 정책 프로필 버전
- 실제로 치환된 파라미터 값
- 실행 대상 데이터 기간
- 기준 통화와 환율 기준일
- 시간대와 일자 마감 기준

정책값이 바뀌었다고 기존 운영 룰에 즉시 반영하면 Alert 수가 갑자기 달라질 수 있다. 따라서 정책 변경도 새 룰 버전과 동일하게 영향도 확인, 승인, 적용일 지정을 거치도록 한다.

#### Rule DSL 검증 단계

Rule DSL은 저장 직후부터 실행 전까지 여러 단계로 검증한다.

##### 구문 검증
- JSON Schema에 맞는 구조인지 확인
- 필수 필드가 존재하는지 확인
- 허용된 필드, 연산자, 집계함수만 사용했는지 확인
- 값의 자료형과 단위가 맞는지 확인
- 지원하지 않는 DSL 버전인지 확인

##### 의미 검증
- 거래 단위 룰에서 계좌 집계 조건을 잘못 사용하지 않았는지 확인
- `BETWEEN`의 하한이 상한보다 작은지 확인
- 입금 룰에 송금인 기준 필드를 잘못 사용하지 않았는지 확인
- 기간, 횟수, 금액 조건이 모두 확정되었는지 확인
- 기준 통화가 다른 금액을 환산 없이 비교하지 않는지 확인
- 미래 정보가 과거 탐지에 사용되는 데이터 누수가 없는지 확인

##### 데이터 검증
- 고객사 데이터에 해당 필드가 실제로 존재하는지 확인
- 필드의 결측률과 최신 적재 시점을 확인
- 고객, 계좌, 거래 식별자의 연결이 가능한지 확인
- 그래프 룰에 필요한 출발·도착 계좌 정보가 존재하는지 확인

##### 실행 비용 검증
- 예상 스캔 거래 수
- 예상 실행시간과 메모리 사용량
- 그래프 탐색의 최대 깊이와 최대 노드·엣지 수
- 너무 긴 기간이나 제한 없는 경로 탐색 여부
- 운영 배치시간 내 완료할 수 있는지 여부

##### 중복·충돌 검증
- 기존 룰과 조건이 거의 같은지 확인
- 기존 룰의 범위에 완전히 포함되는지 확인
- 한 룰은 제외하고 다른 룰은 포함하는 상충 조건이 있는지 확인
- 동일한 거래에서 과도하게 많은 신호가 발생할 가능성이 있는지 확인

검증 실패는 오류와 경고로 나눈다. 오류가 있으면 백테스트와 실행을 막고, 경고는 사유를 확인한 후 사용자가 계속 진행할 수 있도록 한다.

#### 룰 컴파일과 실행 구조

검증된 Rule DSL은 서버에서 내부 실행계획으로 변환한다.

```
자연어 입력
→ Rule DSL 초안
→ DSL Validator
→ 검증된 AST
→ Execution Planner
→ 파라미터화된 SQL 또는 그래프 연산
→ Rule Worker 실행
→ Rule Signal 저장
```

- `DSL Validator`: 문법, 의미, 데이터 필드, 권한을 검증
- `AST`: 검증을 마친 조건 트리. 문자열 코드를 그대로 실행하지 않음
- `Execution Planner`: 조건의 순서와 필요한 집계를 결정
- `SQL Compiler`: 단건·기간 집계 룰을 파라미터화된 쿼리로 변환
- `Graph Operator`: FAN-IN, FAN-OUT, 순환거래, 공유 상대방 등의 제한된 그래프 연산 수행
- `Rule Worker`: 정해진 데이터 기준시점과 룰 버전으로 실행하고 결과 저장

사용자 또는 자연어 모델이 만든 문자열을 `eval`하거나 그대로 SQL에 붙이는 방식은 사용하지 않는다. 필드명과 연산자는 서버의 허용 목록에서만 선택하고, 값은 바인딩 파라미터로 전달한다.

룰은 실행 특성에 따라 세 종류로 구분할 수 있다.

| 실행 유형 | 대상 | 예시 |
|---|---|---|
| 단건 룰 | 거래 1건 | 단건 고액, 고위험 국가 송금 |
| 기간 집계 룰 | 계좌·고객×기간 | 분할거래, 평소 대비 급증, 휴면계좌 활성화 |
| 그래프 룰 | 제한된 서브그래프 | FAN-IN, FAN-OUT, 순환거래, 다단계 자금 통과 |

초기 버전은 일 배치 실행을 기본으로 한다. 실시간 차단 시스템이 아니라 사후 의심거래 탐지 시스템이므로 모든 룰을 스트리밍 방식으로 구현할 필요는 없다. 단건 룰과 짧은 기간 집계 룰만 이후 준실시간 실행 대상으로 확장할 수 있다.

#### 룰과 GNN 탐지 결과의 결합

룰엔진과 GNN은 직렬이 아니라 병렬로 전체 대상 거래를 검사한다.

```
                    ┌→ 룰엔진 ──→ Rule Signal ─┐
거래·계좌 데이터 ──┤                           ├→ 신호 병합 → Alert 생성
                    └→ GNN 모델 → Model Signal ┘
```

룰에서 걸리지 않은 거래만 GNN에 넣으면 룰의 탐지 범위가 모델의 입력 범위를 제한하게 된다. 반대로 GNN에서 걸린 거래만 룰로 검사하면 규정·정책상 반드시 확인해야 하는 거래를 놓칠 수 있다. 따라서 두 탐지기는 독립적으로 실행하고 결과 단계에서 결합한다.

두 탐지 결과는 공통된 `detection_signal` 구조로 저장한다.

```
detection_signal
├─ signal_id
├─ source_type          // RULE 또는 MODEL
├─ source_id            // rule_version_id 또는 model_version_id
├─ subject_type         // TRANSACTION, ACCOUNT, CUSTOMER, SUBGRAPH
├─ subject_id
├─ window_start / window_end
├─ signal_code
├─ severity
├─ matched_transaction_ids
├─ evidence
├─ execution_id
└─ created_at
```

룰 신호의 `severity`는 룰 작성자가 승인한 정책 등급이며 모델 확률과 같은 의미가 아니다. 모델 신호의 점수, 룰 적중 여부, 거래금액 등을 단순히 더해서 하나의 확률처럼 표시하면 안 된다. Alert 위험도와 조사 우선순위 산식은 별도 정책으로 관리한다.

Rule Signal과 Model Signal이 다음 조건을 만족하면 하나의 Alert에 함께 넣을 수 있다.
- 동일한 핵심 거래가 포함됨
- 동일한 계좌 또는 고객을 중심으로 시간창이 겹침
- 한 신호의 핵심 거래가 다른 신호의 탐색 서브그래프에 포함됨

단순히 위험도가 비슷하거나 유형명이 같다는 이유만으로는 병합하지 않는다. 병합된 Alert에서는 `GNN 고위험 탐지`, `분할입금 룰 적중`과 같이 출처별 근거를 각각 보여준다.

#### 룰 생명주기와 승인 절차

룰은 다음 상태를 갖는다.

```
DRAFT
→ VALIDATED
→ BACKTESTED
→ PENDING_APPROVAL
→ SHADOW
→ ACTIVE
→ PAUSED
→ RETIRED
```

| 상태 | 의미 |
|---|---|
| DRAFT | 자연어 또는 화면에서 작성 중인 상태 |
| VALIDATED | DSL과 데이터 검증을 통과한 상태 |
| BACKTESTED | 과거 데이터 영향도 확인을 마친 상태 |
| PENDING_APPROVAL | 운영 적용 승인을 기다리는 상태 |
| SHADOW | 결과는 저장하지만 운영 Alert에는 반영하지 않는 상태 |
| ACTIVE | 운영 Alert 생성에 사용하는 상태 |
| PAUSED | 일시 중지했지만 버전과 이력을 보존하는 상태 |
| RETIRED | 더 이상 사용하지 않는 종료 상태 |

작성자와 승인자는 분리하는 것이 좋다. 최소한 ACTIVE 전환, 임계값 변경, 적용 대상 확대는 별도 승인자가 확인하도록 한다.

운영 중인 룰은 직접 수정하지 않고 항상 새 버전을 만든다.

```
RULE-001 v1  ACTIVE
        ↓ 수정
RULE-001 v2  DRAFT → 검증 → 백테스트 → 승인 → Shadow
        ↓ 적용일 도달
RULE-001 v1  RETIRED
RULE-001 v2  ACTIVE
```

각 버전에는 작성 사유, 변경 전후 비교, 작성자, 승인자, 적용일, 종료일, 근거 문서, 백테스트 결과를 보존한다. 긴급 중지는 가능하게 하되 중지자와 사유를 반드시 기록한다.

#### 백테스트와 Shadow 운영

백테스트는 룰이 문법적으로 실행되는지만 확인하는 과정이 아니라 운영에 미칠 영향을 사전에 확인하는 과정이다.

필수 확인 항목
- 적중 거래 수
- 적중 계좌·고객 수
- 예상 Alert 수와 일별 최대 발생량
- 기존 룰과 겹치는 비율
- GNN Alert와 겹치는 비율
- 새 룰만 추가로 찾는 거래와 Alert 수
- 고객군·상품·채널별 적중 분포
- 과거 분석가 처리 결과가 있다면 관심·비관심 비율
- 실행시간, 스캔량, 메모리 사용량

임계값 후보가 여러 개라면 한 값만 보여주지 않고 비교표를 제공한다.

| 기준금액 비율 | 기간 | 횟수 | 적중 고객 | 예상 Alert/일 | 기존 탐지와 중복 |
|---:|---:|---:|---:|---:|---:|
| 80% | 7일 | 3회 | 1,240 | 310 | 72% |
| 90% | 7일 | 3회 | 620 | 145 | 58% |
| 90% | 7일 | 5회 | 210 | 48 | 41% |

운영 임계값 위의 Alert만 확인하면 임계값 바로 아래에서 놓친 거래를 알기 어렵다. 따라서 가능하면 다음 두 표본을 함께 검토한다.
- ATL: 임계값 위에서 발생한 탐지 표본
- BTL: 임계값 아래에서 발생하지 않은 거래 표본

Shadow 상태에서는 운영 데이터로 룰을 실행하고 결과를 저장하지만 조사자의 기본 Alert Queue에는 넣지 않는다. 일정 기간 동안 예상 Alert 수, 다른 탐지와의 중복, 분석가 표본 검토 결과, 실행 안정성을 확인한 뒤 ACTIVE로 전환한다.

#### 화이트리스트와 예외 처리

화이트리스트는 해당 고객이 안전하다는 의미가 아니라 **특정한 정상 업무 특성 때문에 특정 룰이 반복 적중할 수 있다는 예외 정보**로 관리한다.

예를 들어 공익사업자가 다수 개인에게 정기적으로 입금받는다는 이유로 FAN-IN 룰의 예외가 될 수는 있지만, 고위험 국가의 신규 법인에 거액을 반복 송금하는 다른 룰까지 제외되어서는 안 된다.

화이트리스트는 다음 범위를 명확하게 가져야 한다.
- 적용 대상 고객·계좌
- 적용 룰 또는 시나리오
- 예외 사유와 근거
- 승인자
- 유효 시작일과 만료일
- 정기 재검토일

룰 계산 자체에서 거래를 완전히 제거하기보다는 원래 탐지 결과를 저장하고, Alert 생성 단계에서 억제 또는 별도 표시하는 편이 안전하다. 그래야 예외 적용 전후의 결과를 감사하거나 새로운 위험 신호와 결합해 다시 확인할 수 있다.

#### 저장 구조

최소한 다음 테이블이 필요하다.

| 테이블 | 역할 |
|---|---|
| `rule_templates` | 시스템이 제공하는 검증된 템플릿 |
| `rules` | 회사별 룰의 대표 식별자와 현재 상태 |
| `rule_versions` | DSL, 설명, 파라미터, 적용기간을 포함한 불변 버전 |
| `rule_approvals` | 요청·승인·반려와 의견 이력 |
| `rule_backtests` | 데이터 기간, 후보값, 결과 지표 |
| `rule_executions` | 운영·Shadow 실행 단위와 성공·실패 정보 |
| `rule_hits` | 룰이 탐지한 대상과 시간창 |
| `rule_hit_transactions` | 적중 근거가 된 거래 목록과 역할 |
| `detection_signals` | 룰과 모델 결과를 Alert 전에 통합하는 공통 신호 |
| `rule_exceptions` | 룰별 화이트리스트와 유효기간 |
| `rule_audit_logs` | 생성·수정·검증·승인·중지 등 전체 감사 이력 |

`rule_versions`에는 자연어 원문, 자연어 모델 버전, 모델이 처음 만든 DSL, 사용자가 수정한 최종 DSL을 각각 저장한다. 운영 재현을 위해 실행 당시 해결된 회사 정책값도 `rule_executions`에 스냅샷으로 남긴다.

#### 사용자 화면 구성

##### 룰 목록
- 상태, 버전, 적용 대상, 마지막 실행일
- 최근 적중 수와 예상 Alert 수
- 담당자와 승인자
- 룰 성능 저하 또는 실행 실패 알림

##### 룰 작성 화면
- 템플릿 선택
- 자연어 입력
- 자연어 모델이 추출한 조건
- 확정되지 않은 파라미터
- IF/THEN 시각 편집기
- Rule DSL 원문은 고급 사용자에게만 선택적으로 제공
- 최종 자연어 설명과 테스트 예시

##### 백테스트 화면
- 후보 파라미터별 Alert 발생량 비교
- 날짜·고객군·상품별 적중 분포
- 기존 룰 및 GNN과의 중복·추가 탐지량
- 적중 거래 표본과 미탐지 거래 표본 검토
- 실행시간과 예상 운영 비용

##### 승인 화면
- 변경 전후 조건 비교
- 작성 사유와 근거 문서
- 백테스트 결과
- 예상 Alert 증가·감소량
- 승인, 반려, 수정 요청과 의견 기록

##### Alert 상세 화면
- 어떤 룰의 몇 번째 버전이 적중했는지 표시
- 적중한 조건과 실제 측정값 비교
- 룰의 근거 거래 강조
- GNN 탐지 결과가 함께 있는 경우 출처별 근거를 분리해 표시

예를 들어 단순히 `분할입금 룰 적중`이라고만 보여주는 것이 아니라 다음처럼 설명한다.

```
분할입금 룰 RULE-014 v3 적중

- 관찰 기간: 2026-09-01 ~ 2026-09-07
- 기준: 회사 기준금액의 90% 이상 100% 미만
- 실제 거래: 4건
- 실제 합계: 38,400,000원
- 조건: 3건 이상
- 관련 거래: TX-101, TX-108, TX-115, TX-121
```

#### 초기 개발 범위

처음부터 모든 자연어와 복잡한 그래프 룰을 지원하면 검증 범위가 너무 커진다. MVP에서는 아래 범위로 제한하는 것이 좋다.

지원 템플릿
1. 단건 고액거래
2. 분할 입·출금
3. FAN-IN
4. FAN-OUT
5. 급속 자금 통과

지원 기능
- 템플릿 선택과 자연어 기반 파라미터 추출
- 허용된 Rule DSL 초안 생성
- IF/THEN 시각 편집 및 자연어 재설명
- 구문·의미·데이터 검증
- 과거 데이터 백테스트
- 버전관리와 승인
- Shadow·ACTIVE 실행
- Rule Signal과 GNN Model Signal의 공통 저장
- Alert 상세에서 룰 적중 근거 제공
- 모든 변경과 실행의 감사 로그

초기에는 일 배치 기반으로 구현하고, 순환거래와 임의 경로 탐색, 실시간 스트리밍 룰, 자동 임계값 최적화는 이후 단계로 둔다. 이 범위라면 자연어 룰 생성이라는 기능적 차별점을 보여주면서도 룰이 통제 없이 실행되는 위험을 막고, 실제 AML 업무에 필요한 검증·승인·설명 가능성까지 함께 시연할 수 있다.
