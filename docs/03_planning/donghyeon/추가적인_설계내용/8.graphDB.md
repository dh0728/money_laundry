## 관계형 VS 그래프 DB

| 항목 | 관계형만 (지금) | 하이브리드 (PostgreSQL + 그래프 DB) |
|---|---|---|
| 1~2단계 연결 조회 | 인덱스로 충분히 빠름 | 빠름 (차이 거의 없음) |
| 3단계 이상 경로, 순환 찾기 | 재귀 쿼리로 가능하지만 쓰기 어렵고 데이터가 크면 느려짐 | **강점.** 쿼리가 짧고 깊어져도 잘 버팀 |
| 집계·정렬·날짜 범위 (대시보드, 목록) | **강점** | 약함. 어차피 PostgreSQL에서 해야 함 |
| 데이터 일치 | 저장소가 하나라 항상 일치 | **약점.** 거래 통합·정정이 생길 때마다 그래프에도 반영해야 하고, 실패하면 두 곳이 어긋남 |
| 재현성 | 분석마다 입력을 고정해 두고 씀 | 그래프 DB는 "현재 상태"만 들고 있어서 Alert 생성에는 못 쓰고 탐색용으로만 가능 |
| 개인정보 | 실명·계좌번호 암호화가 한 곳 | 가명 규칙과 접근 통제를 두 곳에 구현 |
| 운영 | EC2 한 대, DB 하나 | DB가 하나 더 (메모리, 백업, 모니터링, 장애 지점) |
| 개발 | 팀이 아는 SQL | 새 쿼리 언어, 동기화 코드, 테스트 환경 추가 |
| 화면 | Alert 안의 그래프는 스냅샷으로 표시 | 계좌를 눌러 계속 넓혀 가는 탐색 화면을 만들기 쉬움 |

## Graph DB를 사용했을 때 장점

| 이점 | 지금 | 그래프 DB가 있으면 |
|---|---|---|
| **1. 자유 탐색** | 그래프는 Alert에 담긴 최대 100건, 2단계까지만 보임 | 계좌를 누를 때마다 주변을 넓혀 감. "시스템이 못 본 범위"를 조사자가 직접 확인 |
| **2. 경로 찾기** | 두 Alert의 연결은 같은 거래·계좌·소유주, 직접 거래까지만 판단 | "두 Alert가 어느 쪽에도 없는 계좌 2개를 거쳐 이어진다" 같은 간접 연결을 찾음 |
| **3. 모양으로 찾기** | 순환거래 같은 템플릿은 "이후 단계"로 잠가 둠 | 순환, 모았다 뿌리기 같은 모양을 쿼리 한 줄로 찾아서 룰 템플릿으로 쓸 수 있음 |
| **4. 묶음 자동 제안** | Episode 후보는 조사자가 Alert 하나씩 보고 찾음 | 연결된 덩어리를 찾는 알고리즘으로 "이 Alert 5개가 한 덩어리"를 먼저 제안 |
| **5. 주변 이력** | "이 계좌를 전에 본 적 있나"만 가능 | "이 계좌에서 2단계 안에 과거 의심 판정 건이 있나"까지 가능 |
| **6. 모델 설명** | 씨앗 거래의 "모델이 본 이웃"을 보여줄 자리가 비어 있음 | 거래 1건의 k단계 주변을 바로 뽑아 설명 기법(GNNExplainer 등)에 넘기기 쉬움 |
| **7. 자연어 질문** | 불가 | LLM이 질문을 그래프 쿼리로 바꿔 답하는 구조가 가능 (아래 "일반 RAG VS GraphRAG"와 이어지는 부분) |
| **8. 눈으로 확인** | SQL 결과를 표로만 확인 | 그래프 DB에 딸린 시각화 도구로 데이터를 바로 그려 보며 디버깅·시연 |

## 일반 RAG VS GraphRAG

|  | 일반 RAG | GraphRAG |
|---|---|---|
| 미리 하는 일 | 문서를 조각으로 잘라 벡터로 저장 | 조각마다 LLM이 엔티티(사람·회사 등)와 관계를 뽑아 **그래프**를 만들고, 뭉쳐 있는 덩어리별로 **요약**까지 써 둠 |
| 찾아오는 것 | 질문과 비슷한 조각 몇 개 | 질문에 나온 엔티티와 그 이웃·관계, 또는 덩어리 요약 |
| 잘하는 질문 | "X가 뭐야?"처럼 답이 한 곳에 있는 질문 | 여러 문서에 흩어진 사실을 이어야 하는 질문, "전체적으로 어떤 주제가 있어?" 같은 질문 |
| 준비 비용 | 낮음 (임베딩만) | 높음 (조각마다 LLM 호출) |
| 약점 | 사실이 흩어져 있으면 못 이음 | 추출이 틀리면 그래프가 틀림, 문서가 바뀌면 다시 만들기 번거로움 |

## 결론
그래프와 링크를 다양하게 구성을 해야할때 그래프 DB를 사용하는건데 지금 현재로 봤을 때는 그정도는 필요 없을
거 같다.(노드종류 엣지종류이게 다양해야 그래프 DB로 가는거임 지금은 모두 계좌이고 이체로 하나씩이라 필요 없을 듯)

그래프 DB로 가는 기준
1. 종류가 다양한가 - 노드·엣지 종류가 많아서 테이블과 조인이 계속 늘어남
  - 계좌 — 이체 — 계좌 한 가지. 소유주·은행까지 쳐도 3~4종
2. 깊이 따라가는가 - 3단계 이상 경로, 순환 같은 탐색이 자주 필요
  - 연관 Alert, 같은 소유주 모두 1~2단계
