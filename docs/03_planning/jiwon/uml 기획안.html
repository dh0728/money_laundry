2.1 식별자·멱등·커서 계약

transaction_id는 전송 요청 ID가 아니라 원천 거래내역의 거래번호다. 전송·추론·화면 갱신 식별자를 분리해 서로 다른 재시도 의미가 섞이지 않게 한다.

식별자의미·발급 주체계약
transaction_id원천 시스템의 거래번호거래 원장의 업무 식별자. 전송 시도 횟수를 세는 ID가 아니다. 동일 공급원에서 같은 거래번호·같은 표준화 payload면 같은 거래의 재전송으로 흡수하고, 내용이 다르면 조용히 무시하지 않고 ID_CONFLICT로 격리한다. 다중 공급원 도입 시 유일 키는 (source_id, transaction_id).
ingest_id수신 관문이 전송 시도마다 발급202 ACK·큐 메시지·수신결과 로그를 잇는 UUID. 같은 거래의 재전송도 서로 다른 ingest_id를 가진다. 수신 회계는 거래 행 수가 아니라 ingest_id 상태 합계로 검증한다.
payload_hash수신 관문이 표준화 payload에서 계산같은 거래번호의 정상 재전송과 ID 충돌을 구분한다. 해시는 업무 데이터의 대체키가 아니라 충돌 탐지 보조값.
job_id배치 워커가 추론 작업마다 발급작업 자체의 식별자. 결과 멱등 키 (job_id, model_version)의 구성요소.
attempt_id·lease작업 선점 때마다 발급타임아웃 재선점과 이전 실행을 구분. 결과 제출은 현재 INFERENCING 상태이고 lease가 유효하며 attempt_id가 일치할 때만 수락한다.
change_seqDB가 변경 때 단조 증가 발급피드 커서. 변경시각 단독 커서의 동률 누락을 피하며 change_seq > cursor로 신규·판정 갱신을 함께 조회한다.

3. 유저 스토리

형식: 역할 관점 스토리 + Given/When/Then 수용 기준(AC). 각 AC는 구현 시 테스트 케이스의 뿌리가 된다.

3.1 모니터링팀

ID스토리수용 기준 (AC)연계
US-01 MVP모니터링 담당자로서, 거래가 들어오면 즉시 목록에서 확인하고 싶다. 판정을 기다리느라 거래 자체를 못 보는 일이 없어야 하기 때문이다.

  • Then 커서는 단조 증가 change_seq라 같은 시각에 여러 행이 바뀌어도 누락되지 않는다

3.2 분석팀

ID스토리수용 기준 (AC)연계
US-05 MVP분석가로서, 알림들을 묶어 사건을 만들고 싶다. 흩어진 알림 단위로는 조사를 관리할 수 없기 때문이다.

3.4 시스템 스토리 (비기능 — 데모 검증 항목)

액터가 사람이 아닌 스토리. 성공 지표(기획서 §4)의 서비스 지표와 직결되며, 각각 데모에서 시연 가능한 형태로 쓴다.

4. 시퀀스 다이어그램

실선 = 동기 호출, 점선 = 응답/비동기 전달, 점선 사각형 = 대안 흐름(alt)/반복(loop). 각 다이어그램 내 번호는 독립 (아키텍처 구조도 ①~⑨와 별개).

S1. 거래 수신·적재 (UC-08) — 관문 검증, 최소 1회 전달, 멱등 적재

  • ⑥ ACK는 투입 확인이 돌아온 뒤에만 나가며 수신 시도 식별자 ingest_id를 반환한다. 원천 거래번호 transaction_id는 ACK 횟수나 큐 전달 횟수를 세는 ID가 아니다. 투입 실패면 ACK 대신 5xx가 나가고, 생성기 재시도가 유실을 막는다.
  • ⑦은 큐가 밀어주는 게 아니라 워커가 가져가는 pull — SQS의 실제 소비 방식이자, S2 에이전트 폴링과 같은 주도권 방향.
  • ⑨의 순서(쓰기→ACK)가 유실 방지의 핵심 불변식 (Q-1). 워커가 ⑧과 ⑨ 사이에서 죽으면 같은 큐 메시지가 재전달되고, 거래 업무키와 payload_hash가 동일내용 재전송과 ID 충돌을 구분한다.
  • 수신 회계는 transaction_id 행 수와 202 응답 횟수를 직접 비교하지 않는다. ingest_id별 처리대기·신규적재·동일내용중복·ID충돌·DLQ 합계가 ACK 합계와 맞는지 검증한다.
  • 관련 결정: §6 수집 경계, Q-1~5. 의미 이상(형식은 유효) 거래는 ④가 아니라 ⑤~⑧ 경로로 가되 격리 플래그를 달고 저장된다.

S2. 5분 배치 추론 (UC-09·10) — pull 방식 원격 추론과 원자적 결과 기록

  • 타이머 소유권: "5분"의 의미는 배치 워커의 선점 타이머(①) 한 곳에만 있다 — 토픽 2의 구현 지점. 에이전트의 2분 폴링은 배치 의미가 없는 전송 간격이며, 짧을수록 픽업 지연만 줄어든다 (판정 지연 = 배치 대기 0~5분 + 픽업 ≤2분 + 추론 + 제출).
  • ①~④(준비)와 ⑤~⑭(실행)은 직접 연결되지 않는다 — 접점은 DB에 저장된 작업뿐. pull 방식(G-1)이라 클러스터 쪽에서만 접속을 시작하며, 작업이 DB에 남아 있어 어느 쪽이 죽어도 증발하지 않는다.
  • ⑨의 반환이 있어야 ⑩의 "양성만" 필터가 성립한다 — 1단계 결과를 에이전트가 받아 2단계 입력을 구성.
  • ⑭는 ⑬(기록) 완료 후에 나간다. 응답이 유실되면 같은 시도의 재제출은 (작업 ID, 모델 버전) 유니크 제약이 중복 결과·중복 알림을 흡수한다. 타임아웃 뒤 이전 시도가 늦게 제출한 결과는 현재 상태·attempt_id·lease 조건부 갱신이 거절한다.
  • ⑬은 결과 기록과 알림 생성이 같은 DB 트랜잭션 (A-1). 상태는 COMPLETED로 전환.
  • 클러스터 전체가 다운되면 ⑤가 멈출 뿐 — 작업은 적체되고 수집·조회는 정상 (G-3, US-14).

S3. 대시보드 실시간 갱신 (UC-01) — 커서 polling

  • ①~③(최초 접속)이 없으면 새 세션은 빈 화면에서 새 이벤트만 기다리게 된다 — 스냅숏 + 커서 발급이 진입점.
  • 하나의 엔드포인트가 "신규 도착"과 "판정 갱신"을 모두 나른다 — 프론트는 원천 거래번호 transaction_id로 행을 찾아 갱신한다. 서버 커서는 별도의 단조 증가 change_seq라 같은 시각의 다중 변경과 페이지 경계에서도 누락되지 않는다.
  • 페이지 응답은 조회 시작 시점의 high-watermark를 고정하고, next_cursor가 그 범위를 모두 소진한 뒤에만 다음 high-watermark로 전진한다.
  • 실시간 푸시(WebSocket)는 스트레치 — 이 API 구조를 바꾸지 않고 병렬 채널로 추가 가능 (부착점 원칙).

S4. 알림 검토 → 사건 조사 (UC-02·03·04) — 사람의 업무 흐름

  • 알림 생명주기 = 4상태: NEW → 검토중 → 조사중(이관) → 종결. 종결 경로는 둘 — 오탐(모니터링, 검토 단계 조기 종결) / 조사 결과(분석, 결과 입력과 함께). 이관은 업무 구두 절차가 아니라 시스템 상태 전환이라, 큐 가시성(누구 화면에 뜨는가)이 상태로 자동 결정된다.
  • ⑫는 사건에 연결된 대상 알림을 각각 종결한다. ⑬ 사건 종결의 허용 조건과 알림 1건의 복수 사건 연결 허용 여부는 팀 결정 전까지 미확정으로 둔다.
  • ⑨의 허브 가드: 허브 계좌(세트당 15개, 2-hop 폭발 유발)는 이웃을 펼치지 않고 요약만 반환 (§10, US-06).

문서 상태: 유스케이스 UC-01~10, 유저 스토리, 시퀀스 4종은 확정 아키텍처(§5~9)에서 직접 도출. 식별자 계약은 원천 거래번호 transaction_id와 전송 시도 ingest_id를 분리하고, 추론 재선점은 attempt_id·lease, 피드 커서는 change_seq를 사용한다. UC-11·12와 US-04, US-08 일부 표시 항목(규칙 히트·유사 사례), 사건 종결 조건은 팀 협의 대기. 폴링 주기·타임아웃 등 수치는 구현 시 확정. STR·의심계좌 뷰 관련 시퀀스는 팀 결정 후 추가.
