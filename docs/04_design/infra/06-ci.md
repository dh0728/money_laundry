# CI 기본 개념

[인프라 결정 기록으로 돌아가기](README.md)

## CI란?

CI(Continuous Integration, 지속적 통합)는 개발자가 코드를 자주 합치고 변경할 때마다 검사와 테스트를 자동으로 실행하는 개발 방식이다. 문제가 있는 변경을 빠르게 발견하고 코드가 항상 빌드 가능한 상태인지 확인하는 것이 목적이다.

```mermaid
flowchart LR
    Push[코드 변경] --> Lint[정적 검사]
    Lint --> Test[자동 테스트]
    Test --> Build[빌드]
    Build --> Image[Docker 이미지 생성]
```

## 기본 용어

- **Workflow/Pipeline**: 자동화할 작업과 실행 순서를 정의한 전체 흐름
- **Job**: 하나의 실행 환경에서 수행하는 작업 묶음
- **Step**: Job 안에서 실행되는 개별 명령
- **Runner/Agent**: CI 작업을 실제로 실행하는 컴퓨터나 프로세스
- **Artifact**: 빌드 결과물, 테스트 보고서처럼 CI가 생성해 보관하는 파일
- **Trigger**: Push, Pull Request, 태그처럼 Workflow 실행을 시작하는 사건
- **Lint**: 코드 형식, 문법과 잠재적인 문제를 정적으로 검사하는 과정
- **Build**: 소스 코드를 실행 또는 배포 가능한 결과물로 만드는 과정

## 제공 Runner와 Self-hosted Runner

제공 Runner는 CI 서비스 업체가 준비하고 관리하는 실행 환경이다. Self-hosted Runner는 팀이 준비한 서버에서 CI 작업을 실행하는 방식이다. 후자는 내부 자원 접근과 환경 제어가 쉽지만 보안, 업데이트와 용량을 직접 관리해야 한다.

## CI와 CD의 차이

CI는 변경을 검사하고 배포 가능한 결과물을 만드는 과정이다. CD는 검증된 결과물을 실제 실행 환경에 전달하고 적용하는 과정이다. 두 과정은 연결할 수 있지만 권한과 실패 영향이 다르므로 별도로 설계할 수 있다.

## 주요 CI 도구

### GitHub Actions

GitHub Actions는 GitHub 저장소의 Push, Pull Request, 태그와 수동 실행 같은 이벤트에 따라 Workflow를 실행하는 자동화 서비스다. Workflow는 `.github/workflows/` 디렉터리의 YAML 파일로 정의하며 Job은 GitHub 제공 Runner나 Self-hosted Runner에서 실행된다.

### GitHub 제공 Runner

GitHub가 준비하고 관리하는 CI 실행 환경이다. Job마다 제공되는 실행 환경에서 저장소 코드를 내려받아 명령을 수행하고, 작업이 끝나면 해당 환경을 폐기하는 방식으로 사용된다.

### GitHub Actions Self-hosted Runner

팀이 소유하거나 임대한 서버에 설치하는 GitHub Actions 실행 프로그램이다. GitHub로부터 Job을 받아 로컬 환경에서 수행하므로 내부 시스템이나 특정 하드웨어에 접근할 수 있다. Runner 서버의 패치, 격리와 보안은 운영 주체가 담당한다.

### Jenkins

Jenkins는 조직이 직접 설치해 사용하는 오픈소스 자동화 서버다. Controller가 Job과 실행 상태를 관리하고 같은 서버 또는 별도 Agent가 실제 명령을 실행한다. Pipeline은 Jenkinsfile 또는 관리 화면에서 정의할 수 있으며 플러그인으로 여러 도구와 연결한다.
