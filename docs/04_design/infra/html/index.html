낮은 초기 비용AWS 교육 크레딧과 단일 서버 구성을 우선 활용합니다.

필요할 때 확장고가용성·자동 확장이 실제 요구가 되면 재검토합니다.

기반 환경

교육 크레딧을 활용하면서 다른 VM 환경으로 옮길 수 있는 단순한 기반입니다.

DECISION 01

클라우드

AWS

선택 이유: 6개월 교육 계정 크레딧으로 초기 비용을 줄일 수 있고, 공식 문서와 실제 운영 사례가 풍부해 팀의 학습과 문제 해결에 유리합니다. 해외 리전과 다양한 서비스가 있어 향후 글로벌 확장 선택지도 확보할 수 있습니다.

원칙·재검토: 애플리케이션은 Docker와 표준 기술로 유지합니다. 크레딧 종료 후 비용, 규제 또는 외부 GPU 서버와의 지연이 문제가 되면 다른 클라우드를 다시 비교합니다.

DECISION 02

서버

EC2 단일 인스턴스

선택 이유: 현재 서비스 규모에서는 여러 서버와 오케스트레이션을 운영할 필요가 없으며, 한 대의 범용 VM에서 웹·Worker·DB를 실행하는 구성이 가장 경제적입니다. 일반 가상 서버이므로 다른 클라우드 VM으로 옮기기도 비교적 쉽습니다.

감수·재검토: 단일 장애 지점과 직접 패치·백업해야 하는 부담을 감수합니다. 고가용성, 무중단 배포 또는 지속적인 자원 부족이 발생하면 다중 서버 구성을 검토합니다.

DECISION 03

운영체제

Ubuntu LTS

선택 이유: AWS뿐 아니라 다른 클라우드와 온프레미스에서도 동일하게 사용할 수 있고, Docker 및 서버 패키지 관련 자료가 풍부합니다. 팀이 익숙한 Linux 운영 방식과 긴 보안 지원 기간을 활용할 수 있습니다.

원칙·재검토: 애플리케이션 의존성은 호스트가 아니라 Docker 이미지에 고정합니다. 필요한 도구의 호환성과 보안 지원이 끝나면 다음 LTS 버전으로 전환합니다.

DECISION 04

컨테이너 실행

Docker Compose

선택 이유: 단일 EC2에서 Nginx, Frontend, Backend, Worker와 선택할 DB 엔진을 역할별 컨테이너로 관리하기에 충분합니다. ECS나 Kubernetes보다 초기 설정, 비용과 운영 학습 부담이 낮고 Compose 파일을 다른 VM에서도 재사용할 수 있습니다.

감수·재검토: 자동 확장과 다중 서버 장애 복구는 직접 해결해야 합니다. 서버가 여러 대로 늘거나 서비스별 독립 확장이 필요해질 때 오케스트레이션을 검토합니다.

소스 · 빌드 · 배포

관리 서버를 추가하지 않고 GitHub 중심으로 자동화합니다.

DECISION 05

소스 저장소

GitHub

선택 이유: 팀이 사용하는 저장소를 별도 이전하지 않고 Pull Request, Branch 보호와 코드 리뷰를 한곳에서 운영할 수 있습니다. GitHub Actions와 자연스럽게 연결되어 별도 Webhook·계정 연동을 줄일 수 있습니다.

운영 원칙: 메인 브랜치 직접 Push를 제한하고 리뷰 및 CI 통과를 병합 조건으로 둡니다. 완전한 폐쇄망 전환 시 사내 Git 또는 GitHub Enterprise Server를 검토합니다.

DECISION 06

CI

GitHub Actions + 제공 Runner

선택 이유: GitHub 저장소 이벤트와 바로 연결되고 Jenkins 서버·플러그인을 별도로 구축하거나 패치할 필요가 없습니다. Pull Request마다 Lint, 테스트, 이미지 빌드와 취약점 검사를 자동화하기에 현재 규모에서 가장 단순합니다.

종속성·재검토: 핵심 명령은 Makefile이나 스크립트로 분리합니다. 내부망 접근이 필요하면 Self-hosted Runner를, 완전한 폐쇄망이면 Jenkins를 검토합니다.

DECISION 07

이미지 저장소

Docker Hub Private

선택 이유: ECR에 비해 특정 클라우드에 종속되지 않는 표준 Registry이며 AWS, 다른 클라우드와 로컬 환경에서 동일하게 사용할 수 있습니다. 현재 이미 사용 중인 운영 경험을 그대로 활용할 수 있습니다.

운영 원칙: `latest` 대신 Commit SHA 또는 버전 태그를 사용하고 Read-only 배포 Token을 분리합니다. Pull 제한, 비용 또는 보안 정책이 문제가 되면 GHCR이나 사내 Registry를 재검토합니다.

DECISION 08

CD

SSM Run Command + 배포 스크립트

선택 이유: GitHub Actions가 AWS Systems Manager API로 배포를 요청하므로 인터넷에 SSH 관리 포트를 열거나 SSH 개인키를 CI에 저장할 필요가 없습니다. 실제 배포 로직은 EC2의 공통 스크립트가 담당해 CI 도구와 분리됩니다.

정확한 흐름: GitHub Actions → SSM Run Command → EC2 `deploy.sh`, EC2 → Docker Hub 이미지 Pull입니다. 다중 서버와 무중단 전환이 필요하면 다른 CD 방식을 검토합니다.

웹 서비스 실행

하나의 EC2 안에서도 역할별 컨테이너를 분리합니다.

DECISION 09

Reverse Proxy

Nginx 컨테이너

선택 이유: 하나의 공개 진입점에서 HTTPS를 처리하고 `/*`는 Frontend, `/api/*`는 Backend로 라우팅할 수 있습니다. 자료와 운영 경험이 풍부하며 어떤 VM에서도 실행할 수 있어 ALB보다 비용과 AWS 종속성이 낮습니다.

감수·재검토: 설정, 패치와 인증서 Reload를 직접 관리합니다. EC2가 여러 대로 늘고 관리형 Health Check·부하분산이 필요하면 ALB를 검토합니다.

DECISION 10

HTTPS 인증서

Let's Encrypt + Certbot

선택 이유: 단일 EC2와 Nginx에서 공개 인증서를 무료로 발급할 수 있고 특정 클라우드 로드밸런서에 종속되지 않습니다. Certbot으로 만료 전 자동 갱신을 구성할 수 있습니다.

운영 원칙: 갱신 실패 알림과 Nginx Reload 절차를 검증합니다. ALB나 CloudFront에서 TLS를 종료하게 되면 ACM으로 전환할 수 있습니다.

DECISION 11

프론트 배포

정적 SPA Nginx 컨테이너

선택 이유: 초기 트래픽에서는 별도 S3·CloudFront 구성을 추가하지 않고 같은 EC2 자원을 활용하는 것이 경제적입니다. Frontend와 Backend 컨테이너는 분리되어 빌드 결과와 설정 책임도 구분할 수 있습니다.

재검토: 정적 파일 트래픽, 글로벌 전송, 캐시 또는 서버 부하가 커지면 S3·CDN 배포로 이동합니다.

데이터와 비동기 처리

DB 엔진과 백엔드 프레임워크는 아직 미정입니다. 아래 흐름은 관계형 DB를 기준으로 하며 PostgreSQL과 Spring Boot 표기는 구현 예시입니다.

DECISION 14

DB 실행 위치

동일 EC2의 Docker 컨테이너

선택 이유: 초기에는 별도 관리형 DB 비용 없이 선택할 DB 엔진을 함께 실행하여 구성 요소와 계정을 줄일 수 있습니다. Docker Compose로 로컬과 운영 환경을 비슷하게 유지하기도 쉽습니다. PostgreSQL은 현재 다이어그램과 상세 흐름을 설명하기 위한 예시이며 엔진은 아직 확정하지 않았습니다.

감수·재검토: EC2 장애가 애플리케이션과 DB에 동시에 영향을 주므로 영구 볼륨, 외부 백업과 복구 검증이 필수입니다. 데이터 중요도와 가용성 요구가 높아지면 관리형 DB 또는 별도 DB 서버로 이전합니다.

개념 문서 보기 →
DECISION 15

파일 저장

Amazon S3 장기 Archive

선택 이유: 실시간 거래는 DB에 원문 Payload와 정규화 데이터로 저장하고, 오래된 원문은 시간 또는 건수 단위의 JSONL·Parquet 파일로 묶어 S3에 장기 보관합니다. 거래 한 건마다 작은 S3 객체를 생성하는 오버헤드를 피하면서 EC2 교체·장애와 무관한 장기 보존 경로를 확보합니다.

역할: S3는 실시간 적재나 GPU 추론 경로에 포함하지 않습니다. Archive 작업이 DB 원문을 묶어 업로드하고 건수·Checksum을 검증한 뒤 보존 정책에 따라 DB 원문을 정리합니다.

DECISION 16

비동기 작업

Amazon SQS Standard + DLQ

선택 이유: 지속적으로 들어오는 거래 접수와 검증·정규화·DB 적재를 분리해 Backend API가 빠르게 응답하고 순간적인 거래 유입도 Queue가 흡수합니다. 관리형 서비스라 별도 메시지 브로커를 운영할 필요가 없습니다.

처리 원칙: Ingestion Worker는 메시지를 모아 원문과 정규화 거래를 DB에 저장하고 PENDING으로 표시합니다. Model Batch Worker는 DB에서 분석 대상을 조회해 GPU 추론 후 결과를 DB에 저장합니다. `transaction_id` 기반 멱등성과 DLQ를 적용하며, 폐쇄망에서는 RabbitMQ 등으로 교체할 수 있게 메시지 경계를 유지합니다.

보안과 운영

초기에는 최소 구성을 적용하고 운영 신호가 쌓이면 확장합니다.

DECISION 18

비밀정보

로컬 .env + 운영 Parameter Store

선택 이유: 개발자는 Git에 포함하지 않는 `.env`로 간단히 실행하고, 운영 비밀번호·JWT Secret·GPU Token은 KMS로 암호화된 SecureString으로 중앙 관리할 수 있습니다. EC2 IAM Role로 경로별 최소 조회 권한도 부여할 수 있습니다.

종속성 완화: 애플리케이션이 Parameter Store SDK를 직접 호출하지 않고 배포 스크립트가 Docker Secret 파일로 주입합니다. 자동 교체가 필요하면 Secrets Manager를 검토합니다.

DECISION 19

로그 · 모니터링

CloudWatch 최소 구성

선택 이유: 단일 EC2 안에 Prometheus·Grafana·Loki를 함께 실행해 서비스 자원을 소모하지 않고 EC2, SQS와 애플리케이션의 핵심 상태를 외부에서 확인할 수 있습니다. 별도 모니터링 서버의 업데이트와 백업도 필요하지 않습니다.

비용·이식성: ERROR·WARN과 필수 메트릭만 수집하고 보존 기간을 제한합니다. 애플리케이션은 구조화된 stdout 로그를 사용해 폐쇄망에서는 Loki·Prometheus로 전환할 수 있게 합니다.

DECISION 20

DNS

Cloudflare Free · DNS-only

선택 이유: 무료 권한 DNS를 사용하면서 도메인 소유권을 6개월짜리 AWS 교육 계정과 분리할 수 있습니다. AWS, 다른 클라우드 또는 온프레미스로 이전할 때 A Record 대상만 변경하면 됩니다.

운영 원칙: 초기에는 Proxy를 끄고 EC2 Nginx가 TLS와 요청 처리를 담당하도록 단순화합니다. CDN, DDoS 완화 또는 원본 IP 보호가 필요하면 Cloudflare Proxy를 별도로 검토합니다.

이 문서의 범위
백엔드 기술, DB 종류, 캐시와 Infrastructure as Code는 아직 확정되지 않아 의도적으로 제외했습니다. 결정이 완료되면 이 요약 문서에도 추가합니다.
상세 비교와 재검토 조건은 인프라 아키텍처 결정 기록에서 확인할 수 있습니다.
