# AML 인프라 아키텍처 발표 대본

## 발표 안내

- 대상: 인프라를 처음 접하는 사람
- 기준 이미지: `자금세탁소drawio.png`
- 예상 발표 시간: 약 12~15분
- 설명 순서: 그림의 위쪽부터 아래쪽으로, 각 영역은 왼쪽에서 오른쪽으로 설명

> 발표 전 확인: 그림에는 PostgreSQL이 표시되어 있지만 DB 엔진은 아직 확정하지 않았습니다. PostgreSQL은 관계형 DB의 예시입니다. Backend 역시 Spring Boot를 포함한 후보를 검토 중이며 아직 확정하지 않았습니다.

## 1. 발표 시작


지금부터 그래프 신경망 기반 자금세탁방지, 즉 AML 모니터링 시스템의 인프라 아키텍처를 설명드리겠습니다.

인프라라는 말이 낯설 수 있는데, 쉽게 말하면 **우리 서비스를 어디에서 실행하고, 거래 데이터를 어떻게 전달하고 저장하며, 장애와 보안을 어떻게 관리할 것인지 정리한 설계도**입니다.

이 시스템의 핵심 목적은 금융 거래가 계속 들어오면 거래들을 안전하게 저장하고, 일정량을 모아 GNN 모델로 분석한 뒤, 의심 거래의 위험 점수와 탐지 결과를 관리자가 조회할 수 있게 하는 것입니다.

그림은 크게 세 영역으로 나뉩니다.

첫 번째 위쪽은 코드를 운영 서버에 반영하는 **CI/CD 영역**입니다.

두 번째 가운데는 사용자의 요청과 금융 거래를 실제로 처리하는 **서비스 요청 및 거래 처리 영역**입니다.

세 번째 아래쪽은 인증서, 비밀정보, 로그와 장애를 관리하는 **보안·운영·관측 영역**입니다.

이제 그림의 위쪽부터 차례대로 살펴보겠습니다.

## 2. 전체 설계 원칙

본격적인 구성 설명 전에 이 아키텍처의 원칙부터 말씀드리겠습니다.

현재는 초기 단계의 프로젝트이므로 AWS EC2 서버 한 대에서 Docker Compose로 서비스를 실행합니다. 처음부터 서버를 여러 대 사용하거나 Kubernetes처럼 복잡한 시스템을 도입하지 않고, 현재 규모에 필요한 만큼만 구성했습니다.

다만 AWS를 사용한다고 해서 모든 기능을 AWS에만 의존하도록 만들지는 않았습니다. 애플리케이션은 Docker 컨테이너로 실행하고, 메시지 형식과 배포 명령도 가능한 한 표준적인 형태로 유지합니다.

따라서 나중에 다른 클라우드나 사내 폐쇄망으로 옮겨야 한다면, AWS 서비스와 연결되는 일부 구간만 교체하고 핵심 애플리케이션 로직은 최대한 유지하는 것이 목표입니다.

## 3. CI/CD 영역 — 코드를 운영 서버에 배포하는 과정

먼저 그림 가장 위쪽의 `1. CI/CD` 영역을 보겠습니다.

CI/CD는 개발자가 작성한 코드를 검사하고, 실행 가능한 형태로 만든 뒤, 운영 서버에 배포하는 자동화 과정입니다.

### 3-1. GitHub에 코드 반영

[그림의 왼쪽 개발자와 GitHub를 가리킨다]

개발자가 기능 개발을 마치고 코드를 GitHub의 메인 브랜치에 병합하면 배포 과정이 시작됩니다.

GitHub는 소스 코드를 보관하고 여러 개발자의 변경 내용을 관리하는 저장소입니다.

### 3-2. GitHub Actions가 검사와 빌드 수행

[GitHub Actions 아이콘을 가리킨다]

다음으로 GitHub Actions가 자동으로 실행됩니다.

여기서는 코드 문법 검사, 테스트, Docker 이미지 빌드를 수행합니다. Docker 이미지는 애플리케이션과 실행에 필요한 파일을 하나로 묶은 실행 패키지라고 이해하면 됩니다.

즉, 개발자의 컴퓨터에서만 실행되는 코드가 아니라 어느 서버에서도 같은 방식으로 실행할 수 있는 상자를 만드는 과정입니다.

### 3-3. Docker Hub에 이미지 보관

[Docker Hub를 가리킨다]

검사와 빌드가 성공하면 Docker 이미지를 Docker Hub의 비공개 저장소에 올립니다.

Docker Hub는 소스 코드를 저장하는 GitHub와 역할이 다릅니다. GitHub가 설계도와 재료를 보관한다면, Docker Hub는 조립이 끝난 실행 제품을 보관하는 창고에 가깝습니다.

Docker Hub를 선택한 이유는 AWS ECR에 비해 특정 클라우드에 덜 종속적이고, 다른 클라우드나 서버에서도 같은 이미지를 쉽게 내려받을 수 있기 때문입니다.

### 3-4. SSM Run Command로 EC2에 배포 명령 전달

[AWS Systems Manager와 EC2를 가리킨다]

이미지 업로드가 끝나면 **GitHub Actions가 AWS Systems Manager의 Run Command를 호출해 EC2에 배포 명령을 전달**합니다.

여기서 중요한 점은 Docker Hub가 배포 명령을 보내는 것이 아니라는 것입니다. Docker Hub는 이미지를 보관하고, 실제 배포 요청은 GitHub Actions가 보냅니다.

EC2는 전달받은 공통 배포 스크립트인 `deploy.sh`를 실행합니다. 스크립트는 `docker compose pull`로 새 이미지를 내려받고, `docker compose up -d`로 컨테이너를 새 버전으로 실행합니다.

이 방식은 운영 서버의 SSH 포트를 인터넷에 공개하지 않고도 배포할 수 있다는 장점이 있습니다.

배포 후에는 서비스가 정상인지 Health Check를 수행합니다. 문제가 있다면 이전 이미지 버전으로 되돌릴 수 있도록 이미지 태그와 배포 이력을 관리합니다.

## 4. 서비스 접속 영역 — 사용자가 화면과 API에 접근하는 과정

이제 그림 가운데의 `2. 서비스 요청 및 거래 처리` 영역을 보겠습니다.

먼저 왼쪽은 사용자 요청이 서비스에 들어오는 경로입니다.

### 4-1. Cloudflare DNS

[Client와 Cloudflare DNS를 가리킨다]

사용자가 서비스 주소를 입력하면 Cloudflare DNS가 해당 도메인을 AWS EC2 서버의 주소로 연결합니다.

DNS는 인터넷의 전화번호부와 비슷합니다. 사람이 기억하기 쉬운 도메인 이름을 실제 서버의 IP 주소로 바꿔 줍니다.

현재 Cloudflare는 트래픽을 대신 처리하는 Proxy가 아니라 DNS-only 방식으로 사용합니다. 실제 요청은 EC2의 Nginx로 직접 전달됩니다.

### 4-2. Nginx Reverse Proxy

[Nginx를 가리킨다]

EC2에 도착한 요청을 가장 먼저 받는 구성 요소가 Nginx입니다.

Nginx는 건물의 안내 데스크와 같은 역할을 합니다. 사용자가 화면 파일을 요청하면 Frontend로 보내고, `/api`로 시작하는 업무 요청이면 Backend API로 전달합니다.

외부에는 HTTPS 443 포트만 공개하고 Backend, Worker와 DB는 인터넷에 직접 공개하지 않습니다.

### 4-3. Frontend와 Backend API

[Frontend와 Backend API를 차례로 가리킨다]

Frontend는 사용자가 보는 웹 화면입니다. 정적 SPA 형태로 빌드된 HTML, CSS와 JavaScript 파일을 별도의 Nginx 컨테이너가 제공합니다.

외부 요청을 받는 Reverse Proxy Nginx와 Frontend용 Nginx를 분리한 이유는 역할이 다르기 때문입니다. 앞쪽 Nginx는 HTTPS와 요청 경로를 관리하고, Frontend Nginx는 화면 파일만 제공합니다. 이렇게 나누면 Frontend 이미지만 독립적으로 교체하기 쉽습니다.

Backend API는 로그인, 권한 확인, 거래 접수, 처리 상태 조회와 탐지 결과 조회 같은 업무를 담당합니다.

다만 Backend가 오래 걸리는 거래 검증과 AI 추론까지 직접 기다리며 처리하지는 않습니다. 이런 작업은 뒤에서 설명할 Worker에게 넘겨 사용자의 요청이 오래 멈춰 있지 않도록 합니다.

참고로 Backend를 Spring Boot로 만들지는 아직 결정하지 않았습니다. 어떤 기술을 선택하더라도 이 역할과 데이터 흐름은 동일하게 유지합니다.

## 5. 실시간 거래 수집 — 거래 한 건이 DB에 저장되는 과정

이제 그림 중앙의 번호가 표시된 거래 처리 흐름을 따라가겠습니다.

### 5-1. 거래 한 건 수신

[1번 화살표를 가리킨다]

외부 금융 거래 시스템에서 거래가 한 건씩 지속적으로 Backend API에 들어옵니다.

여기서 그림의 Client는 일반 사용자 화면뿐 아니라 거래를 전달하는 외부 금융 시스템을 포함한다고 이해하면 됩니다.

Backend API는 인증 여부와 필수 형식처럼 빠르게 확인할 수 있는 항목을 검사합니다.

### 5-2. SQS에 거래 메시지 등록

[2번 화살표와 AWS SQS를 가리킨다]

기본 검사가 끝나면 Backend API는 거래 원문 메시지와 이를 식별할 `event_id`를 Amazon SQS에 등록합니다.

SQS는 처리해야 할 일을 잠시 줄 세워 두는 대기열입니다. 은행 창구의 번호표 대기열을 생각하면 쉽습니다.

거래가 갑자기 많이 들어와도 Backend가 모든 거래를 즉시 DB에 저장하려고 버티는 대신, SQS가 먼저 받아서 순서대로 Worker가 처리할 수 있게 완충합니다.

SQS 등록이 성공하면 Backend는 거래를 접수했다는 응답을 빠르게 반환할 수 있습니다. 이 시점은 최종 분석 완료가 아니라 **접수 완료**입니다.

### 5-3. Ingestion Worker가 여러 거래를 모아 처리

[3번 화살표와 Ingestion Worker를 가리킨다]

Ingestion Worker는 SQS에서 거래 메시지를 여러 건 가져옵니다.

Worker는 사용자에게 화면을 제공하는 별도 서버가 아니라, 화면 뒤에서 특정 작업만 수행하는 백그라운드 프로세스입니다. 현재는 Backend와 같은 EC2, 같은 Docker Compose 안에서 실행됩니다.

거래를 한 건씩 DB에 기록할 수도 있지만, 짧은 시간이나 일정 건수만큼 모아 Micro-batch로 저장하면 DB 작업 횟수를 줄일 수 있습니다.

Ingestion Worker는 거래를 검증하고, 시스템에서 사용하기 쉬운 공통 구조로 변환하며, 중복 거래인지 확인합니다.

### 5-4. 원문과 정규화 거래를 DB에 저장

[4번 화살표와 DB 아이콘을 가리킨다]

검증이 끝나면 두 종류의 데이터를 DB에 함께 저장합니다.

첫 번째는 외부에서 받은 **원문 Payload**입니다. 나중에 오류 조사나 재처리가 필요할 때 처음 받은 내용을 확인하기 위해 보관합니다.

두 번째는 필드 이름, 금액, 시간과 계좌 식별자 등을 시스템 기준에 맞춘 **정규화 거래 데이터**입니다. 실제 조회와 GNN 분석에는 이 데이터를 사용합니다.

두 데이터는 하나의 DB 트랜잭션으로 저장합니다. 둘 중 하나라도 저장에 실패하면 전체 작업을 실패 처리하여 원문과 정규화 데이터가 서로 어긋나지 않게 합니다.

DB 저장이 성공하면 해당 거래의 `inference_status`를 `PENDING`, 즉 **추론 대기 상태**로 설정합니다. 그 후에만 SQS 메시지를 처리 완료로 삭제합니다.

그림에는 PostgreSQL 아이콘이 있지만 DB 엔진은 아직 미정입니다. PostgreSQL은 현재 데이터 구조를 설명하기 위한 관계형 DB 예시입니다.

## 6. GNN 분석 — 거래를 모아 위험도를 계산하는 과정

### 6-1. Model Batch Worker가 분석 대상 선택

[5번 화살표와 Model Batch Worker를 가리킨다]

Model Batch Worker는 DB에서 `PENDING` 상태인 거래를 조회합니다.

Ingestion Worker가 Model Batch Worker에 데이터를 직접 전달하지 않는다는 점이 중요합니다. 두 Worker는 DB에 저장된 데이터와 상태를 통해 연결됩니다.

이렇게 하면 Model Batch Worker나 GPU 서버에 장애가 생겨도 이미 적재된 거래를 잃지 않고 나중에 다시 분석할 수 있습니다. Ingestion Worker부터 다시 실행할 필요도 없습니다.

Model Batch Worker는 시간과 건수 기준으로 분석할 거래를 모으고, 해당 거래와 연결된 계좌 및 과거 거래를 DB에서 함께 조회합니다.

GNN은 거래 하나만 보는 것이 아니라 계좌와 거래 사이의 관계를 그래프로 보기 때문입니다. 예를 들어 여러 계좌를 거쳐 돈이 순환하거나 짧은 시간에 여러 계좌로 분산되는 패턴을 찾으려면 주변 거래 관계가 필요합니다.

처리할 거래를 선점하면 상태를 `INFERENCING`, 즉 **추론 진행 중**으로 변경합니다.

### 6-2. 외부 GPU 서버에 추론 요청

[6번 화살표를 가리킨다]

Model Batch Worker는 조회한 거래로 GNN 입력 그래프를 만든 뒤 외부 GPU 서버에 추론을 요청합니다.

GPU 서버는 AI 모델 계산만 담당합니다. 보안을 위해 GPU 서버가 애플리케이션 DB에 직접 접속하지는 않습니다.

즉, DB에서 필요한 데이터를 읽는 주체는 Model Batch Worker이고, GPU 서버에는 계산에 필요한 입력만 전달합니다.

### 6-3. 위험 점수와 탐지 결과 수신

[7번 화살표를 가리킨다]

GPU 서버는 각 거래나 계좌에 대한 위험 점수와 탐지 결과를 Model Batch Worker에 반환합니다.

위험 점수는 의심 정도를 수치로 표현한 값이고, 탐지 결과는 어떤 패턴이나 기준으로 의심되었는지를 나타내는 정보입니다.

### 6-4. 추론 결과를 DB에 저장

[8번 화살표를 가리킨다]

Model Batch Worker는 받은 위험 점수, 탐지 결과, 사용한 모델 버전과 처리 시각을 DB에 저장합니다.

DB 저장까지 성공해야 상태를 `COMPLETED`, 즉 **처리 완료**로 변경합니다. GPU 응답만 받고 DB 저장에 실패했다면 완료로 보지 않습니다.

GPU 호출 중 일시적인 오류가 발생하면 `RETRY_WAIT` 상태로 두고 제한된 횟수만큼 다시 시도합니다. 계속 실패하거나 복구할 수 없는 오류라면 `FAILED`로 기록하여 운영자가 원인을 확인할 수 있게 합니다.

정리하면 상태는 다음과 같이 흐릅니다.

`PENDING`, 추론 대기.

`INFERENCING`, 추론 진행 중.

성공하면 `COMPLETED`.

일시 오류면 `RETRY_WAIT`.

최종 실패면 `FAILED`입니다.

### 6-5. 결과 조회

[9번 점선과 Backend API를 가리킨다]

분석이 끝난 뒤 AML 관리자가 화면에서 결과를 조회하면 Backend API가 DB에서 처리 상태와 탐지 결과를 읽어 Frontend에 반환합니다.

이 조회 흐름은 SQS 메시지를 관찰하는 운영 모니터링과는 다릅니다. 사용자가 보는 업무 결과는 Backend API와 DB를 통해 조회하고, 시스템 상태와 장애는 아래의 CloudWatch에서 관찰합니다.

---

## 7. S3 — 실시간 경로가 아닌 장기 보관소

[Amazon S3와 DB에서 S3로 향하는 화살표를 가리킨다]

그림 위쪽의 Amazon S3는 거래를 실시간으로 처리하기 위한 중간 저장소가 아닙니다.

거래 한 건이 들어올 때마다 작은 S3 파일을 만들면 요청 횟수와 객체 수가 불필요하게 증가합니다. 그래서 실시간 원문과 정규화 거래는 먼저 DB에 저장합니다.

DB에 일정 기간 보관한 오래된 원문은 시간이나 건수 기준으로 묶어 JSONL 또는 Parquet 파일로 만든 뒤 S3에 장기 Archive합니다.

Archive 작업은 업로드 후 파일의 거래 건수와 Checksum을 검증합니다. S3 보관이 정상적으로 확인된 뒤에만 보존 정책에 따라 DB의 오래된 원문 Payload를 정리합니다.

정규화 거래와 위험 점수, 탐지 결과는 계속 DB에 유지합니다.

S3를 사용하는 이유는 EC2 서버나 로컬 디스크가 교체되어도 장기 원문을 별도로 보존할 수 있고, 대량 파일 보관 비용과 수명주기 관리에 적합하기 때문입니다.

---

## 8. 실패 처리 — SQS DLQ

[SQS 아래의 빨간색 DLQ를 가리킨다]

SQS 메시지는 처리에 실패하면 일정 시간이 지난 뒤 다시 Ingestion Worker에 전달됩니다.

하지만 데이터 형식 자체가 잘못된 경우처럼 계속 재시도해도 성공할 수 없는 메시지가 있을 수 있습니다.

이런 메시지를 무한히 반복하지 않도록 정해진 재시도 횟수를 넘으면 DLQ, 즉 실패 메시지 전용 대기열로 이동합니다.

DLQ는 실패 메시지를 버리는 휴지통이 아니라, 원인을 조사하기 위해 격리해 두는 보관함입니다.

운영자는 오류 원인을 수정한 뒤 해당 메시지를 다시 처리할지 결정합니다. 이를 통해 특정 잘못된 거래 한 건이 전체 거래 처리를 막지 않도록 합니다.

## 9. 보안·운영·관측 영역

이제 그림 아래쪽의 `3. 보안·운영·관측` 영역을 설명하겠습니다.

### 9-1. Let's Encrypt와 Certbot

[Let's Encrypt와 Nginx 연결을 가리킨다]

Let's Encrypt는 HTTPS에 필요한 TLS 인증서를 무료로 발급합니다. Certbot은 인증서를 발급하고 갱신하는 작업을 자동화합니다.

HTTPS는 사용자의 브라우저와 Nginx 사이에서 오가는 로그인 정보와 조회 내용을 암호화합니다.

인증서는 Nginx가 사용하며, 애플리케이션 비밀번호나 DB 접속정보와는 다른 종류의 보안 정보입니다.

### 9-2. Parameter Store

[Parameter Store와 점선 연결을 가리킨다]

Parameter Store에는 DB 비밀번호, JWT 비밀키, 외부 GPU 인증키처럼 코드나 Docker 이미지에 넣으면 안 되는 비밀정보를 암호화하여 보관합니다.

다만 Parameter Store가 각 컨테이너에 값을 직접 밀어 넣는 것은 아닙니다.

EC2의 배포 스크립트가 IAM 권한으로 필요한 값만 조회하고, 제한된 권한의 Secret 파일로 만든 뒤 Docker Compose가 각 컨테이너에 필요한 값만 전달합니다.

Backend API에는 DB 접속정보와 JWT 비밀키 등이 필요합니다.

Ingestion Worker에는 DB와 SQS 관련 정보가 필요합니다.

Model Batch Worker에는 DB 접속정보와 GPU 서버 주소 및 인증키가 필요합니다.

Frontend에는 비밀정보를 절대 전달하지 않습니다. Frontend 파일은 사용자의 브라우저로 내려가기 때문에 그 안의 값은 누구나 확인할 수 있기 때문입니다.

### 9-3. CloudWatch

[CloudWatch를 가리킨다]

CloudWatch는 시스템이 정상적으로 작동하는지 확인하는 관제 화면 역할을 합니다.

Backend와 Worker는 로그를 표준 출력으로 기록하고, 수집기가 이를 CloudWatch Logs로 전달합니다.

EC2의 CPU, 메모리와 디스크 사용률, Backend 오류율, Worker 처리 성공·실패, GPU 요청 지연, SQS 적체량과 DLQ 메시지 수 등을 확인합니다.

중요한 기준을 넘으면 Alarm을 발생시켜 운영자가 장애를 빠르게 알 수 있게 합니다.

단, 거래 원문, 전체 계좌번호, 인증 토큰과 비밀번호 같은 민감정보는 로그에 기록하지 않습니다.

CloudWatch로 향하는 점선은 거래 데이터가 이동한다는 뜻이 아니라, 각 서비스의 로그와 상태 정보가 전달된다는 뜻입니다.

---

## 10. 왜 Backend와 Worker를 분리했는가

여기까지 들으면 Backend API, Ingestion Worker와 Model Batch Worker를 왜 하나로 합치지 않았는지 궁금할 수 있습니다.

세 구성 요소는 현재 별도의 서버가 아닙니다. 모두 같은 EC2와 Docker Compose 안에서 실행하며, 하나의 백엔드 코드베이스와 Docker 이미지를 공유하는 방식도 가능합니다.

다만 실행 역할을 분리했습니다.

Backend API는 사용자의 요청에 빠르게 응답해야 합니다.

Ingestion Worker는 지속적으로 들어오는 거래를 검증하고 DB에 적재합니다.

Model Batch Worker는 시간이 오래 걸릴 수 있는 그래프 생성과 GPU 추론을 담당합니다.

역할을 분리하면 GPU 서버가 느리거나 중단되어도 거래 접수와 DB 적재를 계속할 수 있고, 특정 작업에 문제가 생겼을 때 해당 Worker만 다시 실행할 수 있습니다.

따라서 현재 구조는 여러 독립 서비스가 각각 배포되는 전형적인 MSA라기보다, **모듈러 모놀리스와 비동기 Worker 구조**에 가깝습니다.

향후 거래량이 증가하면 필요한 Worker만 별도 서버로 옮기거나 실행 개수를 늘릴 수 있습니다.

## 11. 현재 구조의 한계와 확장 방향

현재 구조는 비용이 낮고 이해하기 쉽지만 한계도 있습니다.

가장 큰 한계는 EC2 한 대에 Nginx, Backend, Worker와 DB가 함께 있다는 점입니다. EC2 자체에 장애가 발생하면 전체 서비스가 동시에 중단될 수 있습니다.

또한 서버 패치, 디스크 관리, DB 백업과 복구를 운영팀이 직접 관리해야 합니다.

초기 프로젝트에서는 이 단순성과 비용 절감 효과가 더 크다고 판단했습니다.

하지만 다음과 같은 조건이 생기면 구조를 확장할 수 있습니다.

첫째, DB의 중요도와 가용성 요구가 높아지면 DB를 별도 서버나 관리형 DB로 이전합니다.

둘째, 특정 Worker의 처리량이 부족하면 Worker를 별도 EC2로 분리하거나 여러 개 실행합니다.

셋째, 서버 여러 대의 자동 확장과 무중단 배포가 필요해지면 ECS 또는 Kubernetes 같은 오케스트레이션 환경을 검토합니다.

넷째, 완전한 폐쇄망으로 전환하면 SQS는 RabbitMQ 같은 내부 메시지 브로커로, CloudWatch는 Prometheus·Grafana·Loki 같은 내부 관측 도구로 교체할 수 있습니다.

이때도 Docker 이미지, 메시지 Schema와 핵심 업무 로직은 최대한 유지하는 것이 목표입니다.

## 12. 전체 흐름 요약

마지막으로 전체 흐름을 짧게 정리하겠습니다.

개발자가 GitHub에 코드를 병합하면 GitHub Actions가 테스트와 Docker 이미지 빌드를 수행합니다.

이미지는 Docker Hub에 저장되고, GitHub Actions가 SSM Run Command로 EC2의 배포 스크립트를 실행합니다.

외부 금융 거래 시스템에서 들어온 거래 한 건은 Backend API를 거쳐 SQS에 메시지로 등록됩니다.

Ingestion Worker가 여러 거래를 모아 검증하고, 원문 Payload와 정규화 거래를 DB에 저장한 뒤 추론 상태를 `PENDING`으로 설정합니다.

Model Batch Worker가 PENDING 거래와 연관 거래를 DB에서 조회하여 GNN 입력 그래프를 만들고 외부 GPU 서버에 추론을 요청합니다.

GPU 서버가 위험 점수와 탐지 결과를 반환하면 Model Batch Worker가 결과와 모델 버전을 DB에 저장하고 상태를 `COMPLETED`로 변경합니다.

관리자는 Frontend와 Backend API를 통해 처리 상태와 탐지 결과를 조회합니다.

오래된 원문은 여러 건을 묶어 S3에 장기 보관하고, 비밀정보는 Parameter Store, 인증서는 Let's Encrypt, 로그와 메트릭은 CloudWatch에서 관리합니다.

이 아키텍처는 초기 비용과 운영 복잡도를 낮추면서도 거래 수집, 데이터 적재와 AI 추론을 서로 분리하여 장애에 대응하고, 향후 다른 환경으로 이전하거나 확장할 수 있도록 설계했습니다.

이상으로 설명을 마치겠습니다. 감사합니다.

## 13. 발표 후 예상 질문과 답변

### Q1. PostgreSQL과 Spring Boot를 사용하기로 확정한 것인가요?

아닙니다. DB 엔진과 백엔드 프레임워크는 아직 미정입니다. 다이어그램의 PostgreSQL과 문서의 Spring Boot는 구체적인 흐름을 설명하기 위한 예시입니다.

### Q2. S3에 거래를 한 건씩 저장하지 않는 이유는 무엇인가요?

거래마다 작은 객체를 만들면 요청과 객체 수가 지나치게 많아집니다. 실시간 데이터는 DB에 저장하고, 오래된 원문을 일정 시간이나 건수 단위로 묶어 S3에 Archive합니다.

### Q3. Redis에 원문 거래를 저장하지 않는 이유는 무엇인가요?

Redis는 빠른 임시 저장과 캐시에 적합하지만, 원문과 정규화 거래의 신뢰 가능한 영구 저장소로 사용하려면 내구성과 복구 운영이 복잡해집니다. 현재는 트랜잭션과 제약조건을 제공하는 관계형 DB가 더 적합합니다.

### Q4. 거래를 저장하지 않고 바로 GPU에 보내면 안 되나요?

GPU 장애나 네트워크 오류가 발생하면 거래를 잃거나 같은 거래를 안전하게 재처리하기 어렵습니다. 분석 전 거래를 DB에 저장하고 상태를 기록하면 실패한 작업만 다시 실행할 수 있고 감사와 오류 조사도 가능합니다.

### Q5. Worker는 별도의 백엔드 서버인가요?

현재는 별도 물리 서버가 아닙니다. 같은 EC2 안에서 Backend API와 별도 프로세스 또는 컨테이너로 실행되는 백그라운드 작업자입니다.

### Q6. 이 구조는 MSA인가요?

현재는 각 구성 요소가 독립적으로 배포되고 각자 DB를 소유하는 전형적인 MSA가 아닙니다. 하나의 코드베이스와 DB를 공유할 수 있는 모듈러 모놀리스 및 비동기 Worker 구조에 가깝습니다.

### Q7. GPU 서버가 DB에 직접 접근하지 않는 이유는 무엇인가요?

DB 접속 권한과 금융 거래 데이터의 노출 범위를 줄이기 위해서입니다. Model Batch Worker가 필요한 데이터만 읽어 GPU 서버에 전달하고 결과를 받아 DB에 저장합니다.

### Q8. SQS 메시지가 중복 전달되면 거래도 중복 저장되지 않나요?

SQS Standard Queue는 같은 메시지를 두 번 전달할 수 있습니다. 이를 고려해 `event_id`와 `transaction_id`에 고유 제약조건을 적용하고, 이미 처리한 메시지는 다시 저장하지 않는 멱등 처리를 구현합니다.

### Q9. EC2 한 대가 중단되면 어떻게 되나요?

현재 구조에서는 전체 서비스가 중단될 수 있습니다. 이것은 초기 비용 절감을 위해 감수한 단일 장애 지점입니다. 운영 중요도가 높아지면 DB와 Worker를 분리하고 다중 서버 및 자동 복구 구조를 검토합니다.

### Q10. AWS에 너무 종속되는 것은 아닌가요?

SQS, SSM, S3와 CloudWatch를 사용하므로 일정한 AWS 종속성은 있습니다. 다만 애플리케이션은 Docker로 실행하고, 메시지 Schema와 업무 로직을 AWS SDK에서 분리하여 다른 Queue, 저장소와 관측 도구로 교체할 수 있게 설계합니다.
