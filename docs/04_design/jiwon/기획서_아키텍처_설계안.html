1. 기획 배경

금융기관은 이미 AML 거래 모니터링 시스템을 활용하여 사전에 정의된 시나리오, 고객 위험 정보, 거래 패턴과 분석 모델을 기반으로 의심 거래를 탐지하고 있다. 최근 상용 AML 솔루션은 규칙 기반 탐지뿐 아니라 행동 분석, 머신러닝, 거래 네트워크 분석, 경보 우선순위와 조사 업무 관리 기능까지 제공하는 방향으로 발전하고 있다.

그러나 자금세탁 탐지 모델의 효과는 기관이 보유한 데이터, 탐지 시나리오, 모델 구조와 운영 방식에 따라 달라진다. 특히 여러 계좌와 거래가 연결된 패턴을 분석하는 관계 기반 모델이 기존 거래 단위 분석을 어느 정도 보완할 수 있는지, 탐지 결과를 AML 담당자의 조사 과정에서 활용할 수 있는 형태로 제공할 수 있는지는 데이터와 비교 기준을 통한 검증이 필요하다.

본 프로젝트는 기존 AML 모니터링 시스템 전체를 대체하는 것을 목표로 하지 않는다. IBM AML 합성 벤치마크 데이터셋을 이용하여 계좌와 거래 관계를 그래프로 구성하고, GNN 기반 모델이 관계형 자금세탁 패턴을 탐지하는 데 활용될 수 있는지 검증한다. 또한 모델이 산출한 위험 점수와 관련 거래 정보를 AML 담당자가 확인할 수 있는 모니터링 흐름을 MVP로 구현한다.

2. 해결하려는 문제

2.1 개별 거래만으로 파악하기 어려운 관계형 자금세탁 패턴

자금세탁 의심 행위는 여러 계좌와 거래가 연결된 형태로 나타날 수 있다. 하나의 거래만 조회해서는 자금의 순환, 다단계 이동, 다수 계좌로의 분산 등 전체적인 흐름을 파악하기 어렵다. 본 프로젝트는 거래와 계좌의 연결 관계를 그래프로 구성하고 GNN 모델로 분석하여, 개별 거래 조건만으로 발견하기 어려운 관계형 이상 패턴을 탐지하고자 한다.

2.2 대량의 거래 중 우선 조사 대상을 선정하기 어려운 문제

AML 담당자가 모든 거래를 동일한 수준으로 검토하는 것은 현실적으로 어렵다. 본 프로젝트는 거래별 위험 점수와 탐지 결과를 제공하여 담당자가 위험도가 높은 거래부터 확인할 수 있도록 하고, 한정된 조사 자원을 중요한 의심 거래에 우선적으로 투입할 수 있게 한다.

2.3 의심 거래와 연관된 거래 흐름을 확인하기 어려운 문제

의심 거래가 발견되더라도 해당 거래만 확인해서는 판단에 필요한 맥락이 부족할 수 있다. 본 프로젝트는 의심 거래의 기본 정보와 위험 점수뿐 아니라 관련 계좌 및 주변 거래 흐름을 함께 확인할 수 있는 기능을 제공하여 상세 조사를 지원한다.

2.4 거래 수집부터 탐지 결과 조회까지의 처리 과정이 단절되는 문제

거래 데이터 수집, 정제, 모델 분석과 결과 조회가 각각 분리되어 있으면 거래가 어느 단계까지 처리되었는지 확인하기 어렵고, 분석 실패나 지연이 발생했을 때 원인을 추적하기 어렵다. 본 프로젝트는 거래 접수, 데이터 저장, 모델 추론, 결과 저장과 사용자 조회를 하나의 처리 흐름으로 연결하고, 각 거래의 처리 상태와 모델 버전을 기록하여 분석 진행 상황과 실패 여부를 추적할 수 있도록 한다. (→ §5 상태 머신, §7 결정 D-1이 이 요구를 구조로 보장)

2.5 모델 결과를 업무 판단에 활용하기 어려운 문제

모델이 단순히 의심 여부만 반환하면 담당자는 해당 결과를 어떤 순서로 검토해야 하는지 판단하기 어렵고, 모델의 결과가 곧바로 자금세탁 확정을 의미하는 것으로 오해될 가능성도 있다. 본 프로젝트는 모델 결과를 최종 판정이 아닌 조사 지원 정보로 제공한다. 위험 점수, 탐지 여부, 관련 거래 정보와 사용된 모델 버전을 함께 제공하여 담당자가 추가 조사 필요성을 판단할 수 있도록 한다. (→ §7 알림 블록: 알림은 기계가 만들고, 사건은 사람이 만든다)

핵심 문제 정의

AML 담당자는 대량의 금융 거래에서 여러 계좌와 거래가 연결된 의심 패턴을 신속하게 식별하고, 우선 조사할 거래와 관련 거래 흐름을 효율적으로 확인하기 어렵다.

핵심 목표

  • 계좌 간 거래의 GNN 분석으로 관계형 이상 패턴 자동 검출 (1단계 이상거래 이진분류 → 2단계 패턴 다중분류)
  • 거래 수집 → 저장 → 추론 → 결과 조회를 단절 없이 잇는 거래 데이터 파이프라인 구축 (유실 없는 수집, 처리 상태 추적)
  • 거래별 위험 점수·탐지 결과·모델 버전을 담당자 조사 업무에 활용 가능한 형태로 제공
  • 탐지 결과·계좌 관계 그래프를 시각화하고 알림-사건 조사 업무 흐름을 지원하는 웹 대시보드 구현

3. MVP 범위

포함

  • 메인 대시보드 (모니터링팀): 오늘 처리된 거래 수, 신규 알림 건수 등 핵심 지표 카드/차트. 로그인 후 첫 화면.
    • 위험도별 계좌 분포 카드 팀 결정 필요 — 의심계좌 집계 뷰(파생 계층)를 MVP로 당기는 결정과 세트. 부착점이 있어 비용은 집계 쿼리 1개 수준
    • STR 제출 현황 카드 팀 결정 필요 — STR 기능 포함 여부 자체가 프로젝트 미결(아래 STR 경계 항목 참조)
    • 실시간 거래 피드 표시 범위(전체 롤링 / 요약+이상 강조 / 병행) 팀 결정 필요
  • 분석팀 조사 기능: 사건 생성·소견·관계 그래프·알림 종결은 MVP 확정. 이를 케이스 상세 안에 둘지 별도 심층분석 대시보드로 분리할지만 팀 결정 필요
  • 알림/케이스 큐: 시스템이 플래그한 이상거래가 쌓이는 목록. 위험도 정렬, 상태(신규/검토중/조사중/종결)·기간·위험도 필터. (§7 알림 생명주기 NEW→검토중→조사중→종결과 1:1 대응. 모니터링 큐 기본값은 신규·검토중 — 분석팀 이관분은 분석 큐로 이동)
  • 케이스 상세 화면: 알림 클릭 시 진입.
    • 계좌/거래 기본 정보 확정
    • 관계 네트워크 그래프 시각화 확정 — 허브 계좌는 펼치지 않고 요약 표시(허브 가드, 모든 허브 처리안에서 공통 필수)
    • 판단 근거: AI 모델 점수·패턴 분류·모델 버전 확정 / 규칙 히트 내역 팀 결정 필요 — 규칙 엔진은 현재 아키텍처에 없는 블록. 포함하려면 파이프라인 설계 1블록 추가 필요
    • 유사 과거 사례 참고 팀 결정 필요 — 유사도 검색은 미논의 신규 기능. MVP 포함 시 별도 설계 필요
    • 처리 액션(종결/에스컬레이션) 확정 / STR 제출 버튼 팀 결정 필요
  • 사건 조사 기록: 분석가 소견 작성, 계좌에 첨부 (팀 결정 토픽 4) 확정
  • 역할 분리 화면 + 권한 관리 (모니터링/분석/관리자, 팀 결정 토픽 5) 확정
  • 운영 지표 패널 (관리자): 큐 적체량, DLQ 건수, 판정 대기 최고 시간, 추론 에이전트 최근 접속 확정

제외

  • STR 문서 초안 작성 (LLM) — MVP 이후 여유 시 (팀 결정 토픽 4) 스트레치
  • 실시간 푸시(WebSocket) — change_seq polling으로 시작. 추후 같은 변경분 계약을 재사용하되 서버 push 발행기·연결 관리·재접속 보완이 필요한 스트레치 스트레치
  • Kafka 전환 — 공통 큐 어댑터로 호출부 변경 반경을 줄이되 의미 차이 검토·회귀시험·운영 설정이 필요한 전환 스트레치

⚠ STR 경계 일관성: "STR 제출 현황 카드·제출 버튼 포함 + 초안 작성 제외" 조합은 버튼의 동작이 정의되지 않는 공백을 만든다. STR 기능 포함 여부는 프로젝트 미결 사항이므로, 카드·버튼 포함 여부와 (포함 시) "상태 기록만인지"를 팀에서 확정해야 한다.

5. 서비스 아키텍처 — 전체 구조 확정

설계 순서: 구조(역할 블록) 먼저 확정 → 프레임워크 후행 매핑(§9). 배치 원칙 — 동기 백엔드는 외부에 즉시 응답을 약속하는 경계면에, 큐는 생산·소비 속도 차가 실재하는 곳에만, 비동기 워커는 아무도 기다리지 않는 자리에, DB는 진실의 원천으로 중앙에.

5.1 두 개의 독립 경로 — DB에서만 만난다

경로주체·성격흐름장애 격리
A. 거래 파이프라인기계 · 비동기 · 사용자가 없어도 계속 돈다① 수신 → ③ 큐 → ⑤ 적재 → ⑥ 배치 → ⑦ 추론 → ⑧ 결과·알림추론이 죽어도 수집·표시는 계속 (판정 대기 상태로 정직하게 표시)
B. 조사 워크플로우사람 · 동기 · 요청-응답⑨ 조회(change_seq polling) / 사건 기록·알림 상태 변경·권한 관리 쓰기대시보드 장애가 파이프라인에 영향 없음

거래 1건은 대시보드에 두 번 나타난다: 적재 직후 "판정 대기" 행으로 즉시, 추론 완료 후 같은 행이 "정상/이상(패턴)"으로 갱신. 행 업무키는 원천 거래번호 transaction_id, 변경분 커서는 별도 단조 증가 change_seq. 판정 지연은 배치 대기 0~5분 + 작업 픽업 ≤2분 + 추론·제출 + 다음 화면 polling의 합이며 UI가 명시적 상태로 보여준다.

5.2 거래 상태 머신 — 시스템의 중심축

큐가 아니라 DB의 상태·lease가 진실의 원천이다. 결과 제출은 현재 INFERENCING 상태이고 lease가 유효하며 attempt_id가 일치할 때만 수락한다. 타임아웃 이전 시도의 늦은 결과는 거절된다. 알림 생명주기는 별도 축: NEW → 검토중 → 조사중(이관) → 종결(오탐 조기 종결 / 조사 결과 입력). 알림은 기계가 만들고, 사건은 사람이 만든다.

5.3 백엔드 프로세스 편성 — 동기/비동기 구분 확정

동기/비동기의 경계선은 "엔드포인트가 어디 있냐"가 아니라 "요청-응답 프로세스냐, 상주 루프 프로세스냐"다. 후보 평가 1위 "FastAPI + Python Worker" 구조가 정확히 이 편성 — 배포 단위(컨테이너)로는 3개 프로세스다.

프로세스 (컨테이너)성격하는 일구조도 번호
API 서버 (FastAPI)동기 — 엔드포인트별 SLO 안에서 응답, 장기 작업 없음수신 관문(POST /transactions: 검증·ingest_id 발급→큐 투입→202) · 조회 API(change_seq polling, 알림·사건·권한) · 작업 API(GPU 에이전트의 작업 수령/결과 제출)①②③⑦⑧⑨
수집 워커 (Python)비동기 — HTTP 없음, 상주 루프큐 소비 → 거래·수신결과 DB 적재 → 큐 ACK, 신규 계좌 등록. 아무도 호출하지 않는다 — 스스로 돈다④⑤
추론 배치 워커 (Python)비동기 — HTTP 없음, 5분 타이머 루프PENDING 선점 → 서브그래프·특징 구성 → 추론 작업 준비⑥
  • 수신 관문은 동기다 — HTTP 호출 자체는 검증·ingest_id 발급→큐 투입 확인→202 응답으로 끝나고, 적재·판정은 응답과 무관하게 나중에 일어난다. 작업 API(⑦)도 호출은 동기지만 실어 나르는 파이프라인은 비동기다.
  • 워커를 API 서버와 분리하는 이유: 한 프로세스에 기술적으로 함께 둘 수는 있지만, 상주 루프의 부하·장애·재시작 주기를 요청-응답 서버와 격리하기 위해 배포 프로세스를 나눈다. 배치 작업이 API 응답을 막고 워커 장애가 대시보드까지 죽이는 결합을 피한다.
  • API를 둘로 쪼개지 않는 이유: 수신·조회 모두 "짧게 응답하는 HTTP"로 성격이 같음. 트래픽이 커지면 라우팅 분리만으로 쪼갤 수 있는 부착점 확보. FastAPI 코드의 async/await는 프로세스 내부 동시성이라는 별개 층위 — 이 구분과 무관.
  • 쿠버스피어의 추론 에이전트도 비동기 폴링 루프지만 모델팀 소유의 별도 환경(§7 G-2).

5.4 식별자·동시성·변경분 계약 확정

식별자·버전의미저장·검증 계약
transaction_id원천 거래내역의 거래번호전송 요청 ID가 아니다. 현재 공급원 안에서 거래 업무키로 사용하며 다중 공급원 도입 시 (source_id, transaction_id)로 범위를 확장한다. DB 내부 PK는 별도로 둘 수 있다.
ingest_id수신 관문이 전송 시도마다 발급하는 UUID202 응답·큐 메시지·수신결과를 연결. 같은 거래 재전송도 서로 다른 값. ACK 회계는 이 ID의 상태 합계로 검증한다.
payload_hash표준화한 원천 거래 내용의 해시같은 거래 업무키의 동일내용 재전송과 다른 내용 충돌을 구분. 충돌은 ID_CONFLICT로 격리하며 기존 거래를 덮어쓰지 않는다.
job_id추론 작업 식별자결과 멱등 키 (job_id, model_version)의 구성요소.
attempt_id·lease작업을 선점할 때마다 새로 발급결과 제출 시 상태·시도·lease를 조건부 갱신. 타임아웃 이전 시도의 늦은 결과는 거절한다.
model_version·config_version모델과 알림 임계값 설정 버전판정 결과에 함께 각인해 재판정·임계값 변경 뒤에도 당시 판단 조건을 재현한다.
change_seq거래 피드 변경 때 DB가 발급하는 단조 증가값change_seq > cursor로 신규·판정 갱신을 조회. 페이지 조회 시작 시 high-watermark를 고정해 동률·페이지 경계 누락을 막는다.

6. 수집 경계 설계 — 중복·검증 실패 처리 확정

항목확정 설계근거
수신 형태HTTPS 단건, 거래 10필드 + 원천 거래번호 transaction_id. 관문이 전송 시도별 ingest_id를 발급하고 큐 투입 확인 후 202와 함께 반환transaction_id는 거래내역의 번호값이고 전송 횟수를 세는 ID가 아님. 수신 관문은 기존 백엔드의 엔드포인트 1개 — 새 배포 단위 0개
중복·ID 충돌출구(DB)에서 멱등 흡수: 같은 거래 업무키·같은 payload_hash는 기존 원장에 연결하고 수신결과만 추가. 같은 업무키·다른 내용은 ID_CONFLICT로 격리하며 덮어쓰기·조용한 무시 금지큐가 최소 1회 전달이라 중복은 정상. DB 제약과 같은 트랜잭션의 수신결과 기록이 경합에서도 한 번만 원장을 만든다
수신 회계ACK ingest_id = 처리대기 + 신규적재 + 동일내용중복 + ID충돌 + DLQ202 응답 횟수와 거래 원장 행 수를 직접 비교하면 정상 재전송 때문에 반드시 어긋남. 미분류 차이를 유실로 판단
형식 실패수신 관문에서 즉시 거절(400) + 거절 로그. 파이프라인 미진입보낸 쪽이 실패를 즉시 알게 됨. 독성 메시지의 큐 유입 원천 차단
의미 이상수용 후 격리 플래그 저장 (미지 통화, 음수 금액 등)모니터링 도메인에서 "이상한 거래일수록 버리면 안 되는 데이터"
관문의 존재 이유검증 즉시 통보 + ingest_id가 있는 수신 확인(202) 책임 경계 + 큐 비노출중복 제거는 관문의 이유가 아님(위 참조). 은행은 HTTPS 엔드포인트 하나만 알면 됨

8. 설계 불변식 · 부착점 원칙 확정

불변식내용
쓰기 → ACK 순서수집 워커는 거래와 ingest_id 수신결과를 같은 DB 트랜잭션에 기록한 뒤에만 큐 ACK. 거래 업무키·payload_hash가 동일내용 중복과 ID 충돌을 구분
두 경로는 DB에서만 만남사용자 요청이 추론을 기다리지 않고, 추론 장애가 대시보드를 죽이지 않는다
조회 커서·시간 규율범위 조회는 시간 조건, 화면 변경분 조회는 단조 증가 change_seq. 페이지 시작 high-watermark를 고정해 동시 변경·페이지 경계 누락 방지
큐 어댑터 계약관문·워커는 publish/consume/ack/fail 추상 동작만 사용. SQS→Kafka 전환 시 호출부 반경을 줄이되, 소비자 그룹·offset·보존·재시도·DLQ·순서 의미가 달라 어댑터 구현과 운영 설정·회귀시험이 필요하다. 환경변수 변경만으로 끝난다고 보장하지 않는다
부착점 증명 원칙미루는 항목은 재사용할 계약·교체 인터페이스·예상 변경 파일과 회귀시험을 지금 명시한다. "기존 코드 무수정"을 과장해 약속하지 않으며, 핵심 데이터 모델을 바꾸는 항목은 지금 반영
결과 제출 멱등·lease(job_id, model_version) 유니크로 같은 결과 재제출을 흡수하고, 상태·attempt_id·lease 조건부 갱신으로 타임아웃 이전 시도의 늦은 결과를 거절. 결과·작업 COMPLETED·알림을 한 트랜잭션에 기록하고 알림은 inference_result_id 유니크로 중복 방지
버전·감사 보존판정에 모델·설정 버전을 각인. 알림 상태, 사건·소견, 임계값, 역할 변경은 행위자·시각·사유·요청 ID가 있는 append-only 감사 이벤트를 남긴다
알림은 기계, 사건은 사람모델 결과는 조사 지원 정보이지 확정 판정이 아니다 — §2.5 요구의 구조적 표현

9. 프레임워크 매핑 — 백엔드·인프라 확정, 프론트 최종 결정 대기

구조를 요구 명세로 확정한 뒤 기술스택 후보군 평가(별도 문서)를 재검토한 결과. 큐만 순위가 뒤집혔다 — Kafka 1위 근거의 43%(보존·재처리 25% + 순서 18%)가 Q-2·Q-4 확정으로 무력화됨.

분야선택구조와의 정합
FrontendReact (TypeScript·Vite·MUI·Cytoscape.js) Vue와 POC 비교 후 최종 확정change_seq polling·관계 그래프 화면. 평가 1.5점차 근접 — 동일 화면 POC로 팀 학습 속도 확인 후 확정
BackendFastAPI + Python Worker (동기 API 서버 1 + 비동기 워커 2 — §5.3)"동기 2역할(수신·조회) 한 프로세스 + 비동기 워커 분리"가 이 구조 그 자체. 세 프로세스가 전부 Python이라 데이터 계약(스키마)을 코드로 공유 — Java 조합 대비 직렬화 경계 없음. 평가 1위 강화
메시지 큐SQS (+ 어댑터 계층 필수) → Kafka 스트레치DLQ 내장, 운영 부담 최소, 명세 Q-1~5 충족. 어댑터는 호출부 변경 반경을 줄이는 장치이며 Kafka 전환에는 의미 차이 검토·회귀시험·운영 설정이 별도로 필요

AI·ModelPyTorch + PyG + scikit-learn이웃 샘플러(NeighborLoader)가 허브 처리안 B/C의 표준 도구. 클러스터 내부는 모델팀 소관
실행·배포Docker Compose (EC2 단일 호스트)I-1·I-2와 정합. 평가 1위 유지

10. 허브 계좌 처리 — 모델팀 위임 패키지 모델팀 위임

배경: 세트당 15개 준중앙은행 계좌(통화당 1개, 창작자 공식 확인)가 행의 8.9~9.6%, 2-hop 탐색 비용의 97.7~99.2%를 차지 (ML-08, R-11 교차검수 대기 중 — 인용 시 단서 필요). 검토 결과 허브 결정은 아키텍처 골격을 바꾸지 않는다 — 어느 안이든 "상한 있는 이웃 조회기 + 화면 허브 가드"라는 구조는 공통.

구분내용결정 주체
지금 고정 (서비스)추론 페이로드 예산 상한 · 이웃 조회 상한의 존재 · 조사 화면 허브 가드(펼치지 않고 요약 표시) · 계좌 등록부의 허브 플래그 컬럼 부착점아키텍처 확정 사항
위임 (모델팀)처리안 선택 — A 완전 제거(단독 자격 미달: 판정 커버리지 구멍) / B 샘플링 상한 / C 허브 플래그 특징 + 상한 / D 메시지 전달만 차단. 상한 값·특징 구성 포함모델팀 (예산 내 자유)
결정 기한백엔드가 서브그래프 조회기를 구현하기 전 — 모델팀이 "서브그래프 명세서"(hop 수·상한·허브 취급) 1장을 백엔드에 전달하는 형태일정에서 역산
C(허브 플래그 + 샘플링 상한)로 시작하고 B/D를 비교 실험 항목으로 등록하는 것을 권장 — 허브 정체가 추정이 아닌 창작자 확인 사실이라 특징화가 정당하고, 상한만으로는(B) 그 정보를 버리는 셈이기 때문. 제약 2개는 어느 안이든 준수: ① 허브 거래도 판정 커버리지에 포함(전체 행의 8.9~9.6%, 세탁 라벨 점유 10.8~25.6%) ② 시간창은 해결책이 아님(시간축·차수축 직교, 허브 하루 최대 58,260건).
