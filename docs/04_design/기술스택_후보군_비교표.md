# AML 웹서비스 업무 분야별 기술 후보군

| 추천도 | 의미 |
|---|---|
| ★★★ | 1순위 추천 |
| ★★☆ | 충분히 가능한 대안 |
| ★☆☆ | 특정 조건에서만 선택 |
| 제외 | 현재 웹서비스 범위에는 부적합 |

## 최종 추천 조합

| 업무 분야 | 추천 기술 | 주요 작업 단위 | 조합이 필요한 이유 |
|---|---|---|---|
| Frontend | React + Vite + TypeScript + MUI + Cytoscape.js | 관제 화면, 알림·사례 화면, 권한별 UI, 거래 관계 그래프, REST·WebSocket 연결 | React는 UI, Vite는 개발·빌드, MUI는 공통 화면 부품, Cytoscape.js는 거래 그래프를 담당 |
| Backend | FastAPI + Pydantic + SQLAlchemy + Alembic | API, 로그인·권한, 사례 관리, 배치 수신, 모델 추론 호출, 결과 전달 | FastAPI는 API, Pydantic은 입출력 검증, SQLAlchemy는 DB 연결, Alembic은 스키마 변경 이력을 담당 |
| DB · Data Pipeline · Infra | PostgreSQL + Kafka + confluent-kafka + Docker Compose | 목업 거래 생성, 실시간 수신, 1분 배치, 거래·탐지·사례 저장, 통합 실행 환경 | Kafka는 거래 이벤트 전달·재처리, PostgreSQL은 서비스 데이터 저장, Docker Compose는 여러 프로그램의 실행 환경을 통일 |
| AI · Model (2명) | PyTorch + PyTorch Geometric + scikit-learn | 공통 전처리, GNN 실험, 1단계 이진분류, 2단계 패턴 다중분류, 평가·모델 저장 | PyTorch는 학습 기반, PyG는 GNN 연산, scikit-learn은 전처리·기준 모델·평가 지표를 담당 |

## Frontend 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [React + Vite](https://react.dev/) | 자료와 라이브러리가 많음 · 컴포넌트 분업이 쉬움 · 대시보드·그래프 연동에 유리 | 상태 관리와 폴더 규칙을 팀이 정해야 함 | ★★★ |
| [Vue + Vite](https://vuejs.org/guide/introduction.html) | HTML과 비슷해 입문이 쉬움 · 단일 파일 컴포넌트가 직관적 | React보다 선택 가능한 예제·라이브러리 폭이 좁음 | ★★☆ |
| [Angular](https://angular.dev/overview) | 라우팅·폼·의존성 주입 등 기능이 통합됨 · 큰 프로젝트의 구조가 명확 | 학습 범위와 초기 코드량이 많아 부트캠프 MVP에 무거움 | ★☆☆ |
| [Qt 6](https://doc.qt.io/qt-6/qt-intro.html) | 설치형 데스크톱 앱과 네이티브 UI에 강함 | 브라우저 웹서비스와 맞지 않음 · 배포가 별도이며 WebAssembly 사용은 복잡 | 제외 |

## Backend 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [FastAPI](https://fastapi.tiangolo.com/features/) | AI와 같은 Python 사용 · 입출력 검증과 API 문서 자동 생성 · 비동기·WebSocket 지원 | ORM·마이그레이션·관리자 화면을 별도 조합해야 함 | ★★★ |
| [Django + Django REST Framework](https://docs.djangoproject.com/en/5.2/intro/overview/) | 인증·관리자·ORM이 기본 제공됨 · 자료가 많고 CRUD 구현이 빠름 | 프레임워크 학습 범위가 넓고 실시간 파이프라인·추론 API에는 다소 무거움 | ★★☆ |
| [Flask](https://flask.palletsprojects.com/) | 구조가 단순하고 작은 API를 빠르게 만들기 쉬움 · 자료가 많음 | 검증·문서·인증·프로젝트 구조를 직접 선택해야 해 규모가 커질수록 부담 | ★★☆ |
| [Spring Boot](https://docs.spring.io/spring-boot/index.html) | 기업용 Java 생태계·보안·운영 기능이 강함 · 참고자료가 많음 | Java와 Python 모델 사이 연결이 추가되고 초심자 팀에는 설정·학습량이 큼 | ★☆☆ |

## DB 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [PostgreSQL](https://www.postgresql.org/docs/current/) | 트랜잭션·관계형 조회·JSON·분석 SQL이 강함 · 거래·탐지·사례 데이터를 한곳에서 관리 가능 | 초기 스키마와 인덱스 설계가 필요 | ★★★ |
| [MySQL](https://dev.mysql.com/doc/refman/8.4/en/) | 널리 사용됨 · 자료가 많음 · 일반적인 CRUD와 트랜잭션 처리에 충분 | 복잡한 분석 조회와 확장 기능은 PostgreSQL 쪽이 더 편리함 | ★★☆ |
| [SQLite](https://www.sqlite.org/docs.html) | 설치가 거의 필요 없고 로컬 개발이 간단 | 동시 쓰기와 서버 운영에 한계가 있어 실시간 팀 서비스의 메인 DB로 부적합 | ★☆☆ |
| [DuckDB](https://duckdb.org/docs/stable/) | CSV·Parquet 대용량 분석과 로컬 SQL이 편리 · AI팀 실험에 유용 | 서버형 운영 DB가 아니므로 PostgreSQL을 대체할 수 없음 | 보조 |

## 실시간 데이터 전달 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [Apache Kafka](https://kafka.apache.org/documentation/) | 이벤트 보존·재처리·순서 관리·소비자 분리가 가능 · 실시간 입력→1분 배치 구조를 잘 표현 | 브로커·토픽·파티션·오프셋 개념과 운영 설정을 배워야 함 | ★★★ |
| [RabbitMQ](https://www.rabbitmq.com/docs) | 작업 큐와 라우팅이 직관적 · 작은 규모에서 시작하기 쉬움 | 장기간 이벤트 보존·재처리·스트림 분석은 Kafka보다 약함 | ★★☆ |
| [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/) | 가볍고 빠름 · 소비자 그룹과 이벤트 보관을 지원 | Redis 운영 지식이 필요하고 대규모 이벤트 스트리밍 자료·기능은 Kafka보다 제한적 | ★☆☆ |

## AI · Model 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [PyTorch + PyTorch Geometric](https://pytorch-geometric.readthedocs.io/en/stable/) | PyTorch 기반 GNN 구현·미니배치·샘플링 지원 · 사용자 정의 2단계 모델 실험이 쉬움 | 그래프 구성·샘플링·메모리 관리 학습이 필요 | ★★★ |
| [PyTorch + DGL](https://www.dgl.ai/dgl_docs/) | 대규모 그래프·메시지 패싱·분산 학습 기능이 강함 | 현재 팀 기준 PyG보다 학습자료와 예제 통일이 어려움 | ★★☆ |
| [TensorFlow + Keras](https://www.tensorflow.org/guide/keras) | 일반 딥러닝 학습·저장·배포 흐름이 잘 갖춰짐 | 이번 PyTorch·GNN 중심 설계를 바꿀 만큼의 이점이 적고 GNN 라이브러리 선택이 추가됨 | ★☆☆ |
| [scikit-learn](https://scikit-learn.org/stable/) | 전처리·기준 모델·교차검증·분류 평가 지표가 편리 | GNN 주 모델을 만들 수 없어 단독 사용은 불가 | 보조 |

## 실행 · 배포 후보

| 후보 | 장점 | 단점 | 추천도 |
|---|---|---|:---:|
| [Docker Compose](https://docs.docker.com/compose/) | Frontend·Backend·Kafka·PostgreSQL 실행 환경을 한 파일로 통일 · 팀원별 환경 차이를 줄임 | Docker 기본 개념과 PC 자원이 필요 | ★★★ |
| 개별 로컬 실행 | 처음에는 가장 단순하고 디버깅이 쉬움 | 설치 버전과 실행 순서가 팀원마다 달라져 통합 단계에서 오류가 늘어남 | ★★☆ |
| [Kubernetes](https://kubernetes.io/docs/home/) | 대규모 운영·자동 복구·확장에 강함 | 부트캠프 MVP에는 학습량과 설정이 지나치게 큼 | 제외 |
