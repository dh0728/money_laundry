## 문제 상황

### 막힌 내용 1 — 주피터랩 서버 다운 (약 3시간 30분 지연)

- 작업 중 서버가 갑자기 내려가 개발이 약 3시간 30분 지연됨.
- 재발 방지를 위해 필요한 것: 원인 확인(메모리 초과인지 다른 문제인지), 그리고 장시간 작업 중간 저장 기준. 전처리 산출물이 `processed_multiclass/`에 저장돼 있어 전처리는 다시 안 돌려도 되지만, 모델 학습 중이었다면 처음부터였음.
- 참고로 전처리는 60초, 창 스윕은 73초, 모델 학습은 약 8분이라 재실행 비용 자체는 크지 않음. 지연의 대부분은 서버 복구 대기였음.

### 막힌 내용 2 — recall 0.70은 HI-Small로는 도달 불가능함이 확인됨

오늘 가장 중요한 발견이자, 내일 계획을 그대로 두면 안 되는 이유다.

- 사건이 **정답대로 완벽하게 묶였다고 가정한 상한 대조군(attempt 규칙)** 의 성능이 **0.6791** 이다. 즉 사건 묶는 규칙을 아무리 잘 고쳐도 이 데이터로는 0.70에 못 미친다.
- 목표까지의 거리를 원인별로 쪼개면 이렇다.

| 층 | 구간 | 크기 | 메우는 방법 |
|---|---|---|---|
| 1층 | v1 → v2 (0.395 → 0.461) | +0.066 | **오늘 완료** (누수 제거 + 창 재선택) |
| 2층 | v2 → 상한 (0.461 → 0.679) | +0.218 | 사건 연결 규칙 개선 (계좌 연결 기준 변경) |
| 3층 | 상한 → 목표 (0.679 → 0.700) | +0.021 | **사건 구성으로는 불가. 표본 크기 문제** |

- 상한 대조군의 학습 표본은 **180건에 8종**, 수법당 평균 22.5건이다. 이 규모로 8종을 학습·검증하는 것은 무리다.
- 근거 보강: 학습곡선이 train 25%→100%에서 0.403→0.569로 **아직 우상향**이다. 곡선이 평평해지지 않았다는 건 표본을 늘릴 여지가 남아 있다는 직접 증거다.
- 이건 새로 생긴 문제가 아니라 전처리 설계 보고서 §5.1이 "[심각] HI-Small은 2차 모델 학습에 표본이 부족하다"로 이미 지적한 내용이며, 오늘 상한 대조군 실측으로 **정량 확인**된 것이다.

### 막힌 내용 3 — 시간창으로는 못 묶이는 수법이 있음

- BIPARTITE와 STACK은 시간창을 무제한으로 열어도 조각난 채 남는다. 세탁 거래끼리 계좌를 직접 공유하지 않기 때문이다.
- 시간창 조정으로는 해결 불가. 정상 거래를 경유한 2홉 연결이나 계좌 커뮤니티 기반 묶기가 필요하다.

### 완료 기준

원래 잡았던 "recall 0.70 달성"은 **오늘 확인한 상한(0.679) 때문에 HI-Small에서는 달성 불가능한 기준**이다. 그대로 두면 도달할 수 없는 목표를 계속 쫓게 되므로 아래로 나눈다.

| 구분 | 완료 기준 | 달성 가능성 |
|---|---|---|
| **내일 안에** | 모델 구조를 팀원에게 설명할 수 있는 수준으로 파악 · 결정 안건 5건 상정 | 가능 |
| **이번 주** | 사건 연결 규칙 개선(2홉/커뮤니티)으로 macro-recall **0.55 이상** — §5.4의 2층 일부 회복 | 가능 |
| **데이터 확대 후** | macro-recall **0.70 이상** — 화두 12 결정 + 원본 재수급이 선행 조건 | 선행 조건 충족 시 |

- 추가로, 성능 수치만 쫓지 않기 위해 **macro-precision을 항상 함께 본다**. 오늘도 recall만 올리는 기법 2가지(사전확률 보정 α, 다중 스케일 증강)를 시험했다가 precision이 0.60 → 0.42로 떨어져 기각했고, 그 근거를 `model_multiclass_v2/summary.json`에 남겨뒀다.
