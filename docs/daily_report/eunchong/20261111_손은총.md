## 실적

- 완료한 일 + 산출물 경로/이슈 번호 :
1. **블록(묶음) 단위 유형분류 설계 조사**: 학습 전에 서버 코드와 train 자료를 세어 선택지를 정리함. 한 시도의 거래만 담은 깨끗한 묶음에서는 거래 목록의 모양만 보고도 '그날 보인 모양'을 거의 다 맞힐 수 있음(위 한계 0.996). 그래서 모델이 값어치를 낼 곳은 '다른 시도와 섞인 묶음'과 '다음 단계 미리 보기' 둘뿐임. 그 밖에 센 것: 시도 길이 중앙값 28.5일 · CYCLE 749시도는 모두 마지막 날에만 고리가 닫힘 · 최근 14일만 보면 앞 거래를 잃는 묶음 0.510 · 다른 시도와 계좌 · 기간이 겹치는 시도 0.607. 서비스 저장소에는 묶음 단위 유형분류기가 없고(거래마다 유형을 낸 뒤 Alert 를 묶음), Alert 묶기는 한 블록 14일 · 한 걸음 7일 상한이 있음.
2. **팀 회의 결정 반영 → 정의 한 장**: 회의에서 무패턴 뺌 · BIP · STACK 뺌(정답 6칸) · 보이는 대로 학습 · 시도 단위(이진분류가 만든 Alert 를 유형 모델에 넣음)로 정함. 여기에 덜 끝난 묶음도 학습 · 채점에 넣음 · 노이즈 시도는 train 에서만 뺌 · 아무 모양도 안 보이면 RANDOM · 왕복 고리는 CYCLE · 묶음마다 같은 무게 · 14일로 자르지 않고 합쳐서 봄 · 성적표 둘을 냄으로 정해, 13가지를 한 장에 모으고 근거 숫자 표 12개를 저장함. 시도를 끝까지 보면 보인 모양이 원래 유형과 0.969 같고, 덜 끝난 묶음까지 넣으면 0.625 가 같음.
3. **묶음 안의 거래 지도를 통째로 보는 모델 첫 판(학습 · val 채점)**: 묶음 = 한 시도의 거래를 첫 거래부터 그날까지 쌓은 것(train 3,214시도 19,414장 · val 2,203시도 13,892장). 계좌를 점, 거래를 화살표로 둔 작은 그래프를 통째로 받아 6칸을 답하는 모델을 새로 짬(화살표마다 금액 · 첫 거래부터 지난 날 · 마지막 거래까지 남은 날 · 계좌 번호와 달력 날은 안 넣음). 사전기록을 고정한 뒤 CPU 로 씨앗 3개를 학습함(하나 4분쯤). val 6유형 macro 정밀도 / 재현율: 성적표 1(모든 묶음 · 보이는 대로) 0.9982 / 0.9984(학습 없는 모양 규칙 0.9882 / 0.9854) · 성적표 2(시도마다 마지막 묶음 · 원래 유형) 0.8778 / 0.8268(모양 규칙 0.8496 / 0.7967). 성적표 2 유형별: FAN-OUT 0.995 / 0.755 · FAN-IN 0.871 / 0.788 · CYCLE 0.749 / 0.952 · SC-GA 0.998 / 0.759 · GA-SC 1.000 / 0.706 · RANDOM 0.654 / 1.000. 틀린 것은 거의 모두 거래를 다 봐도 제 유형의 모양이 안 나오는 시도 372개(val 시도의 0.169)이고, 모양이 나온 1,831시도에서는 씨앗마다 0 ~ 2개만 틀림.
4. **누수 · 미래 참조 점검**: 점수가 너무 높아서 따로 점검함. 묶음에 그날 마감 뒤 거래가 든 것 0 / 33,306 · train 과 val 에 겹치는 시도 0 · 거래 0 · 정답을 뒤섞어 학습하면 0.054 / 0.167(한 칸으로만 답함) · 점 번호와 화살표 차례를 뒤섞어도 답이 그대로 · val 로 epoch 를 고른 효과는 작음(epoch 5 뒤 맞은 몫 0.978 이상). 묶음 안의 연결만 무작위로 바꾸면 성적표 2 가 0.877 / 0.826 → 0.344 / 0.287 로 떨어짐. 실수로 생긴 누수는 없었고, 점수가 높은 까닭은 설계에 있음: 묶음을 정답(시도 번호)으로 만들어 한 사건의 거래만 깨끗하게 들어가고, 정답이 그 묶음의 모양에서 정해짐. "닫힌 고리만 있으면 CYCLE" 한 줄 규칙만으로도 CYCLE 정밀도 · 재현율이 1.0 임.
5. **test 한 번 채점(재학습 없음)**: 사전기록을 따로 고정하고, 같은 코드로 val 을 다시 만들어 앞 결과와 똑같이 나오는 것을 확인한 뒤 돌림. 성적표 1 0.9985 / 0.9986(모양 규칙 0.9926 / 0.9937) · 성적표 2 0.7512 / 0.6830(모양 규칙 0.7382 / 0.6773). 성적표 2 유형별: FAN-OUT 0.735 / 0.797 · FAN-IN 0.587 / 0.776 · CYCLE 0.785 / 0.484 · SC-GA 0.995 / 0.522 · GA-SC 1.000 / 0.518 · RANDOM 0.405 / 1.000. val 보다 낮은 것은 끝까지 본 모양이 원래 유형과 같은 시도 몫이 test 0.660 · val 0.831 이기 때문임. 마지막 거래 날이 뒤쪽일수록 이 몫이 낮고(0.764 → 0.614) test 시도의 0.427 이 마지막 나흘에 몰려 있어, 자료가 끝나는 날에 진행 중이던 시도가 잘려 들어온 것으로 봄. 모델은 모양이 나온 시도에서 0.9992 를 맞히고, 안 나온 시도에서는 못 맞힘.

## 문제 상황

- 막힌 내용 : 오늘 점수는 '묶음이 완벽하게 만들어졌을 때'의 값이라 서비스 성능으로 말할 수 없음. ① 어느 거래들이 한 사건인지를 정답으로 알려 준 것인데, 서비스에서는 이진분류와 Alert 묶기가 알아내야 함. ② 지금 저장소는 거래마다 유형을 낸 뒤 Alert 를 묶는 차례라, 회의에서 정한 'Alert 를 유형 모델에 넣음'은 새로 만들어야 함. ③ 묶기 함수는 14일을 넘는 블록을 합치지 않고 한 걸음도 7일 안이어야 하는데, HI-Large 시도의 0.733 이 15일 이상에 걸침. 최근 14일만 보면 제 모양이 보이는 시도가 SC-GA 0.12 · GA-SC 0.26 · CYCLE 0.21 뿐임. ④ HI-Large 의 이진 점수가 서버에 없어 실제 Alert 를 만들어 볼 수 없음. ⑤ 거래를 다 봐도 제 유형의 모양이 안 나오는 시도(val 0.169 · test 0.340)는 어떤 방법으로도 원래 유형을 맞히기 어려워, 원래 유형 점수의 위쪽 한계가 됨.
