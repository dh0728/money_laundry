## 실적

- 추론 서버 네이버 이전 결과 확인
  - KubeSphere와 같은 조건(HI-Medium 20개 은행, 백필 7일, 분석 9일)으로 재실행하여 거래 3,079,111건 전부 대조, 점수 상관 0.99956, Alert 388개와 일별 Alert 수 동일
  - 의심 거래 1,822건 → 1,827건, 패턴 세탁 재현율 75.23% → 75.37%로 의심 기준 근처 13건만 갈려 이전 정상 확인
- 누적 처리시간 증가 원인 진단
  - 날이 갈수록 같은 규모 날의 처리시간이 늘고 마지막 날 거래 통합이 제한 시간을 넘겨 실패하는 문제로, worker 제한 시간을 30분 → 120분으로 늘려 우선 완료되도록 조치
  - DB 통계와 실행 계획 확인 결과 DB 서버 메모리 2GB 대비 DB 15GB, 매일 누적 이력을 다시 읽는 구조, 은행 보고 원문 표(7.3GB, DB의 49%)의 반복 읽기가 겹친 것으로 확인
- 은행 보고 원문 분리
  - 은행 보고 암호문을 별도 표로 분리하고 조회에 한 번도 쓰이지 않던 색인(685MB) 제거
  - 실행 1회 디스크 읽기 약 636GB → 296GB, 거래일 9/7~9/10 하루 처리시간 23.5/24.6/15.0/15.3분 → 14.5/15.8/11.4/12.0분, 시간 초과 없이 완료
- 분석 입력 고정 급증 원인 수정
  - Performance Insights로 특정 날 분석 입력 고정이 급증한 원인이 점수 확인 SQL 한 문장임을 확인하고, 뜻은 유지한 채 대상 밖 거래만 먼저 골라 대조하도록 변경
  - 거래일 9/13 분석 입력 고정 2,922초 → 429초, 그날 전체 61.1분 → 20.1분
  - 분석 입력 고정에서 대상 집합을 중복으로 임시 복사하던 부분 제거

## 문제 상황
- 실행 도중 DB 서버 디스크 버스트가 바닥나면 모든 단계가 느려져(처리량 약 54MB/s → 21MB/s) 수정 후 9일 전체 시간을 같은 조건으로 비교하지 못함
## 내일 계획
- 분석 입력 고정이 바뀐 거래만 다시 계산하도록 변경
- 중복 임시 복사 제거 효과 측정
