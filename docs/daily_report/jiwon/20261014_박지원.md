## 실적

- Alert 계획 준비 단계 성능 개선
  - 데이터가 쌓일수록 계획 준비 시간이 폭증하는 문제(9일째 990초)를 해결하기 위해 구간별 소요 시간·횟수 계측을 추가하여 병목 구간 확인
  - 공개 근거 중복 조회 제거, 비교용 경량 렌더링, 계획 묶음 저장을 적용하여 결과 변화 없이 합성 데이터(OPEN 1만 건) 기준 81.4초 → 53.0초로 단축
  - worker가 입력 전체를 메모리에 올리지 않고 필요한 열만 순차로 읽도록 변경하여 Alert 저장 단계 메모리 67% 절감
  - 로컬 데모 10일 연속 실행을 처음으로 끝까지 완료하고, 9일째 작업 시간 3,075초 → 778초 확인
- 시스템 기준 시각을 업무 시각으로 통일
  - 시연 데이터는 2023년인데 수신·분석 기준 시각은 실제 시각(2026년)을 사용하여 커버리지 달력이 1,144일로 불어나는 문제 발견
  - 수신·분석 기준·처리 기록 시각을 업무 시계 하나로 통일하고, dev·local에서 실제 시각 기준 자동 분석 예약 중지
  - Java 테스트 295개·worker 테스트 255개 통과, 데모 이틀 실행에서 달력 5~6일·2일째 계획 준비 79초 → 30초 확인
- Alert 생성 규칙 개정
  - 증분 Alert 생성의 전제 조건으로, Alert 묶음이 정해진 기간(240시간) 안에서만 만들어지도록 생성 규칙 개정
  - 기간을 넘는 묶음이 만들어지던 기존 결함 2건을 수정하고, 동률일 때 거래 id 기준으로 항상 같은 결과가 나오도록 처리
  - 새 테스트 6개 추가, 원장 실측에서 품질 지표가 기존 생성기와 동일함을 확인
- 증분 처리 구현 설계
  - 매일 원장 전체를 다시 처리하는 구조를 바꾸기 위해 증분 Alert 생성과 INTEGRATE 누적 재처리 제거의 구현 설계 문서 작성
  - 입력 사본 방식, 변경 거래 목록 저장, 미배정 사유 저장 방식 등 결정 사항과 DB 마이그레이션 범위 확정
- INTEGRATE 누적 재처리 제거
  - 매일 지난 모든 날짜의 보고를 다시 복호화하던 구조를, 처리할 날짜를 먼저 판정하여 변경된 날짜만 복호화하도록 개선
  - Java 테스트 296개·worker 테스트 261개 통과, 새 테스트가 이전 코드에서는 실패함을 확인
  - (진행 중) 데모 10일 연속 실행으로 INTEGRATE 메모리 사용량 측정(기존 10일째 2.36GiB)

## 문제 상황
- INTEGRATE 메모리 개선 효과는 데모 10일 실행 측정이 끝나야 확인 가능
- 증분 Alert 생성 전까지는 매일 원장 전체와 공개 Alert 전체를 다시 처리하여, 데이터가 쌓일수록 처리 시간과 메모리 사용량 증가

## 내일 계획
- INTEGRATE 메모리 측정 결과 정리 및 기존 대비 개선 확인
- 증분 Alert 생성 1단계(입력 기반: 공유 입력 사본, 변경 거래 목록 테이블) 구현 착수
