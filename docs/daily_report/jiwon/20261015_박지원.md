## 실적

- 거래 통합 단계 메모리 개선 검증 완료
  - 변경된 날짜만 복호화하도록 바꾼 거래 통합 단계를 데모 10일 연속 실행으로 측정하여, 최대 메모리가 10일 내내 약 1.0~1.2GiB로 일정하게 유지됨을 확인(기존 1.2GiB → 10일째 2.36GiB로 증가)
- 분석 입력 고정 단계 정지 문제 해결
  - 데모 2일째 분석 입력 고정 단계가 약 35분 걸리는 문제를 발견하고, 새 실행 데이터에 DB 통계가 없어 비효율적인 실행 계획이 선택되는 것이 원인임을 확인
  - 새로 넣은 데이터를 통계가 있는 임시 표로 조인하고 입력 고정 직후 통계를 갱신하도록 수정하여, 같은 쿼리 180초 초과 → 1.1초로 개선
- 분석 입력 장부 전환
  - 실행마다 원장 거래·점수·공개 Alert·멤버 사실 전체를 복사하던 구조를, 바뀐 것만 기록하고 각 실행은 자기 시점에 유효한 행만 읽는 버전형 장부로 전환
  - 설계안을 별도 검수받아 구현을 막는 문제(외래 키 제약, 이전 날짜 재실행 시 누락)를 사전에 찾아 반영
  - 데모 10일 연속 실행에서 입력·점수·멤버 사실이 기존 방식과 차이 0건임을 확인
  - 거래 입력 사본 406만 행 → 69만 행, 점수·공개 Alert·멤버 사실 사본(10일 누적 약 419만 행) → 0행
  - 분석 입력 고정 단계가 날짜가 쌓여도 거의 늘지 않게 되었고, 8일째 하루 처리 시간 711초 → 507초로 단축
- 장기·대용량 확장성 검증 계획 수립
  - 실서비스처럼 데이터가 수개월 쌓여도 버티는 구조인지 보이기 위해 HI-Large 데이터로 장기 누적 실험을 계획하고, 사용 가능한 기간(시험 분할 제외 75일) 확인
  - 현재 데모 점수기는 전체 거래의 30%를 의심 거래로 만들어 현실(1% 안팎)과 달라 실험 결과가 의미 없음을 확인하고 실험 조건 재설계
- 증분 Alert 생성 엔진 설계
  - (진행 중) 그날 바뀐 거래 주변만 다시 계산하는 Alert 생성 방식의 설계를 작성하고 독립 검수 진행
- 팀원 이진분류 모델(v10) 연동 검토
  - 모델 출력은 기존 모델 계약대로 바로 연결 가능하나, 입력은 거래 이력과 계좌 KYC로 만든 2홉 그래프가 필요하여 추가 연결 작업이 필요함을 확인
  - 변환 코드가 없어 기준 그래프를 원본 데이터와 직접 대조하여 입력 생성 규칙을 역추적(엔티티 유형 362/362건, 국가 2,730/2,730건 일치)
  - 팀원에게 확인할 질문 8개 정리(배치 추론 코드, 중복 처리 규칙, 짧은 누적 기간에서의 성능, 임계값 등)
- 백엔드 코드 구조 정리 및 dev 병합
  - 흩어져 있던 코드를 파이프라인 단계 순서(파일 수집·적재 → 거래 통합 → 분석 입력 고정 → 모델 추론 → Alert 구성 → Alert 공개 → 조회·조사·대시보드)에 맞춰 Java 패키지와 worker 폴더로 재배치하고, 조사 쪽 컨트롤러를 역할별 4개로 분리
  - 팀원의 외부 추론 서버 인증서 설정 변경을 충돌 없이 병합하고 새 구조로 이동
  - 동작 변경 없이 Java 테스트 303개·worker 테스트 268개 통과, Docker 이미지 빌드와 dev 구성 검사 통과

## 문제 상황
- 장기 확장성 실험에 쓸 점수기 결정 필요(라벨 기반 점수기 복원 또는 팀원 모델 사용)
- 팀원 모델 연동에 계좌 KYC 정보가 필요하나 worker 권한 밖이고 엔티티 이름이 암호화되어 있어 공급 방식 결정 필요
