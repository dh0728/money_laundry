## 실적

- dev HI-Large 부하 테스트 측정
  - 상위 10개 은행 데이터로 dev에서 5일치를 돌려 하루 처리 시간 32.4~62.4분, 10만 건당 처리 시간 9.5분 → 14.3분으로 누적량에 따라 늘어나는 것을 확인
  - 단계별로 나눠 모델 구간(입력 준비~추론 결과 회수)이 전체의 75~85%이고, 나머지 단계도 5.6분 → 15분으로 늘어남을 확인
  - DB 사용량이 거래 1건당 약 3.4KB(173만 건에 5.9GB)로, 추세상 누적 약 3,000만 건에서 하루 6시간을 넘을 것으로 추정되어 테스트를 멈추고 이 결과를 개선 전 기준선으로 사용
- 증분 처리 설계
  - 매일 쌓인 전체 이력을 다시 계산하는 곳이 모델 추론, 분석 입력 고정, Alert 구성 세 곳임을 확인하고, 모두 그날 들어온 양만 처리하도록 바꾸는 설계 작성
  - 분석 입력 장부에 바뀐 거래를 바로 찾는 색인 2개를 초기 스키마에 추가(테이블 변경 없음), 300만 행에서 변경분 조회가 색인을 쓰는 것과 worker DB 테스트 48개 통과 확인
- 추론 서버 v10 피처 하루치 갱신 구현
  - 원장 사본을 하루치 조각을 더하는 방식으로 바꾸고, v10 피처 누적값을 추론 서버에 보관하여 매일 그날 거래로만 갱신하도록 구현(과거 거래 정정 시에는 전체 재구축)
  - 추론 서버 테스트 67개 통과, 로컬 HI-Medium 16일 연속 실행에서 1·2·9·16일째 점수가 전체 재계산과 차이 0건임을 확인
  - v10 피처 갱신 시간이 하루 3~19초로 날짜가 쌓여도 늘지 않게 되었고, 남은 시간은 대상 거래별 모델 계산으로 그날 거래 수에만 비례함을 확인
  - 모델 입력을 고정 기간으로 자르는 방안은 시간 이득이 거의 없고 모델 재학습이 필요하여 채택하지 않음
- Alert 구성 새 의심 거래 기준 설계
  - 묶는 규칙은 그대로 두고 오늘 의심 거래와 그 주변 약 17일, 거래는 약 27일치만 읽어 열린 Alert에 붙이도록 하여, 하루 비용이 쌓인 기간과 상관없이 일정해지도록 설계(새 테이블 없음)
  - Alert 기간이 240시간을 넘으면 원래 Alert와 연결된 후속 Alert로 만들기로 확정
- Alert 묶기 범위 비교 실험
  - (진행 중) 묶을 때 과거를 며칠까지 볼지 정하기 위해 누적·60일·30일 세 경우를 비교하는 실험 시작
  - HI-Large 4개 은행 97일(거래 501만 건, 세탁 거래 9,519건)로 모델 점수를 한 번 계산한 뒤, 실제 Alert 생성 코드로 하루씩 재현하여 처리 시간·메모리·Alert 수와 세탁 거래 포함률을 비교 예정

## 문제 상황
- dev DB가 운영 DB와 같은 RDS(30GB)를 써서 HI-Large 97일 전체 적재(추정 약 89GB)가 불가하여, 장기 실행 전에 저장 공간 확보나 오래된 데이터 보관 정책 필요
- 로컬 Docker 메모리(3.66GB) 한계로 분석 입력 고정 단계에서 API 컨테이너가 한 번 강제 종료되어 큰 데이터의 로컬 검증에 제약
- v10 증분 계산을 위해 계좌 번호 규칙을 고정하여 점수가 이전 dev 결과와 소폭 달라질 수 있어 팀원에게 공유 필요

## 내일 계획

- v10 하루치 갱신을 dev에 배포하고 HI-Large를 다시 돌려 하루 처리 시간이 일정해지는지 확인
