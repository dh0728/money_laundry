## 실적

- Alert 묶기 범위 비교 실험
  - Alert를 묶을 때 과거를 며칠까지 볼지 정하기 위해 HI-Large 4개 은행 97일(거래 501만 건, 세탁 거래 9,519건)로 같은 모델 점수를 두고 누적·60일·30일 세 경우를 재현하여 비교
  - 세탁 씨앗이 Alert에 들어간 비율은 누적 51.0%·60일 51.1%·30일 51.4%로 차이가 없었고, 여러 Alert로 나뉜 세탁 패턴은 누적 342개 대비 60일 365개(+7%)·30일 420개(+23%)
  - 하루 묶기 시간은 누적이 날짜에 비례해 97일째 11.5초까지 늘어난 반면, 60일은 창이 찬 뒤 6.7초에서 일정하게 유지됨을 확인하고 60일로 확정
- Alert 구성 새 의심 거래 기준 구현
  - 매일 전체 기간을 다시 묶던 Alert 구성을, 최근 60일 범위의 거래·의심 거래와 그날 닿은 Alert만 읽고 계획·공개하도록 변경(테이블 변경 없음)
  - worker 테스트 249개·Java 테스트 305개 통과, 로컬 HI-Medium 16일 연속 실행에서 날짜별 의심 거래·Alert 수가 16일 모두 변경 전과 같음을 확인
- Alert 묶기 시간 상한 조정
  - 데이터셋별 세탁 패턴을 측정하여 기존 상한(거래 간격 4일·Alert 기간 10일)이 HI-Small 기준 값이라 시연용 HI-Medium 패턴의 간격 90.39%·기간 95.32%만 담는 것을 확인
  - 상한을 거래 간격 7일·Alert 기간 14일로 바꿔 HI-Medium 패턴을 간격·기간 모두 100% 담도록 조정
  - 같은 모델 점수로 비교하여 세탁 씨앗의 Alert 포함 비율이 HI-Medium 64.06% → 65.35%, HI-Large 51.12% → 52.58%로 개선, HI-Large 하루 묶기 시간은 6.9초 → 9.5초

## 문제 상황
- 모델이 의심 거래로 잡은 세탁 거래가 HI-Medium 전체 세탁 거래의 37.67%(935/2,482건)여서, Alert 쪽 개선만으로는 세탁 거래 포함률을 크게 올리기 어려워 팀원과 공유 필요
- 로컬 Docker 메모리(3.66GB) 부족으로 검증 중 분석 입력 고정 단계에서 API 컨테이너가 2회 강제 종료되어(자동 복구 후 완료) 로컬 검증에 계속 제약
- 입력 장부 색인·v10 하루치 갱신·Alert 묶기 규칙 변경이 아직 dev에 반영되지 않아, dev DB 재생성 후 처음부터 다시 실행 필요
