## 실적

- Alert 생성기 근본 설계 검토 착수
  - Alert 생성기 입력인 이진분류 의심 거래에 오탐·미탐이 섞여 있는 상태에서, 오탐은 감수하되 실제 세탁 거래를 놓치지 않고 패턴 단위로 묶는 방법 검토 시작(더 묶는 것은 허용, 덜 묶는 것은 불가, 연결이 긴 패턴 포함)
  - 공개 연구 방법(2단계 임계값, PPR, FlowScope, 2SCENT) 조사 후 입력 오류 측정 → 평가 기준 → 기준 방법·규칙별 제거 비교 → 공개 방법 비교 → 긴 연결 패턴 → 결과 안정성 → 다른 합성 데이터 검증 → 일일 실행 조건 순으로 작업 순서 정리
  - 팀 합의(학습 HI-Large, 시연 HI-Medium)에 따라 Alert 생성기 검토는 HI-Medium 원본 전체를 쓰고, 정답 패턴을 무작위로 절반씩 조정용·평가용으로 분리
  - HI-Medium 원본 변환: 거래 31,898,238건, 28일, 세탁 35,230건, 정답 패턴 2,756개, 패턴 거래 22,743건 전부 원본 거래와 대응 확인
- HI-Medium 원본 전체 이진분류(v10) 점수 계산
  - 운영 방식(거래별 계산)은 약 25시간 예상되어, 실험용으로 그래프 256개 묶음·프로세스 4개로 계산(운영 코드 변경 없음), 거래 3,000건 대조 최대 점수 차이 0.00000009, 임계값을 넘나든 거래 0건
  - 첫날 446만 건 21.8분, 이력이 쌓이면서 거래당 처리 시간 0.29ms → 3.68ms
  - 둘째 날 증분 계산의 계좌쌍 이력 결합이 35분 넘게 끝나지 않아, 결과가 같은 빈 결합으로 바꿔 33.5초로 단축
  - 전체 재계산은 메모리 14.3GB를 넘겨 불가 확인
  - 11/02 23:15 전체 31,898,238건 점수 계산 완료, 누락 0건
- Alert 생성기 입력 오류 측정(임계값 0.434)
  - 의심 거래 203,519건 중 세탁 9.75%, 오탐 183,682건 중 170,456건(92.8%)이 이력이 없는 첫 2일(9/1~9/2)에 집중
  - 9/3~9/16 기준 하루 의심 거래 약 2,000건, 세탁 비율 54.64%, 패턴 거래 재현율 83.86%
  - 정답 패턴 기준 1건 이상 포착 79.57%, 전부 포착 37.48%, 하나도 못 잡은 패턴 20.43%(길이별 2건 59.11%, 3~5건 10.99%, 6~10건 1.35%, 11건 이상 0%)
  - 놓친 패턴 거래 3,382건 중 잡힌 거래와 계좌를 바로 공유 54.46%, 2단계 이상 떨어짐 1.48%, 패턴 전체가 안 잡힘 29.07%, 같은 패턴이나 계좌 연결 없음 14.99%
  - 놓친 패턴 거래와 가장 가까운 잡힌 거래의 시간 차이 중앙값 5.7시간, 90%가 46.7시간 이내
  - 오탐 송금 계좌 상위 15개 합계가 오탐의 0.21%로 특정 계좌 몰림 없음, 정답 패턴 밖 세탁 거래 12,487건은 3.81%만 포착
  - 임계값 0.2로 낮추면 패턴 거래 재현율 85.13% → 91.21%, 의심 거래 1.89배(383,874건)
- Alert 유형 분류를 거래 단위로 되돌림
  - 팀원 거래 단위 유형 분류 모델 연결을 위해, 10/29 Alert 단위 교체 이후 커밋 8개·파일 73개(수정 62, 신규 11)를 확인하고 화면 변경까지 포함해 교체 전 시점으로 되돌림, 기준 시점과 차이 0 확인
  - backend 반영 후 dev 병합
  - KubeSphere dev 추론 서버 파일 5개 교체, Alert 단위 결정트리 제거 후 정상 응답 확인
  - DB 초기 스키마 변경으로 dev DB의 거래 3,510,480건, 분석 작업 11개, Alert 1,488개를 비우고 설정 백업·복원 후 dev 재배포
- dev 은행 설정 정리
  - dev 은행이 32,648곳까지 늘어난 원인 확인: 거래 통합 단계가 상대 은행을 자동 등록하고(계좌가 은행을 참조, 은행 국가가 v10 입력), 데이터셋을 바꿀 때 설정 백업·복원으로 그대로 이어짐
  - 보고 은행만 남긴 설정으로 복원: 은행 20, 보고 기간 20, 계정 4, 환율 15
- 팀원 거래 단위 유형 분류 모델(SALT-GNN R) 연결
  - 팀원이 처음 준 파일은 Alert 단위 입력용이어서 거래 단위 원본 파일을 확인, 모델 구조·가중치 동일(해시 일치), 거래마다 유형 확률 9개 출력
  - 과거 이력이 필요한 모델 확인(받는 쪽 2단계·각 최근 100건, 보내는 쪽 1단계 최근 100건), 이력이 없으면 정밀도/재현율 0.70/0.64 → 0.11/0.12
  - 추론 서버 연결 파일과 등록 줄 작성(백엔드는 모델 이름만 변경), 추론 서버 테스트 70개, worker 테스트 249개(70개 건너뜀), 원본 자체 점검 통과
  - dev 실데이터 측정: 2일 장부 102만 건 중 2만 건 62.8초(건당 3.1ms), 메모리 2.44GB, 마지막 날 16일 장부 548만 건 기준 건당 4.9ms, 52.7만 건 하루 약 43분, 최대 메모리 5.82GB
  - backend 반영, KubeSphere 추론 서버 교체 파일 묶음 준비
- 세탁 유형 화면 표시 이름 검토
  - 8패턴은 IBM 합성 데이터의 그래프 모양 이름으로 국내 공식 번역명이 없어, 화면용 짧은 이름(분산, 집중, 집중-분산, 분산-집중, 이분, 다층, 순환, 무작위) 정리, 화면 반영은 프런트 팀원 담당

## 문제 상황
- 운영 v10 증분 계산에도 같은 계좌쌍 이력 결합이 있어, 하루 수백만 건 규모에서 느려질 수 있음(원인 미조사)
- 이진분류 오탐의 92.8%가 이력이 없는 시작 2일에 몰려, 분석 시작 구간 의심 거래는 대부분 오탐임
- 하나도 못 잡은 정답 패턴 20.43%(주로 거래 2건 패턴)는 Alert 생성기에 묶을 의심 거래가 없어 생성기 개선으로 되살릴 수 없음
- SALT-GNN R 유형 분류가 하루 52.7만 건 기준 약 43분 걸리고, 과거 이력이 없으면 정확도가 크게 떨어짐
