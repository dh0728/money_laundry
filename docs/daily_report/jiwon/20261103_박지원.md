## 실적

- 팀원 거래 단위 유형 분류 모델(SALT-GNN R) dev 적용
  - KubeSphere dev 추론 서버를 SALT-GNN R 연결 파일로 교체한 뒤 backend를 dev에 병합하여 dev 배포
  - dev에서 HI-Medium 은행 20곳 데이터로 전체 기간 분석 진행, 7일차까지 완료
- 세탁 유형 분류 체계 정리
  - 원본 HI-Medium Patterns.txt를 계좌 기준으로 다시 이어 본 결과, 나머지 6개 유형은 3건 이상 패턴 1,447개 중 1,445개가 하나의 그래프로 이어지나 BIPARTITE는 209개 중 0개, STACK은 244개 중 13개만 이어짐을 확인
  - 계좌로 이어지지 않아 어떤 묶음 방식으로도 Alert 하나에 담을 수 없어, 프로젝트 전체에서 BIPARTITE·STACK을 빼고 6개 유형 + NON_PATTERN 7종으로 정리(해당 거래를 정리한 유형 분류 재학습은 모델 팀원 담당)
- Alert 생성기 근본 설계 검토: 평가 기준 확정
  - 채점 대상에서 1건 패턴 364개 제외, 2건 패턴 492개도 같은 모양이 여러 유형으로 나와(A→B→C가 RANDOM 33, STACK 23, GATHER-SCATTER 22개) 제외, 3건 이상 패턴만 사용
  - 서비스 시작 직후 이력이 없는 기간은 분석하지 않고 거래만 쌓는 방식(백필)으로 결정: 분석 후 화면에서만 숨기면 첫 2일 오탐 170,456건이 Alert 구성 60일 범위에 남아 이후 Alert에 섞이는 차이 확인
  - 백필 2·5·7일 비교 후 7일로 결정: 분석 시작 첫날 의심 거래 중 세탁 비율 34.41% → 55.56%, 평가 대상 패턴 302개
  - 설정 조정은 HI-Small(5,078,345건, 패턴 76개), 시험은 HI-Medium 302개 전체로 분리, HI-Small에서 고른 설정 56.95%와 HI-Medium에서 직접 고른 설정 57.62%의 차이가 0.67%p(패턴 2개)로 HI-Small 조정이 충분함을 확인
- Alert 생성기 근본 설계 검토: 현행 기준선과 공개 방법 비교
  - 평가 지표: 정답 패턴 하나가 Alert 하나에 통째로 들어간 비율(HI-Medium 302개, 이진분류 v10 입력)
  - 현재 생성기 56.62%, 정답 라벨 입력 시 74.17%로 이진분류 오류로 잃는 몫 17.55%p
  - 규칙별 제거 실험에서 결과를 바꾼 규칙은 의심 표시 없는 거래를 거쳐 잇는 규칙 하나뿐(제거 시 HI-Medium -9.93%p, HI-Small -10.53%p)
  - 공개 방법(금액 비율 연결, 이중 임계값, 둘의 조합, FlowScope, 순환 찾기) 1차 비교 진행, 순환 찾기(2SCENT)는 변화 없음(HI-Small), 최종 수치는 평가 기간을 바로잡은 재실행 결과로 11/04 정리
  - 안정성 확인(HI-Small): 잡힌 세탁 거래를 10%만 빼도 모든 방법이 크게 하락, 오탐을 4배까지 더하면 통째 포함 비율은 거의 그대로이고 Alert 거래만 증가, 두 경우 모두 방법 간 순위 유지
- Alert 대표유형 결정 방식 검토
  - 현행 구조 확인: 거래 유형은 들어온 날 한 번만 판정해 고정하고, Alert 대표유형은 SEED 거래의 1위 유형 개수로 결정, SALT-GNN R은 대상 거래보다 앞선 거래만 봐서 9/1~9/5 세탁 거래 7,172건을 다시 판정해도 7,172건 모두 같은 결과
  - 패턴 블록 하나를 Alert 하나로 가정한 측정에서 RANDOM 블록 331개 중 50.45%가 CYCLE로 판정(정답 10.88%), CYCLE 블록 367개 중 정답 54.77%
  - 모델과 무관한 한계 측정: 누가 누구에게 보냈는지만으로 거래가 들어온 날 유형이 하나로 정해지는 패턴 거래는 HI-Medium 15,623건 중 17.56%, FAN-OUT·FAN-IN·RANDOM은 패턴이 끝나도 모양만으로는 확정 불가
  - 계산량 측정: 원장 전체를 매일 다시 판정하면 하루 27.6시간, 갱신된 Alert의 SEED만 다시 판정하면 그날 거래의 최대 1.37%
  - 채점 기준 확정: Alert 안에 3건 이상 이어진 패턴 블록이 하나면 그 블록 유형이 정답, 둘 이상이면 복수 정답, 없으면 패턴 미특정
  - 백엔드 후처리 조합(판정 시점 2가지 × 집계 방식 3가지 + 예전 판정 보관)을 가상 판정기(틀림 0/20/40%, 보는 범위 2가지)와 SALT-GNN R 실제 출력으로 비교
  - 1위 개수 세기 → 확률 곱하기: SALT-GNN R 실제 출력 기준 완성 후 정확도 53.77% → 62.08%(+8.30%p, 95% 신뢰구간 +6.51~+10.10), 매일 정확도 45.37% → 53.40%, Alert당 대표유형이 바뀐 횟수 1.221회 → 0.867회
  - 확률 더하기 대비 곱하기 +2.77%p(95% 신뢰구간 +1.25~+4.22), 모든 설정에서 곱하기가 같거나 높음
  - Alert 갱신 때 SEED 유형을 다시 요청·보관하는 방식은 모델 오류가 반복되는 가정에서 -2.06~+1.32%p로 이득이 없어 보류
  - 집계 방식만 확률 곱하기(0 확률은 1e-6으로 대체)로 바꾸기로 결정
- 보고서용 설계·검증 방법 정리
  - 10/12 Alert 생성기 재설계부터 진행 중인 검토까지 18개 항목을 문제, 검증 방법, 결과, 한계 순으로 정리하고, 사용한 검증 기법 17가지(동등성 검증, 규칙별 제거 실험, 장애 주입, 부트스트랩 등)를 표로 정리한 문서 초안 작성

## 문제 상황
- SALT-GNN R이 대상 거래보다 앞선 거래만 보는 구조여서, Alert가 갱신돼도 예전 거래 유형 판정은 바뀌지 않음(모델 팀에서 제약 해제와 재학습이 필요)
- 정상 거래만 든 Alert 버전의 44.75%에 유형이 붙으며, 대표유형 집계 방식으로는 줄지 않음
- 실제 Alert 기준 대표유형 비교는 완성 후 Alert 43개로 표본이 작아 +6.98%p(95% 신뢰구간 하한 0.00)로 확실하지 않음
- 통째 포함 비율이 높은 묶음 방법일수록 Alert 거래가 늘고 비세탁 비율이 오르며, 하루 검토량 한도는 아직 정하지 않음
- Alert 생성기 결과가 이진분류 미탐에 민감하여, 잡힌 세탁 거래가 10%만 줄어도 모든 방법이 크게 떨어짐
- HI-Large 가장 큰 하루(5,379,624건)를 SALT-GNN R로 판정하면 CPU 4개 기준 약 5.3~7.3시간으로 하루 6시간 조건을 넘을 수 있음(추정, 실측 아님)
