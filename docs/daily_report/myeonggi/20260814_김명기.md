## 실적

- 일정이 앞당겨지고 Frontend 작업 밀도가 높아진 상황을 회의에서 확인하고, 다음 주까지 기존 AML 서비스 리서치와 기획 구체화를 진행한 뒤 멘토링·와이어프레임으로 이어가는 작업 순서를 정리
- FigJam에서 빨간 포스트잇은 바로 수정할 항목, 노란 포스트잇은 경고·참고 사항, 초록 포스트잇은 반영 완료 항목으로 구분하고, 외부 서비스 조사 결과에 따라 현재 흐름도 변경될 수 있음을 작업 영역에 표시
- FigJam `Plan`의 `Userflow`를 `Meaning·Color: Permission·Tasks·유즈케이스 대조 / Landing / Onboarding / Working` 구조로 재정리하고, Landing은 최종 산출물 제외 결정, Working은 추가 리서치 후 변경 가능 영역으로 표시
- 오늘 회의에서 Home Dashboard를 역할별 Routing의 진입 화면으로 사용하는 방향을 정하고 Userflow에 반영
- 최종 산출물에서 제외한 Landing 참고 영역에 은행 도입 담당자의 문의와 사이트 운영진의 계약·최초 관리자 계정·임시 비밀번호 발급 흐름을 정리
- Onboarding에 관리자 최초 로그인·비밀번호 재발급·은행 API 연결 검증·기본 정보 동기화·보고책임자와 직원 권한 설정, 직원의 팀별 권한 onboarding 흐름을 정리
- Working에 Login 역할 판별, 역할별 Routing, 모니터링 팀 업무, 분석 팀 업무, 시스템 자동 배정, 관리자 공통 흐름과 관리자의 모든 권한에 추가 권한을 갖는 보고책임자 흐름을 분리
- 모니터링 흐름에 신규·미할당 Alert 확인, 정렬·필터, 기존 담당자 충돌 안내, 자기 할당, 오탐 사유 코드·검토 의견 입력 후 종결, 이관 사유·1차 검토 의견 입력 후 분석팀 이관을 반영
- 분석 흐름에 이관 사건 확인, 담당자 충돌 처리, 관계 그래프와 계좌·거래 상세 확인, 조사 근거 선택, 관련 계좌 연결, 조사 소견 작성·저장, 조사 결과 분류와 종결·추가 항목 보완 loop를 반영
- 시스템 흐름에 미배정·기한 초과 사건 감지, 직원 역량·업무량 기반 자동 배정, 담당자 변경 알림, 계정·권한 변경 시 진행 중 업무 확인과 Audit Log 기록을 정리
- 관리자 공통 흐름과 보고책임자 추가 흐름에 직원 계정·권한 변경, 권한 부족 안내, 변경 사유·최종 확인, 위험도 기준 변경 가능성 검증, 새 version 생성과 적용·Audit Log 기록을 정리
- Chrome에서 FigJam `Userflow` 내부의 신규·기존 모든 section을 각각 실제 읽기 배율로 확대 검수하고, 전날 보고서에서 남겼던 오탐 사유 입력, 자기 할당·이관 순서, 관리자 capability 표기, 분석팀 사건 처리 흐름이 현재 보드에 반영됐음을 확인 — 검수 기록: `Frontend/FigJam Userflow 검수 2026-08-14.md`, screenshot: `Frontend/assets/figjam-audit-20260814/`

## 문제 상황

- Lucinity와 SAS는 팀장이 찾은 초기 사례 2개일 뿐이므로 전체 서비스 조사나 최종 정보 구조로 확정할 수 없음
- 일정이 앞당겨진 상태에서 경쟁 서비스 조사와 기획 구체화를 동시에 진행해야 하며, 현재 FigJam의 내용도 주말 리서치 결과에 따라 변경될 수 있음
- 현재 `Userflow` 안에 자동 배정·계정 변경 검증 같은 system process가 섞여 있어 최종 사용자 흐름에서는 별도 참고도로 분리할 필요가 있음
- 역할별 Permission 영역에 운영자·보고책임자·관리자·직원 등의 틀만 만들고, 각 역할이 실제로 무엇을 조회·처리·변경·승인·요청할 수 있는지 구체적으로 정의하지 못함. 팀원 피드백대로 화면의 틀을 먼저 확정하지 말고 역할별 권한을 충분히 고민한 뒤 구조를 다시 만들어야 함
- 기획·리서치·FigJam 작업에 집중해 JavaScript 강의 수강·실습 진도는 진행하지 못함

## 내일 계획

- Lucinity·SAS 외 GNN 기반 AML 기존 서비스를 추가 조사하고, 서비스별 `Actor / 핵심 과업 / Alert→Case / queue·상세 화면 / graph·거래 근거 / 판단·이관 / Audit / 우리 서비스 적용 여부`를 근거와 함께 비교
- 조사 결과를 직접 이해한 뒤 `채택 / 수정 채택 / 보류 / 제외`로 판정하고, 근거가 확인된 결정만 FigJam의 빨간 포스트잇과 Userflow에 반영
- 운영자·보고책임자·부서별 관리자·직원의 역할별로 `대상 업무 / 조회 / 처리 / 변경 / 승인·요청 / 접근 범위 / 제한·예외`를 비교한 권한표를 먼저 만들고 팀과 합의한 뒤 Permission 구조에 반영
- 추가 리서치 결과를 바탕으로 system process 분리와 Userflow 수정 필요 항목을 정리
- 화요일 회의에서 AI 문안을 읽는 방식이 아니라 각 서비스의 구조와 우리 서비스 적용·비적용 이유를 직접 설명할 수 있도록 비교 결과를 복습
