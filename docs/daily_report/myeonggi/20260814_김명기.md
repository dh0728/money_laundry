- FigJam의 미반영·검토 필요 항목은 빨간 포스트잇, 반영 완료 항목은 초록색으로 관리하고, 외부 서비스 조사 결과에 따라 현재 흐름도 변경될 수 있음을 작업 영역에 표시
- GitHub `doc/resarch-donghyeon` 브랜치 ZIP을 내려받아 압축 해제하고 `docs/01_research`의 Lucinity Case Manager·SAS AML Transaction Monitoring HTML과 연결된 화면 이미지를 확보
- 두 HTML의 이미지 참조 29개와 추가 이미지 2개 등 총 31개 화면을 실제로 확인하고 누락 이미지가 없음을 검증

- 제품 화면에서 직접 확인된 기능과 HTML 작성자의 프로젝트 적용 제안을 분리하고, 우리 서비스에는 Alert·Case 의미 구분, Score·업무 Priority 분리, 담당자 선점·이관, 종결 전 사유·의견 입력, Audit Log, GNN 근거와 거래 연결을 우선 적용하는 방향으로 정리

- Onboarding에 관리자 최초 로그인·비밀번호 재발급·은행 API 연결 검증·기본 정보 동기화·보고책임자와 직원 권한 설정, 직원의 팀별 권한 onboarding 흐름을 정리
- Working에 Login 역할 판별, 역할별 Routing, 모니터링 팀 업무, 분석 팀 업무, 시스템 자동 배정, 관리자 공통 흐름과 관리자 중 법정 지정 1명인 보고책임자의 추가 흐름을 분리

- 분석 흐름에 이관 사건 확인, 담당자 충돌 처리, 관계 그래프와 계좌·거래 상세 확인, 조사 근거 선택, 관련 계좌 연결, 조사 소견 작성·저장, 조사 결과 분류와 종결·추가 항목 보완 loop를 반영

## 문제 상황

- Lucinity와 SAS는 팀장이 찾은 초기 사례 2개일 뿐이므로 전체 서비스 조사나 최종 정보 구조로 확정할 수 없음
- 일정이 앞당겨진 상태에서 경쟁 서비스 조사와 기획 구체화를 동시에 진행해야 하며, 현재 FigJam의 내용도 주말 리서치 결과에 따라 변경될 수 있음
- 현재 `Userflow` 안에 자동 배정·계정 변경 검증 같은 system process가 섞여 있어 최종 사용자 흐름에서는 별도 참고도로 분리할 필요가 있음
- `Tasks` 메모에서는 Home Dashboard가 검토 후보지만 `Routing`에서는 확정 경로처럼 표현돼 있어 팀 결정과 보드 표현이 일치하지 않음
- 보고책임자는 법적으로 관리자 중 1명을 지정하고 일반 관리자보다 추가 권한을 부여하는 역할이므로 관리자 영역 안에 중첩한 구조는 적절함. 다만 `관리자 중 지정 1인`과 `관리자 공통 권한 + 추가 권한`을 명시해 별도 직군이나 단순 상위 직급으로 오해되지 않게 보완할 필요가 있음
- Landing을 최종 산출물에서 제외하기로 표시했지만 Onboarding과 실선으로 연결돼 있어 참고 범위와 최종 범위의 시각적 구분을 보완해야 함
- Alert와 Case의 관계, 상태값, 담당자 동시 선점 처리, 보고책임자의 위험도 기준 변경 범위, GNN 결과의 근거·모델 버전·거래 table 연동은 팀·Backend·모델 담당자와 추가 합의 필요
- 기획·리서치·FigJam 작업에 집중해 JavaScript 강의 수강·실습 진도는 진행하지 못함

## 내일 계획

- Lucinity·SAS 외 GNN 기반 AML 기존 서비스를 추가 조사하고, 서비스별 `Actor / 핵심 과업 / Alert→Case / queue·상세 화면 / graph·거래 근거 / 판단·이관 / Audit / 우리 서비스 적용 여부`를 근거와 함께 비교
- 조사 결과를 `채택 / 수정 채택 / 보류 / 제외`로 판정하고, 근거가 확인된 결정만 FigJam의 빨간 포스트잇과 Userflow에 반영
- Home Dashboard, Landing, 보고책임자의 관리자 공통·추가 권한 표기, system process 분리, Alert·Case 관계와 담당자 선점 규칙의 미결 항목을 목록화해 팀 회의에서 결정할 질문으로 준비
- 화요일 회의에서 AI 문안을 읽는 방식이 아니라 각 서비스의 구조와 우리 서비스 적용·비적용 이유를 직접 설명할 수 있도록 비교 결과를 복습
