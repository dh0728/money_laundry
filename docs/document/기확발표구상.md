## 4. 기획 배경

이런 자금세탁을 보여주는 그림
```
범죄수익
   ↓
여러 계좌로 분산
   ↓
복수 금융기관을 거쳐 이동
   ↓
순환·재집중
   ↓
정상 자금처럼 위장
```

멘트:
>자금세탁의 핵심은 하나의 거래가 아니라 여러 거래가 연결된 전체 흐름에 있습니다. 예를 들어 큰 금액을 한 번에 이동하면 쉽게 의심받을 수 있기 때문에, 자금을 여러 계좌로 나누어 소액으로 이체하고 복수의 금융기관을 거쳐 이동시킨 뒤 다시 특정 계좌로 집중시키는 방식을 사용합니다.  
>이 과정에서 각각의 거래만 보면 일반적인 송금처럼 보일 수 있지만, 계좌와 거래를 서로 연결해서 보면 분산, 순환, 재집중과 같은 의심스러운 패턴이 나타납니다. 따라서 자금세탁을 효과적으로 탐지하려면 거래 한 건의 금액이나 시간뿐만 아니라 계좌와 금융기관 사이에 형성된 전체 거래 관계를 함께 분석해야 합니다.

## 5. 현재 구조의 문제점

시각화:
```
은행 A        은행 B        은행 C
 Alert 1       Alert 2       Alert 3
    └──────── 같은 자금 흐름 ────────┘
              연결되지 않음
```

멘트:
>앞에서 살펴본 것처럼 금융기관들은 각자의 거래 데이터를 기반으로 AML 모니터링 시스템을 운영하고 있습니다. 화면의 예시처럼 하나의 자금이 은행 A에서 은행 B를 거쳐 은행 C로 이동하더라도, 각 금융기관은 자신이 보유한 거래 구간을 중심으로 위험 신호를 생성합니다.  
>그 결과 실제로는 하나로 연결된 자금 흐름이지만 시스템에서는 Alert 1, Alert 2, Alert 3과 같이 서로 다른 조사 대상으로 분리될 수 있습니다. 경우에 따라서는 각 거래가 기관별 탐지 기준보다 낮아 개별적으로 정상거래처럼 보일 가능성도 있습니다.  
>결국 조사 담당자는 분리된 정보를 수작업으로 연결해야 하고, 동일한 자금 흐름을 반복적으로 검토하거나 전체 이동 경로를 파악하지 못하는 문제가 발생합니다.
>저희는 이러한 기관 단위 분석 구조에서 발생하는 한계를 다음 세 가지 핵심 문제로 정리했습니다.

### 6. 한계로 뽑은 핵심 문제
- 금융기관별로 거래정보와 Alert가 분리됨
- 동일한 자금 흐름이 여러 조사 건으로 나뉨
- 개별 거래 점수만으로 탐지 원인을 설명하기 어려움

멘트:
>첫째, 금융기관별로 거래정보와 Alert가 분리되어 있어 기관을 넘어가는 전체 자금 흐름을 한 번에 확인하기 어렵습니다.  
>둘째, 실제로는 동일한 자금 흐름에 포함된 거래가 여러 조사 건으로 나뉘면서 중복 검토와 조사 업무가 증가할 수 있습니다.  
>셋째, 개별 거래의 위험 점수만으로는 해당 거래가 왜 위험한지, 어떤 계좌와 연결되어 있는지, 전체 자금이 어떤 경로로 이동했는지를 설명하기 어렵습니다.  
>따라서 기관별 위험 신호를 통합하고, 관련 거래와 탐지 근거를 하나의 흐름으로 제공할 수 있는 분석 체계가 필요합니다.

## 8. 해결방안
- 분산된 거래를 연결해 조사 가능한 하나의 Episode로 제공

```
금융기관별 거래 CSV
        ↓
표준화·가명처리·통합
        ↓
계좌·기관 거래 그래프 구축
        ↓
이진분류 + 패턴분류
        ↓
탐지 유형별 Alert 생성
        ↓
관련 Alert·거래를 Episode로 통합
        ↓
L1 1차 검토 → L2 심층분석
```

멘트:
>앞에서 말씀드린 문제를 해결하기 위해 저희는 금융기관별로 분산된 거래를 통합하여 하나의 작므 흐름으로 분석하는 서비스를 구상했습니다. 
>먼저 각 금융기관에서 CSV 형태로 제공받은 거래 데이터를 공통된 형식으로 표준화하고, 계좌 식별자를 가명처리한 후 하나의 데이터 구조로 통합합낟. 이후 계좌를 노드로, 거래를 연결선으로 표현한 거래 그래프를 생성합니다.
>생성된 그래프에는 이진분류 모델과 패턴분류 모델을 병렬로 적용하여 위험점수와 탐지 유형을 기준으로 관련된 거래를 Alert로 구성하고 동일한 자금 흐름에 포함된 Alert들을 하나의 Episode로 연결합니다.
>여기서 Alert는 특정 탐지 유형에 해당하는 관련 거래를 묶은 위험 알림이고, Episode는 여러 Alert와 거래를 종합한 최종 조사 단위입니다.
>생성된 Episode는 L1 담당자가 먼저 검토하고, 추가 분석이 필요한 경우 동일한 Episode를 L2 담당자에게 전달하여 심층분석을 진행합니다. 이를 통해 담당자는 기관별 Alert를 따로 확인하는 대신 전체 자금 흐름과 탐지 근거를 하나의 화면에서 확인할 수 있습니다.  
>이러한 거래 관계와 자금 흐름을 분석하기 위해 저희가 활용하는 핵심 기술이 GNN입니다.

## 9. GNN 설명

- GNN을 이해하기 쉽도록 하는 시각화

멘트:
>일반적인 모델이 거래 한 건의 금액과 시간 등을 분석한다면, GNN은 계좌를 점으로, 거래를 연결선으로 표현하여 주변 계좌와 자금 이동 관계를 함께 학습합니다.
>이를 통해 특정 계좌가 어떤 계좌들과 연결되어 있는지, 자금이 여러 계좌로 분산되었는지, 순환한 뒤 다시 집중되었는지와 같은 관계 구조를 함께 학습할 수 있습니다.
>따라서 각각은 정상적으로 보이는 거래라도 여러 거래를 연결했을 때 나타나는 자금세탁 패턴을 탐지하는 데 활용할 수 있습니다.

>실제로 IBM의 NeurIPS 2023 연구에서도 합성 금융거래를 그래프로 구성하고 GNN의 자금세탁 탐지 성능을 평가했습니다.
>하지만 담당자에게 단순히 위험하다는 점수만 제공해서는 충분하지 않습니다. 위험 여부와 함께 어떤 유형의 거래인지도 설명할 필요가 있기 때문에 저희는 두 개의 모델을 병렬로 구성했습니다.

## 10. 이진분류·다중분류 병렬모델 

```
통합 거래 그래프
      ├─ 이진분류 모델 → 자금세탁 위험 여부
      └─ 다중분류 모델 → 정상 / 5개 이상의 패턴 / 무패턴 자금세탁
                              다중 클래스
```
멘트:
>저희가 두 개의 모델을 사용하는 이유는 자금세탁 인지 아닌지를 탐지하는 것과 구체적인 거래 유형을 설명하는 것이 서로 다른 목적을 가지기 때문입니다.
>먼저 이진분류 모델은 해당 거래가 정상거래인지 자금세탁 위험 거래인지를 구분하고 위험점수를 산출합니다. 다중분류 모델은 정상거래와 자금세탁 패턴, 그리고 기존 패턴에 매칭되지 않는 자금세탁 거래를 구분하여 담당자에게 구체적인 탐지 유형을 제공합니다.
>두 모델을 직렬이 아닌 병렬로 적용하기 때문에 이진분류 모델이 거래를 놓치더라도 다중분류 모델의 결과를 별도의 위험 신호로 확인할 수 있습니다. 반대로 두 모델의 결과가 일치하지 않는 거래는 담당자가 우선적으로 확인해야 하는 검토 대상인지 표시할 수 있습니다. 

>AML 분야의 DELATOR 연구에서도 목적이 다른 판단을 두 개의 보완적 분류기로 분리하고 단일 분류기와 비교한 사례가 있습니다. 다만 해당 연구가 저희와 동일한 분류 구조를 사용한 것은 아니기 때문에, 저희 역시 병렬 구조가 더 우수하다고 미리 단정하지 않고 단일 다중분류 모델과의 비교 실험을 통해 효과를 검증하겠습니다.
>이러한 모델을 학습하고 검증하기 위해 저희가 선택한 데이터가 IBM AML 합성 거래 데이터입니다.

| `accounts.csv` | 계좌 1개 | 은행·계좌·Entity 식별정보 | 계좌 노드 생성 |
| `Trans.csv` | 거래 1건 | 송수신 계좌, 시간, 금액, 통화, 방식, 이진 라벨 | 거래 엣지 및 이진분류 |
| `Patterns.txt` | 패턴에 참여한 거래 | 패턴명, 시도 단위, 관련 거래 | 패턴분류 라벨 및 평가 |

어떻게 넣을지는 고민좀 해봐야 할듯

작게 표시: 실제 개인정보 및 고객확인(KYC) 정보가 포함되지 않은 합성 데이터

멘트:
>데이터 한세트는 크게 세가지 파일로 구성됩니다. 
>accounts.csv에는 계좌와 소유 주체에 관한 정보가 있고, Trans.csv에는 누가 누구에게 언제, 얼마를, 어떤 방식으로 보냈는지가 거래 한 건씩 기록돼 있습니다. Is Laundering 컬럼은 해당 거래가 정상인지 자금세탁인지 나타내는 이진 라벨입니다.
>Patterns.txt에는 일부 자금세탁 거래가 어떤 패턴과 시도에 속하는지가 기록되어 있습니다. 저희는 계좌 파일과 거래 파일을 은행 ID와 계좌번호로 연결하고, 패턴 파일을 추가로 매칭하여 학습용 데이터를 구축합니다.

## 12 그래프 변환 과정

```
은행 A·계좌 123                              은행 B·계좌 456
       ● ───────────────────────────────────────▶ ●
              2,848.96 EUR · ACH · 09:32
                     Is Laundering = 1
```

- 노드: 은행과 계좌로 식별한 송금·수취 계좌
- 엣지: 계좌 사이에서 발생한 방향성 거래
- 엣지 속성: 시각, 금액, 통화, 결제방식
- 이진 라벨: 정상거래 / 자금세탁 거래
- 다중 라벨: 정상 / 패턴 / 무패턴 자금세탁

멘트:
>실제 모델에서는 CSV의 거래 한 행을 그래프의 연결선 하나로 변환합니다. 송금 계좌와 수취 계좌는 노드가 되고, 두 계좌 사이의 거래는 방향을 가진 엣지가 됩니다. 거래 시각과 금액, 통화, 결제방식은 엣지의 속성으로 사용합니다.
>이렇게 구성하면 모델이 거래 한 건의 속성뿐 아니라, 해당 계좌가 주변 계좌와 어떤 관계를 맺고 자금이 어떤 경로로 이동했는지도 함께 학습할 수 있습니다.

## 16. 목표 및 성과지표
모델 성능뿐 아니라 조사 효율과 시스템 품질까지 검증합니다
4개의 영역을 카드 형태로 배치하면 좋습니다.

```
┌──────────────────┐  ┌──────────────────┐
│ ① AI 탐지 성능    │  │ ② 조사 효율       │
│                  │  │                  │
│ Recall@1% ≥ 60%  │  │ Alert 감소율 ≥ 30%│
│ Macro-F1 ≥ 0.70  │  │ 상위 위험 우선제공 │
└──────────────────┘  └──────────────────┘

┌──────────────────┐  ┌──────────────────┐
│ ③ Episode 품질    │  │ ④ 시스템 완성도    │
│                  │  │                  │
│ 연관거래 포함 ≥80%│  │ 508만 건 처리 검증 │
│ 비관련 혼입 ≤20%  │  │ 핵심 화면 6종 이상 │
└──────────────────┘  └──────────────────┘
```

| 평가 영역 | 지표 | 목표 |
|---|---|---:|
| 이진분류 | Recall@상위 1% | 60% 이상 |
| 다중분류 | Macro F1-score | 0.70 이상 |
| 비교 실험 | XGBoost·Random Forest·GNN | 동일 데이터로 3종 비교 |
| 조사 효율 | Alert 감소율 | 30% 이상 |
| Episode 품질 | 연관 거래 포함률 | 80% 이상 |
| Episode 품질 | 비관련 거래 혼입률 | 20% 이하 |
| 데이터 품질 | 처리 정합성 | 99.9% 이상 |
| 기능 완성도 | 핵심 화면 | 6종 이상 |

Recall@1%는 전체 거래 중 위험도가 높은 상위 1%만 조사했을 때 실제 자금세탁 거래를 얼마나 찾아내는지 나타냅니다.
Alert 감소율은 다음과 같이 계산할 수 있습니다.
1 - (생성된 Episode 수 ÷ 기존 Alert 수)

수치는 현재 단계에서는 목표 초안으로 제시하고, 첫 번째 기준 모델 결과가 나온 후 확정하는 것이 안전합니다.

멘트: (수정예정)
>성과는 단순히 모델 정확도만으로 평가하지 않겠습니다. 자금세탁 데이터는 정상거래가 압도적으로 많기 때문에 Accuracy보다는 PR-AUC, Recall, F1-score와 같은 불균형 데이터에 적합한 지표를 사용합니다.
>특히 전체 거래 중 위험도가 높은 상위 1%를 검토했을 때 실제 자금세탁 거래를 얼마나 포함하는지를 Recall@1%로 평가합니다. 또한 관련 Alert를 Episode로 묶었을 때 조사 대상이 얼마나 감소하는지, 실제 연관 거래를 얼마나 포함하는지도 함께 측정합니다. 마지막으로 약 508만 건의 HI-Small 데이터를 안정적으로 처리하고 핵심 화면 6종 이상을 구현하는 것을 시스템 목표로 설정했습니다.
