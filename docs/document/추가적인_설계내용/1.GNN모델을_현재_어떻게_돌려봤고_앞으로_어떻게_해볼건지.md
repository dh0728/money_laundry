
**공통으로 지금 쓰고 있는 구조**
이진·유형분류 둘 다 같은 그래프 파이프라인 위에서 돈다. 계좌가 노드, 거래가 엣지고, 하루 단위로 그래프를 만든다. 문맥은 판정일 기준 최근 30일 거래인데 전부 쓰는 게 아니라 수취 계좌당 최근 10건만 남기고, 판정할 거래 양끝 계좌에서 들어오는 방향으로 2홉까지만 본다. 모델은 TransformerConv 2층에 송신 계좌 표현 + 수신 계좌 표현 + 거래 피처를 붙여서 분류하는 가장 기본적인 MPNN이다.

**이진분류**
- 지금까지: 위 구조로 TGNN·GAT·GATv2·GINE·EdgeSAGE·EdgeGCN 6종을 원본/랜덤/클러스터 언더샘플링 3방식 × 3시드로 돌렸다. 검증셋에서 에폭과 임계값을 골랐고 테스트는 아직 안 봤다.
- 문제: 6종 다 표준 MPNN이라 아래 논문 장치가 하나도 없다. 그리고 이웃을 10건까지만 보는 게 fan-in 신호를 자르고 있다(논문은 100건).
- 앞으로: 아래 장치를 순서대로 하나씩 넣어보고 검증 AP가 움직이는지 확인한다.

**유형분류(9클래스)**
- 지금까지: 같은 구조로 출력만 9개로 바꿔 돌렸다. 세탁 행만 놓고 8종 고르기(§2)에서는 GNN이 트리보다 나았는데, 정상까지 섞인 전체 거래에서는 macro-AP 0.17 vs 트리 0.27로 밀렸다.
- 문제: epoch 1이 최고고 이후 계속 떨어졌다. 배치를 시간순 그대로 잘라서 학습이 불안정한 게 원인으로 보인다. FAN-IN은 26,576건 찍고 FAN-OUT은 252건밖에 안 찍었고, BIPARTITE·STACK은 거의 예측을 안 했다. GNN이 앞선 것도 평가 행의 65%가 학습 때 본 attempt라서, 처음 보는 attempt만 보면 트리랑 같다(28.6% vs 28.1%).
- 앞으로: 배치 셔플(시드 고정)부터 고치고, 그다음 아래 장치를 넣는다. 라벨도 팀 결정(패턴 밖 세탁 → 클래스 0)에 맞춘다.

#### 1. 이웃 샘플링 방식
논문은 60/20/20 시간순 분할에서 val 그래프에 train 거래까지 다 넣고, test 그래프에는 전체를 넣는다. 대신 손실과 지표는 해당 구간 거래에만 계산한다. 과거 거래는 이웃 맥락으로만 쓰고 역전파에는 안 쓰는 것. 이웃은 1홉 100개, 2홉 100개로 랜덤 샘플링한다.

현재 원리는 같다. val 날짜를 채점할 때 이전 30일(train 기간 포함) 거래가 이웃으로 들어가고 손실은 그날 거래에만 걸린다. 다른 점은 문맥을 최근 30일로 자르고, 수취 계좌당 최근 10건만 남기고, **들어오는 방향만 따라간다는 것.** 30일은 패턴 기간(중앙값 27일)을 생각하면 짧지 않은데, 10건 상한은 fan-in을 못 세게 만든다. 64~100으로 무조건 올려야함

**들어오는 방향만 따라 간다는게 무슨뜻이냐?**

예를 들어 이런 그래프에서 A→B를 판정한다고 하면
```
X → A        (A로 들어옴)        ← 1홉에 포함
Y → X        (X로 들어옴)        ← 2홉에 포함
A → C, A → D (A가 보냄)          ← 안 봄
B → E        (B가 보냄)          ← 안 봄
```

나중에 설명할 ReverseMP도 그렇고 둘다 고쳐야함

#### 2. Reverse MP, Ego ID, Port numbering
지금은 셋 다 안 쓰고 있고, 안 써서 생기는 증상이 유형분류 결과에 그대로 보인다.

- **Reverse MP(역방향 채널)**: 지금은 메시지가 src→dst 한쪽으로만 흘러서 받는 계좌는 누구한테 받았는지 알지만 보내는 계좌는 자기가 누구한테 보냈는지 모른다. 그래서 fan-out을 src 자리에서 못 본다. FAN-IN 26,576건 vs FAN-OUT 252건이 이 증상이다. 엣지를 그냥 양방향으로 만들면 방향을 잃어서 fan-in/out이 같아 보이니까, 뒤집은 엣지를 별도 가중치로 따로 돌려야 한다.

- **Ego ID**: 노드에 이름표가 없어서 "한 바퀴 돌아 나한테 온 메시지"와 "비슷하게 생긴 남한테서 온 메시지"를 구분 못 한다(WL 한계 — 표준 GNN은 WL 테스트가 구분 못 하는 구조를 구분 못 하고, 대표적으로 사이클을 못 센다). 판정할 거래 양끝 계좌에 flag 1차원만 붙이면 된다. CYCLE 재현율 0.23이 이 증상이다.

- **Port numbering**: 같은 두 계좌 사이 거래 여러 건이 aggregate에서 한 덩어리로 합쳐져서 "상대가 몇 명인가"를 못 센다. 수취 계좌별로 송신자를 첫 거래 시각순으로 번호 매겨 엣지 피처에 넣는다. 지금은 pair_prior_count 피처가 일부 대신하고 있다.

적용 순서는 Reverse MP → Ego ID → Port numbering. 논문에서도 효과가 큰 순서고, 각각 넣을 때마다 FAN-IN/OUT 균형과 CYCLE 재현율이 바뀌는지로 확인할 수 있다.

#### 3. Edge update(EU), 3-hop

**Edge update(EU)**: 층마다 엣지 피처도 갱신하는 것. 논문에서 Multi-GIN+EU가 최상위 조합 중 하나이고, edge_attr = edge_attr + MLP([h_src, h_dst, edge_attr]) 한 줄임.
**3층**: 논문도 "2층이라 긴 사이클은 못 잡는다"고 적어놨음. Ego ID 넣은 뒤에 3층으로 늘리면 CYCLE·STACK에 효과가 있을 수 있다. 대신 서브그래프가 커져서 이웃 상한과 같이 조정해야 함
