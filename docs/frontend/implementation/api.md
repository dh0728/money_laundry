# 화면에 필요한 API와 미확정 사항

대상: 지원님·백엔드·프론트엔드 팀원 · 언어: 한국어 · 구분: API 데이터 요구사항 정본

문서 수정: 2026-11-20. 화면 검수용 초안이며, 운영 연동 상태와 백엔드 합의 상태는 아래에 따로 기록한다.

기존 [API.md](../../../backend/api-server/API.md)는 현재 백엔드 동작을 확인하는 참고 자료다. 새 화면을 기존 API에 맞춰 바꾸는 기준은 아니다. 2026-11-15에 정한 순서는 **가짜 데이터로 화면 구현 → 필요한 데이터와 동작 기록 → 백엔드와 API 합의**다. 유형 등 도메인 값은 [codes.ts](../../../frontend/web-app/src/api/codes.ts)를 따른다. 함께 볼 문서: [데이터 표시 규칙](frontend-handoff.md#display-id), [화면 목록](frontend-handoff.md#screen-inventory).

<a id="per-screen-data-handoff"></a>
## 화면별 데이터 전달

화면을 구현할 때마다 이 문서의 해당 화면에 다음 내용을 기록한다. 화면 경로·구성·구현 검수는 [프론트엔드 기준](frontend-handoff.md#screen-inventory)을 따른다.

- 화면에 나오는 필드·지표의 의미, 단위, 가짜 데이터 출처, 집계식과 필터 조건.
- 필요한 식별자와 `codes.ts` 값. 화면에 표시하는 이름과 저장하는 값을 구분한다.
- 사용자 동작, 필수 입력, 기대 결과, 권한, 실패 상태.
- 로딩, 빈 결과, 값 없음, 데이터가 오래된 상태(stale), 오류 발생 시 동작.
- 참고할 기존 API가 있다면 그 근거. 각 항목은 `가짜 데이터만 구현`, `기존 동작 확인`, `제안`, `백엔드 합의 완료` 중 어디에 해당하는지 표시한다.

경로, 응답 필드, 권한이나 합의 내용을 임의로 만들지 않는다. 가짜 데이터로 화면이 동작해도 API 연동을 마쳤다는 뜻은 아니다.

아래 화면별 요구사항은 [첫 묶음](history/first-bundle.md#data-required-from-backend)과 [전체 샘플 앱](history/complete-bundle.md)에서 통합했다. 두 자료의 과거 구현·검증 결과를 현재 완료 상태로 옮기지는 않았다. **표의 서버 데이터는 요청 사항이며, 백엔드 합의 완료를 뜻하지 않는다.**

확인되지 않은 항목은 미확정(`unconfirmed`)으로 남긴다. 추측을 사실처럼 적지 않는다.

<a id="existing-integration-safeguards"></a>
## 기존 API 연동 시 지킬 규칙

기존 엔드포인트를 사용할 때도 아래 규칙을 유지한다. 새 화면에 연결하기 전 실제 엔드포인트를 다시 확인한다. 이 규칙만으로 아래 미확정 사항이 해결된 것은 아니다.

- 표시 ID(`A-1042`)의 숫자를 `caseId`로 보내지 않는다. 정확한 `alertId`로 조회한 뒤 해당 행의 `caseId`를 사용한다.
- `revision`은 GET 응답 값을 그대로 돌려보낸다. 프론트엔드에서 합치거나 새 값을 만들지 않는다.
- 시각은 오프셋이 포함된 ISO-8601로 받고 KST로 표시한다. 날짜 필터는 시작일 00:00을 포함하고, 종료일 다음 날 00:00은 제외한다.
- USD 합계가 없으면 원래 통화의 합계로 대신 채우지 않는다. 점수 범위는 0~1이다.
- '자금세탁 규모'나 '세탁된 거래'로 단정하지 않는다. '의심 거래'로 표기하고 패턴에는 확률을 함께 표시한다.
- 모델 결과와 사람의 판정은 별개다.

### 2026-11-17 기존 서버·어댑터 대조

현재 checkout의 `AuthController`·`StaffAccounts`·`ReviewController`와 API.md §5·§6.5·§9를 대조한 결과. 배포 서버에 접속한 결과가 아니며, 새 `src/next` 화면은 계속 샘플 상태.

| 영역 | 확인한 기존 계약 | 새 화면 연결 전 남은 차이 |
| --- | --- | --- |
| 사용자 세션 | `GET /api/me`, CSRF 조회, 양식 로그인, 세션 로그아웃. 사용자 응답은 `id, username, name, role`; 역할은 `STAFF/ADMIN` | 기존 `src/api/auth.ts`에 로그인·복원 응답 검사 추가. 잘못된 200 응답은 `INVALID_SESSION_RESPONSE`로 거절. 새 화면의 샘플 로그인에는 연결하지 않음 |
| 대시보드 | `GET /api/v1/dashboard?from=...&to=...`. 개인 집계 주체는 세션 사용자, 기준 시각은 `businessAt` | 서버의 현재 OPEN·72시간 집계와 새 화면의 기간·상태별 보드는 의미가 다름. 필드 이름만 바꾸거나 샘플 KPI에 끼워 넣지 않음 |
| 조사 목록·상세 | `GET /api/v1/review/cases`, `GET /api/v1/review/cases/{caseId}` | 원본 Alert ID와 caseId, 표시 ID, 업무 상태·판정 단위 대응 확인 필요. 새 화면의 전체 원장 메모리 계산을 서버 페이지 합계로 대체하려면 집계 계약 필요 |
| 원장 | `GET /api/v1/ledger/owners`, `/accounts`, `/transactions`. 계좌·소유주 ID는 문자열 | 새 샘플의 숫자 계좌 ID와 직접 호환되지 않음. UUID를 숫자로 바꾸거나 표시 문자열에서 잘라내지 않음 |
| Alert 동결 근거 그래프 | API.md §3.2의 `GET /api/v1/alerts/{alertId}/graph?version=...`는 거래별 edge와 원본 거래·버전을 보존 | 옛 `/api/alerts/.../graph`의 묶음 edge 자료형과 다름. 미채점 scores null을 0으로 바꾸거나 반복 거래를 원본 없이 합치지 않음 |

로컬 API 서버의 기본 포트 8080에서 리스너를 찾지 못함. 이번 인증 검사는 fetch를 합성 응답으로 대체한 자동 테스트이며, 실제 세션·서버 저장·배포 확인을 대신하지 않음. 운영 서버 연결이나 데이터 변경 요청 없음.

### 2026-11-18 별도 셸 시험 화면

`frontend/web-app/src/app/radar`의 검색과 보관함은 브라우저에서 생성한 테스트 데이터로 동작한다. 검색은 거래·Alert·Episode의 전체 시험 코드를 검색어로 필터링한다. 알림 필터와 모두 읽음은 메모리에서 처리하며 새로고침하면 초기화된다. 계정 메뉴는 설정·권한·로그아웃 항목의 배치만 검토 중이다. 운영 연결에는 검색 범위와 페이지네이션, 알림 읽음 상태 저장, 계정·권한 계약 확인이 필요하다.

### 5215 대시보드의 모의 응답과 연결 기준

프리뷰의 일별 Alert 차트는 한 시간축에 생성일별 현재 상태를 누적 영역으로, 실제 종결일별 건수를 별도 선으로 표시한다. 생성 건수는 상태의 합으로 읽고, 종결일별 건수는 그 합계에 더하지 않는다.

현재 집계에 쓰는 상태·위험도·패턴·경과·담당 필터는 모의 규칙이다. 거래에서 담당이나 상태를 직접 읽을 수 없으므로 개인 범위와 업무를 좁힌 경우에는 선택 업무의 근거 거래만 중복 없이 센다. 이 필터를 운영 집계와 보드 양쪽에 전달할 필드·값과 동일 스냅샷 보장 방식은 백엔드 합의 대상이다.

검수 화면은 요약, 차트, 업무 보드에 별도 로딩 상태를 둔다. 업무 카드에는 상태별 8건을 먼저 그린 뒤 더 보기에서 추가한다. IBM 대시보드는 저장소의 원본 집계 응답만 요청하고, 거래 원장을 열 때 상세 거래 파일을 요청한다. IBM 기간은 2022-09-01~18 원본 시각 기준이며 5,078,345건 중 원본 세탁 라벨 5,177건이다.

유형 차트의 지원 태그는 우선 `FAN-OUT`, `FAN-IN`, `GA-SC`, `SC-GA`, `CYCLE`, `BIPARTITE`로 표시한다. 그 밖의 원본 분류 건수는 집계에 보존하고 빗금으로 구분한다. 모델 팀의 확정 코드 목록과 용어를 연결할 때 다시 대조한다.

## 샘플 구현과 API 계약의 구분

2026-11-15 인계 기록의 `src/next`는 메모리에 있는 가짜 데이터를 여러 화면에서 공유하는 앱이다. 실제 인증·API 요청·AI 모델 실행·서버 저장·운영 룰 배포를 연결했다는 뜻이 아니다. 기존 `src/app`의 실제 API 시연 코드와 구분한다.

당시 데이터 출처는 다음과 같다. 샘플 개수는 서버의 운영 규모·성능·현재 제품 상태를 뜻하지 않는다.

- `src/next/dashboard-data.ts`: 2026-11-09~15 합성 거래·업무, 기준일, 가린 이름, 점수·확률. Figma 예시 숫자는 데이터로 사용하지 않는다.
- `src/next/workspace-data.ts`: 거래 126건, 업무 24건, 룰 3개, 초기 판정 6건, 알림 3건. 계좌 47개와 소유주 19명은 샘플에서 도출한다.
- `workspace-store.ts`: `LedgerTransaction`, `WorkspaceCase`, `RuleRecord`, `JudgmentRecord`, `WorkspaceNotification`은 프론트 내부 자료형이며 확정된 백엔드 DTO가 아니다.
- 당시 샘플은 페이지를 옮기면 상태가 유지되고 새로고침·로그아웃 시 초기화됐다. 테마·브랜드·글자 크기만 브라우저 설정에 저장했다. 서버 저장 정책은 별도 합의 대상이다.
- AI 요약·보고서 문구는 합성 데이터 설명 예시다. 실제 AI 호출·정확도·자금세탁 사실을 입증하지 않는다.

### 식별자·유형·집계 의미

표시 ID는 `{A|E}-YYMMDD-NNNNNN`이며 서버 숫자 ID와 별개다. 업무의 `caseId`·`sourceId`를 표시 문자열에서 잘라내지 않는다. 모델 `score`·`probability`는 0~1, 금액 합계는 USD 또는 값 없음, 날짜 표시는 KST다. 분모가 0이면 비율을 0%로 꾸미지 않고 값 없음으로 표시한다.

패턴 코드는 `codes.ts`의 0~8을 따른다. 0 `NON_PATTERN`은 사람의 정상 판정과 다르며 패턴 요약 차트에서는 제외하되 그래프·거래 근거에서 삭제하지 않는다. 코드 3은 `GATHER-SCATTER`, 코드 4는 `SCATTER-GATHER`다. 전체 대응은 [패턴 코드](frontend-handoff.md#pattern-codes)를 따른다.

샘플의 사람 판정 `normal` / `abnormal`과 백엔드 enum은 구분한다. 화면에 `FALSE_POSITIVE` 선택지를 추가하거나 `SUSPICIOUS`를 합의된 API 값으로 제출하지 않는다. 업무 상태·판정 매핑은 [도메인 대응](frontend-handoff.md#domain-reconciliation)과 위 미확정 사항을 함께 확인한다. 위험 구간의 `medium=0.7`, `high=0.9`는 샘플 룰 설정이지 운영 고정값이 아니다. 운영값의 출처·버전·적용 기간이 필요하다.

## 룰 버전 비교·템플릿의 추가 요구사항

현재 샘플은 룰 저장·상태 변경 전의 실제 조건을 보존하고, 같은 현재 거래·기간에 두 조건을 실행해 비교 가능. 최초 샘플의 과거 조건과 운영 이력은 없음. 새로고침 시 새로 쌓인 조건 기록도 초기화되는 메모리 구현이며 서버 저장·연동 완료를 뜻하지 않음.

| 항목 | 화면에 필요한 값·동작 | 미확정 사항 |
| --- | --- | --- |
| 보존된 이전 조건 | 이름·설명·유형·최소 점수·최소 거래 수·시간 창, 버전·상태·작성자·시각. 실제 존재하는 조건만 선택 | 이전 버전 조회·고정 조건 식별자·보존 정책. 현재 샘플은 조건 저장과 상태 변경 모두 버전 증가 |
| 비교 실행 | 현재·기준 조건, 동일한 거래 스냅샷과 기간. 양쪽 실행 성공 후 결과를 함께 교체. 실패 시 직전 양쪽 결과 유지 | 서버 작업·데이터 스냅샷 고정·취소·결과 페이지 계약 |
| 계좌 비교 수치 | 전체 적중 송금 계좌 ID 집합 기준. 새로 걸림=현재−기준, 빠짐=기준−현재. 화면의 거래 페이지25/100행과 독립 | 수취 계좌 등 다른 평가 단위와의 구분. 현재 샘플의 `accountId`는 송금 계좌 기준 |
| 사람 판정 기준 정확도 | 계좌 단위 판정 기준이 없어 현재 `미제공` 표시 | 기준 라벨·평가 포함 범위·정확도 정의. 거래 판정을 계좌 정답으로 임의 합성 금지 |
| 원본9종 템플릿 | 단건 고액·분할 입출금·FAN-IN/OUT·급속 통과·휴면·평소 대비 급증·순환·반복 상대방의 조건 구조 | 금액·서로 다른 상대 계좌 수·방향·기간·AND/OR·신규/해외 속성·기본값·검증 범위 계약 필요 |

`codes.ts`의0~8은 모델 분류 값이며 템플릿 ID가 아님. 현재 샘플 백테스트는 이미 분류된 유형·점수와 송금 계좌별 거래 수·시간 창을 평가. FAN-IN의 서로 다른 송금 계좌 수나 금액 조건을 모델 점수·일반 거래 건수로 바꾸면 의미가 달라지므로 자동 치환하지 않음. 과거 운영 당시 결과 재현·원본 템플릿 엔진·정확도63% 구현으로 표시하지 않음.

<a id="interaction-contract"></a>
## 조회·변경 요청과 상태 처리

아래는 기존 샘플 동작에서 추출한 연동 요구사항이다. 실제 서버의 검증·원자성·권한을 시험한 결과가 아니다. 입력값·권한·상태 전이·저장 방식이 바뀌면 프론트와 백엔드가 먼저 합의한다.

- **조회:** 로딩·빈 결과·재조회 오류를 구분한다. 룰 목록, 원장, 업무 목록, 보고서는 재조회 실패 시 직전 성공 결과를 유지하며, 직전 결과가 0건이어도 유지한다. 상세도 이전 업무 내용과 오류 안내·재시도를 함께 제공한다. 필터는 적용 후 URL과 조회에 반영하고 잘못된 날짜와 종료일이 시작일보다 앞선 경우를 검증한다.
- **생성·수정:** 기존 생성·설정·계정 화면은 로컬 입력·조회여서 네트워크 상태가 없었다. 실제 연결 시 요청 중(pending), 입력 검증, 권한 없음, 실패 응답을 붙여야 한다. 화면 코드의 지연 로딩은 서버 요청 로딩의 증거가 아니다.
- **판정:** 기존 샘플은 단일 또는 최대 100건의 복수 판정에 사유와 최종 확인을 요구한다. 다른 담당자·종결 항목·revision 충돌이 섞이면 전체 실패로 처리하고 일부 상태·기록만 저장하지 않는다. 실패·충돌 시 입력은 보존한다. 거래 판정은 연결 업무 전체의 담당·종결 여부를 검사한다. 실제 DB 트랜잭션·재시도 중복 방지는 서버에서 합의·검증해야 한다.
- **Alert 묶기:** 샘플 허용 범위는 2~100건이며 내 담당·미종결·미묶음 업무만 선택한다. 거래 ID를 중복 제거해 Episode를 만들고 원래 Alert의 처리 상태·사람 판정은 유지한다. 서버의 권한·revision·원자적 생성은 미확정이다.
- **룰 상태:** 초안→승인 대기→테스트→운영/반려/중지 등의 샘플 전이는 사유와 함께 기록한다. 실제 승인자 역할·허용 전이·운영 배포 정책은 미확정이며 모의 전이를 운영 승인으로 보지 않는다.
- **백테스트:** 실행 전·실행 중·0건·성공·재실행 오류를 구분하고 실패 시 이전 결과를 유지한다. 작업 ID, 고정된 룰 버전, 진행률·취소·재시도·결과 페이지가 필요하다.
- **상세·열린 업무:** 개요 all/per, 패턴·소유주 그래프, 근거 표·거래 상세·관련 계좌·연관 업무·검토 의견이 샘플 범위다. 열린 업무는 6개씩 페이지로 표시하며 전체 탭 수 제한은 없다. 이는 서버 페이지 크기나 접근 권한의 정의가 아니다.
- **보고서 선택:** 링크의 selected ID가 있는 페이지로 이동하되 명시한 page가 우선한다. 다른 화면으로 옮긴 뒤 숨겨진 선택 항목을 내보내지 않는다. 판정 당시 근거를 고정해 이후 데이터 수정이 과거 보고서를 바꾸지 않도록 한다.
- **PDF·CSV:** 샘플 PDF는 기존 판정을 하나의 한국어 A4 이미지 기반(raster) PDF로 내보냈다. 텍스트 검색·복사·벡터 인쇄는 지원하지 않으며 상한은 25판정·100쪽·32MiB 이미지다. 운영용·장기 보관 보고서는 서버 생성 요구를 합의해야 한다. CSV는 BOM·CRLF·따옴표 이스케이프와 공백·탭·개행 뒤 수식 시작 문자 방어를 유지한다.

## 관계 그래프의 데이터 요구사항

기존 그래프는 `workspace-data.ts`·`dashboard-data.ts`의 합성 데이터와 `case-selectors.ts`의 범위 내 파생값을 사용했다. 예시 캡처의 3거래·6노드·3연결은 실제 운영 데이터가 아니다. 금액은 `amountUsd` 합이며, 사람의 이상 판정을 먼저 표시하고 나머지는 모델 score 구간을 따른다. 모델 확률·점수·사람 판정을 섞지 않는다.

| 분석 화면 | 근거·집계 출처 | 필요한 서버 데이터 |
| --- | --- | --- |
| Alert 계좌·패턴별 (`alert-account`) | Alert transactionIds의 from/to 계좌, 거래 수·USD 합, score·humanVerdict·typeCode·probability. 연결을 선택하면 그 transactionIds만 표시 | 제한된 계좌 이웃, 방향, 근거 거래 cursor, 누락 개수 |
| Alert 소유주별 (`alert-owner`) | 같은 근거에 accountId → ownerId 매핑을 적용한 소유주 집계·계좌 수. 소유주를 모르면 계좌 노드로 유지 | 소유권 맵·기준 시각·미확인 상태, 소유주 집계 범위 |
| Episode 계좌·패턴별 (`episode-account`) | Episode 자체 transactionIds로 집계·선택·표 구성. Alert 데이터로 대체하지 않음 | Episode 범위의 근거·연결, 거래 cursor |
| Episode 소유주별 (`episode-owner`) | Episode 근거와 소유권 맵, 소유주·계좌 수·USD 합 | Episode 소유주 이웃, 집계 기준·미확인 상태 |

공통으로 업무 ID·revision·asOf, 제한된 nodes/edges, account-owner 매핑, 표시·생략 개수, 위험도·통화·합계의 집계 기준이 필요하다. 거래 페이지에는 from/to·시각·유형·확률·점수·사람 판정이 필요하며 기간·위험·정렬·조회 한도 조건을 함께 전달해야 한다.

기간·위험도와 노드·연결 선택은 실제 근거 거래와 함께 바뀌어야 한다. 샘플 재생은 occurredAt과 ID 순서로 거래를 보여주는 1/2/4배 재생이며 실제 금융망 이벤트 스트림이 아니다. 배치 좌표는 메모리의 화면 상태이며 서버에 저장하지 않았다. 노드 드래그는 거래 관계의 생성·재연결·삭제를 허용한다는 뜻이 아니다. 그래프의 실제 동작 검수는 [프론트 검증 기준](frontend-handoff.md#verification)에서 수행한다.

## 데이터 규모별 제한과 운영 연동 제안

이전 구현은 거래 126건의 합성 데이터 흐름이다. 수억 건 실데이터 처리, SLA, 부하 성능을 검증하지 않았다. **전체 원장을 내려받아 브라우저에서 집계하는 방식으로 운영 API를 연결하지 않는다.** 아래 서버 처리 방식·수치는 합의가 필요한 요구사항 제안이며 존재하거나 확정된 엔드포인트가 아니다.
