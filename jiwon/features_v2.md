# 피처 명세 v2 — 클래스 타깃 확장 (v1 61개 + 신규 23개 = 84개)

대상: HI-Large. v1(61개, [features_v1.md](features_v1.md)) 전체를 유지하고 아래 23개를
추가한다. 목적: 최약 클래스 신호 보강 — OVR 기준 BIPARTITE .143 · RANDOM .155 ·
CYCLE .208 · FAN-IN .304 (run_101).

## 설계 근거 3줄

1. **장주기 결함**: HI-Large 블록 span 중앙값 27일·p95 60일인데 v1 윈도우는 최대
   72h — 패턴의 시간 구조 대부분이 윈도우 밖이다. 정확 윈도우를 늘리면 큐·dict
   메모리가 폭발하므로(30d 이벤트 5,800만) **지수 감쇠 카운터**(O(1)/계좌, 큐 없음)
   로 장주기를 본다.
2. **클래스 모티프의 거래 단위 근사**: FAN-IN/OUT·BP = 일회성 간선 축적, RANDOM·
   STACK·CYCLE = 중계(받은 만큼 곧 보냄 — RANDOM 은 블록 중계 비율 ~90%가 유일한
   서명), CYCLE = 되돌림. 각각을 명시 피처로.
3. **인과성·구현 제약 유지**: 전부 t 미만 상태만 사용, 단일 패스 빌더에 계좌당
   O(1) 상태(감쇠쌍·최근값)만 추가. 신규 큐·신규 dict 없음.

## 감쇠 카운터 정의 (공통)

상태 = (value: f32, last_t: i32). 읽기/갱신 시 `value *= 0.5^((t-last_t)/HL)` 후
사용·증가. 반감기 HL 2종: **7일**(블록 내 활동 리듬), **30일**(블록 전체 스팬의
상대 축적). 이력 없으면 0 (v1 규약).

## 신규 피처

### A. 장주기 감쇠 활동 (u, v 각 5개 = 10)

| 피처 | 정의 |
|---|---|
| dk7_sent_cnt / dk7_recv_cnt | 송신·수신 감쇠 카운트 (HL 7d) |
| dk7_sent_usd_log / dk7_recv_usd_log | log1p(송신·수신 USD 감쇠 합) (HL 7d) |
| dk7_flow_ratio | log((dk7송신합+1)/(dk7수신합+1)) — G-S/S-G 허브의 "지금 모으는 중/뿌리는 중" 국면 |

### B. 신규 상대 유입 (u, v 각 2개 = 4) — FAN-IN·FAN-OUT·BP 축적 신호

| 피처 | 정의 |
|---|---|
| dk30_new_in / dk30_new_out | **처음 보는 상대**와의 간선 발생 시에만 +1 하는 감쇠 카운트 (HL 30d). 간선 첫 발생은 edge_cnt 0→1 전이로 판정 |

### C. 일회성 간선 비율 (u, v 각 2개 = 4) — FAN-IN/OUT·BP 의 "한 번씩만" 서명

| 피처 | 정의 |
|---|---|
| once_in_ratio | (정확히 1회 발생한 in-간선 수) / (in_deg+1) |
| once_out_ratio | (정확히 1회 발생한 out-간선 수) / (out_deg+1) |

상태: in/out_deg_once — 간선 0→1 전이 시 +1, 1→2 전이 시 −1.

### D. 중계·되돌림 (거래 단위 4개) — RANDOM·STACK·CYCLE

| 피처 | 정의 |
|---|---|
| relay_amt_logratio | log((이번 송신 USD+1)/(u의 직전 수신 USD+1)) — 받은 만큼 보내면 ≈0 |
| relay_gap_min | t − u의 직전 수신 시각. **수신 이력 없으면 −1** (0은 즉시 중계와 겹치므로) |
| backfill_amt_logratio | log((이번 수신 USD+1)/(v의 직전 송신 USD+1)) — CYCLE 되돌림 |
| backfill_gap_min | t − v의 직전 송신 시각. 이력 없으면 −1 |

상태: last_recv_t/usd, last_sent_t/usd (계좌당 4값). v1의 pass_speed_24h(24h 합
기반)와 달리 **수평선 무제한** — 며칠 간격 홉(중앙 홉 간격 ~2일)을 잡는다.

### E. 사이클 장주기 (1개)

| 피처 | 정의 |
|---|---|
| cycle3_flag_30d | v1 cycle3_flag_72h 와 동일 로직·동일 링(최근 송신 50건 캡), 시간 한계만 72h→30d |

## 상태 추가 요약 (계좌 213만 기준)

감쇠쌍 6종×(u,v 공용 배열 12개) ≈ 100MB + once 2배열 + last 4배열 ≈ 50MB.
큐·dict 추가 없음 → 빌더 피크 메모리 영향 ~150MB, 시간 영향 ~+20% 추정(실측 기입).

## 알려진 한계·주의 (사전 등록)

- B·C 축은 "수신계좌 기존 활동 유무" 신호를 강화한다 — 이 축은 생성기의 계좌
  사용 습관 의존이라는 경고가 이미 있다(bp_stack_case_analysis §시사점). 개선이
  나와도 포함 닻으로 교차 확인, 과신 금지.
- BP↔STACK 을 거래 단위 argmax 로 가르는 것은 원리적 한계(결정 증거가 미래) —
  v2 는 완화 시도일 뿐, 근본 해법은 블록 재구성 판정(이월 미결).
- 긴 사이클(4홉+)·경로 추적은 v2 범위 밖.
