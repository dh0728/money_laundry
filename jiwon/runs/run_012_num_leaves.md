# run_012 — num_leaves 확장 (127 / 512)

상태: 완료 — 둘 다 discard, num_leaves 31 유지
기준선: run_011b (λ=100, `min_sum_hessian` 1.0, `num_leaves` 31, 상한 1000,
PR-AUC 0.6652 / max-F1 68.98% / P@R0.7 32.94%, iter 279)
단일 변인: `num_leaves` 31 → 127(012a) / 512(012b). 나머지 011b 설정 고정
피처: features_v1
가설: 소폭 개선 또는 동률. 리프 수는 트리 하나의 표현력인데, 강한 정규화
(λ=100 + H≥1.0)가 과적합을 눌러주는 상태라 용량 증가의 순기능이 남을 여지가
있다 — 특히 D-4 약체인 구조 패턴(FAN-OUT·FAN-IN·BIPARTITE)은 분할을 여러 번
겹쳐야 표현되므로 리프가 더 필요할 수 있다. 반면 H≥1.0 이 잘게 쪼개는 분할을
막아 512 는 127 과 사실상 같은 트리가 될 가능성도 있다(하한이 바인딩되면 리프
수 상한은 남는 손잡이).
예측: 012a P@R0.7 32~34%, 012b 는 012a 와 근사(추가 이득 없음). 학습 시간은
리프 수에 비례해 늘어난다 — 012b 는 1시간 넘을 수 있음.

G-SCATTER +2.2 수준) — 용량을 4~16배 늘려도 클래스 신호는 늘지 않았다.

**정정:** "012a 32~34%" 예측은 빗나갔다(30.3%). "012b ≈ 012a" 는 대체로 맞았다 —
리프 수 127→512 에서 iter(220→217)·시간·지표가 거의 같다. H≥1.0 하한이 분할을
먼저 막아서 리프 상한이 바인딩되지 않는다는 해석과 부합. 즉 이 정규화 체제에서
`num_leaves` 는 남는 손잡이가 아니라 **이미 초과 상태** — 31 이 오히려 유효한
추가 정규화 역할을 하고 있었다.
