# HI-Medium + LI-Medium 합성 데이터셋 구축 기록 (G38)

- 작성일: 2026-08-12
- 목적: HI+LI medium 합성 학습 → HI-small test(G39)로 "도메인 합성이 HI 성능을 올리는가" 검증
- 비교 기준: G34 (HI-medium 단독 학습 → small 전이, test F1 0.6081 / AP 0.6261)

## 0. 배경 — 왜 합성하는가

- 출발점: "Medium으로 학습 → Small로 테스트" 경로(G34→G35)에서 F1 0.6081로 small 직접학습(G31, 0.7471) 대비 -0.14 열위가 확인됐다. 이 격차를 줄이는 방법 중 하나로 **학습 데이터의 다양성·양성 샘플 확대**가 거론됐다.
- HI-Large 학습은 17GB CSV·57GB 피처 행렬로 이 컨테이너(cgroup 27.3GB)에서 공수 대비 성공 가능성이 낮아 보류했다 (Medium 3GB도 OOM 3회 경험).
- 그다음 후보가 **HI-Medium + LI-Medium 합성**이다. 이유:
  1. 양성 샘플이 11,360 → 17,534건(+54%)으로 늘어 희소 클래스 학습에 유리
  2. 같은 생성기(IBM AML)라 스키마·통화·결제형식·패턴 분류 체계가 동일 — 합성 비용이 작음
  3. 두 도메인의 공통 세탁 메커니즘(사이클, 자금통과 등)을 일반화 피처로 학습할 가능성
- 리스크도 사전에 인지: G33에서 HI→LI 전이가 AP 0.06으로 완전 실패해 결정경계가 도메인별로 다르다는 증거가 있다. 그래서 합성하되 **모델이 도메인을 구분할 수 있는 장치(is_li 플래그)** 를 필수 조건으로 뒀다. 이 실험의 판정 기준은 단순하다: G34(0.6081)보다 오르면 합성 유효, 내리면 도메인 간섭.

## 1. 사전 검토 결과 (실측)

| 항목 | 결과 | 판정 |
|---|---|---|
| 스키마 | 양쪽 19컬럼 완전 동일 | 문제없음 |
| 범주값 | 통화 15종·결제형식 7종 완전 일치 | 원핫 충돌 없음 |
| 시계열 | HI 2022-09-01~09-28 / LI 2022-09-01~09-27, 거의 완전 겹침 | 같은 시간 split 규칙 적용 가능 |
| **계좌 ID 충돌** | `bank/account` 키 교집합 **14,414개**, 그중 **2,521개 라벨 모순** (HI만 세탁 2,133 / LI만 388 / 둘 다 103) | **접두사 없는 병합 금지** |
| 세탁률 | HI 0.1104% vs LI 0.0513% (2.2배 차이) | 사전확률 희석 대응 필요 |

## 2. 설계 결정과 이유

1. **그래프 병합 금지, ID 공간 분리**
   - 이유: `bank/account` 키 14,414개가 양쪽에 존재하는데 2,521개는 한쪽 세계에서만 세탁 노드다. 같은 계좌가 HI에서는 세탁·LI에서는 정상인데 노드를 합치면 ① 두 세계의 거래 그래프가 실제로는 존재하지 않는 경로로 연결되고(유령 엣지), ② 한 노드에 모순된 라벨이 붙어 학습 신호가 오염된다.
   - 방법: LI 노드 ID에 +2,077,023(HI 노드 수) 오프셋. 그래프 피처(cycle/passthru/pairagg/timefreq/pattern)는 각 도메인 내에서만 계산되므로 도메인 간 오염이 원천 차단된다.
2. **`is_li` 도메인 플래그 피처 추가**
   - 이유: 세탁률이 0.1104% vs 0.0513%로 2.2배 차이 나는 데이터를 그냥 섞으면 사전확률이 희석되고, 도메인별 결정경계 차이(G33에서 확인)를 모델이 하나의 경계로 억지로 학습하게 된다. 플래그를 주면 트리 분기가 도메인을 먼저 갈라 도메인별 경계를 학습할 수 있다. HI-small 평가 시에는 is_li=0 상수라 HI 전용 모델처럼 동작한다.
   - 구현: 82번째 피처, train 통계로 표준화 (다른 수치 피처와 동일 규칙).
3. **split 재분할 금지**
   - 이유: 합친 뒤 시간으로 다시 자르면 두 도메인이 train/test 양쪽에 섞여, test 지표가 "HI 운영 환경 투입 성능"이 아니라 "도메인 혼합 환경 성능"이 되어 질문에 답이 안 된다. 각 셋의 기존 시간 split(누수 검증 완료된 것)을 그대로 유지하면 기존 실험들과 시간 무결성이 동일하다.
4. **엣지 행 순서 보존 (HI → LI 순 concat)**
   - 이유: cycle3/passthru/pairagg 캐시가 엣지 행 번호에 정렬된 per-edge 피처이므로, 행 순서만 유지하면 수 시간짜리 그래프 피처 재계산 없이 캐시를 단순 concat으로 합성할 수 있다. HI 캐시는 기존 것을 재사용하고 LI 것만 신규 계산하면 되는 이유가 이것이다.

## 3. 구현 중 발견·수정한 구조 이슈

- 최초 설계는 "split 내 연속 번호가 필요하다"고 가정하고 split→source→node_id 순 재번호 로직을 작성·실행했으나 **오류**였음.
- 실제 구조 검증 결과: `node_features_*.parquet`는 **노드×split 3행 구조**(노드별 각 split 구간 피처)이고, `node_id`는 데이터셋 내 **전역 ID**. `load_node_features`가 split별 node_id 정렬 후 positional indexing을 하므로, 필요한 것은 split별 재번호가 아니라 **전역 ID 유지 + LI 오프셋**뿐이었음.
- 이 이슈를 놓쳤다면: 같은 계좌가 split마다 다른 ID를 받아 한 계좌의 시계열 행동이 3개의 가짜 계좌로 쪼개지고, 엣지 재매핑 테이블도 마지막 split 기준으로 덮어써져 그래프가 완전히 깨졌을 것. 1차 산출물은 폐기하고 스크립트 재작성 후 재실행했다.
- `src/gnn/build_dataset_hili.py`를 오프셋 방식으로 재작성해 재실행 (58초). 잘못 생성된 1차 산출물은 2차 실행이 덮어씀.

## 5. 최종 결과 — 판정: 기각 (도메인 간섭)

- G38 학습 완료 (3시드 HGB, 6시간 04분): 합성 test AP 0.5040 / F1 0.4493
- G39 평가 (HI-small, G35 동일 프로토콜): test AP 0.6010 / F1 0.5790 (small valid 임계값 0.795)
- **비교 기준 G35 (G34 HI-medium 단독): AP 0.6261 / F1 0.6081 → 합성이 F1 -0.029, AP -0.025 하락**
- 해석: 양성 +54% 확대 효과보다 도메인 결정경계 차이(G33 참조)의 간섭이 큼. is_li 플래그로는 상쇄 불가
- 운영 이슈: featmat 63M행 OOM 2회 → 5단계 프로세스 분리로 해결. 학습 OOM 1회 → GBT_LOW_MEM(valid 시드별 해제) 추가로 해결
- 후속 조치: 1단계 최종은 G31 유지 확정. 합성 데이터·캐시(featmat_hili 20.7GB 등)는 재실험 여지 대비 보관
